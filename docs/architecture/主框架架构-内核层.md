# 主框架架构 · 内核层（L1）

> 对应主方案 §8。

## 8. L1 · 内核层改造

### 8.1 配置 Schema 化

现有 `Config`（深度合并 / 热重载 / 原子写 / chmod 600）**全部保留**，增加 schema 驱动：

```python
# core/schema.py —— 本质是数据契约，不含任何 PySide6 依赖
class FieldType(Enum):
    BOOL = "bool"; INT = "int"; TEXT = "text"; SECRET = "secret"
    CHOICE = "choice"; MULTI = "multi"; LIST = "list"; SECTION = "section"

@dataclass
class FieldSpec:
    key: str
    type: FieldType
    label: str
    default: object = None
    choices: "list[str] | None" = None
    min: "int | None" = None
    max: "int | None" = None
    help: str = ""
    validate: "Callable[[object], str | None] | None" = None

@dataclass
class FormSchema:
    version: int = 1
    fields: "list[FieldSpec]" = field(default_factory=list)
    migrations: "dict[int, Callable[[dict], dict]]" = field(default_factory=dict)
```

框架负责：注入默认值 → 生成设置页 → 保存前校验 → 版本迁移。

**`poll` 不是双真源**：

| 项                            | 角色              | 说明                                                          |
| ---------------------------- | --------------- | ----------------------------------------------------------- |
| `Plugin.suggested_poll`（类属性）  | **唯一真源 / 组件声明** | 组件只说「我的合理节拍」；RUN_PERIODIC 类必填且 > 0                          |
| 设置窗**组件页页尾**的**运行间隔**下拉（行标签「框架检查间隔」） | **用户覆盖通道**      | 框架按 `run_mode` ＋ `suggested_poll` **自动生成**，写 `plugins.<id>.poll`；组件**不得**声明 `poll` 字段。2026-09-21 从「插件」管理页下沉到各组件自己的设置页 |
| 运行期                          | 合成              | `effective = user_config.get("poll", plugin.suggested_poll)` |

- **默认值判据单点**：`scheduler.poll_default_of(declared, run_mode, plugin_id)` —— 设置窗手上只有**类属性**（未启用的组件也要能画控件），调度器手上是**实例**，两者问同一个函数，界面显示的默认值不会与实际用的节拍分叉。
- **用户覆盖的读写**在 `Config.plugin_poll()` / `set_plugin_poll()`：读**用户差异层**（「用户改没改过」只在那一层答得出），写回默认值＝**删键**（留一个与默认同值的覆盖，会让组件日后调整建议值传不到用户）。
- **改完当场生效**：`PluginManager.set_plugin_poll()` 落盘后让 `Scheduler.set_poll()` 重挂心跳 ticker —— 只落盘不重挂就是「界面上改了、实际还按老节拍跑」的空转。
- 门禁 `test_no_plugin_declares_framework_poll_field`：组件 schema 里出现 `poll` 字段即红。组件**自己**的后台节律（`resolve_poll` / `helper_poll`，D27）不在这一列。

**热重载回环抑制（必做，实践坑）**：框架自身的写盘路径必须**不触发**热重载。否则「用户在设置页编辑 → 框架写盘 → 触发热重载 → 反写控件」会打断编辑（光标跳位、未提交输入被覆盖）。

**做法（2026-09-19 核对，与初稿不同）**：不置 `_suppress_reload` 标记、也不比对 content hash —— 靠 **mtime 对齐**。`Config._reload_from_disk()` 收尾时把 `self._mtime` 对齐到盘上值（`core/config.py:204`），而 `_check_mtime()` 只在 mtime 变了才重载（`:617`），于是**框架自写不触发重载**；`save_user()`（`:594`）自写后直接自 reload、**不 emit `changed`**，也就不反写控件。约束仍是「必做」，只是兑现手段换了。

**边界**：FormSchema 覆盖**表单类配置**；表格 / 树 / 日志流等动态集合视图仍走 CustomPage。据此，约 1400 行手写对话框中，hosts_guard 的域名表格部分保留为 CustomPage，其余（分类、开关、阈值）走 schema。

### 8.2 事件总线

`EventBus` 保留（Qt Signal 跨线程安全）。本轮补四件事。

#### 8.2.1 命名约定

| 类别   | topic 格式                         | payload                                                                            |
| ---- | -------------------------------- | ---------------------------------------------------------------------------------- |
| 插件状态 | `plugin.<id>.status.<key>`       | 必须是 `StateReport`；由框架在 tick 返回后自动 publish，插件不得自 publish（§5.3）。`<key>` 必带，不留可选写法 |
| 系统事件 | `system.<domain>.<event>`        | 由事件源定义                                                                             |
| 框架事件 | `app.<event>`（如 `app.panel_opened`） | —                                                                                  |

**框架事件：谁发、为什么常量在 `core`**。发布方是框架自身（今天唯一一条 `app.panel_opened` 由状态面板发，经装配器的 `set_open_notifier` 接到总线上），消费方是各组件 —— 所以 topic **常量**落在 `core/events.py`：组件的 import 面只应触及 `core` / `contribution` / `capabilities`，为一个字符串去 import 整个面板 widget 模块会把「视图实现」拖进「组件契约」。UI 层本身**不认 topic**（与本文件对 `set_ui_visibility` 的要求同款）：面板只报告「我打开了」。

`app.panel_opened` 的语义是「用户刚把面板打开」，载荷为空，**它存在的唯一理由是「按需型组件没有节拍」**：面板那一行画的是最后一次 `tick()` 的结论，而按需型只在启动 / 系统事件时跑 ⇒ 屏幕一直亮着时掉线，那一行会停在旧结论上。组件按 §8.3.1 声明该 topic 即可「每次开面板重跑一轮」；**框架不替所有按需型无条件重跑**（成本该由组件自己认领：有的 `tick()` 是空实现，有的要起子进程）。

#### 8.2.2 handler 契约：只标记脏，不干活

**现状风险**：handler 在总线所在线程（主线程）**同步执行**。插件若在 handler 里做 IO / 子进程 / 网络，会直接卡住 UI。

规则：**事件 handler 只允许做两件事**——更新内存状态、调用 `ctx.mark_dirty(reason)`。任何实际工作由调度器在 worker 线程跑一次 `tick()` 完成。

收益：① 事件风暴天然被合并成一次 tick，插件不必自己写 debounce（`notify_guard` 现有 `debounce=2` 可下沉）；② UI 不被事件拖卡；③ 事件路径与轮询路径汇入同一执行入口。

#### 8.2.3 事件源由框架统一提供（懒加载）

插件不应各自接系统 API。收归框架后按需启动——**无人订阅则不加载**：

| topic                                        | 源                             |
| -------------------------------------------- | ----------------------------- |
| `system.network.changed`                     | `SCNetworkReachability`       |
| `system.usb.changed`                         | IOKit 设备插拔                    |
| `system.helper.observed`                     | 守护会话推来的领域事实（2026-09-29 取代 `system.file.changed`） |
| `system.power.wake` / `.sleep` / `.display_wake` / `.display_sleep` | `NSWorkspace` 通知（**两族**：系统与显示器各自一对睡眠／唤醒，共用同一个观察者） |
| `system.screen.locked`                       | `NSWorkspace` 通知（尚未实现）      |

> **2026-09-29 收口**：「文件通道 → 会话」之后 `system.file.changed` 连同它的源 `core/filewatch.py`
> 一并删除 —— 观测由守护主动**推**来，框架转成 `system.helper.observed` 再分发（分发规则一字未变，
> 见 `core/events.py`）。插件侧的 `Plugin.file_watches()` 相应换成 `Plugin.subjects()`。

#### 8.2.4 生命周期

插件 `stop()` / 卸载时，框架按注册记录**自动 unsubscribe**（已落地：`EventBus.unsubscribe` ＋ `plugin_manager` 在卸载路径上分条撤回 —— 状态订阅 / 会话 subject / 任意事件 topic）。不撤的话，卸载的插件会泄漏 handler 并继续回调已销毁对象。

### 8.3 调度器

#### 8.3.1 调度权归框架

**插件只声明，不自己起时钟：**

```python
class Plugin:
    suggested_poll: float = 30     # 秒；取代 plugin_config().get("poll")
```

> ◷ 原样例还有 `subscriptions: tuple = ()`（插件声明任意 topic）—— **已裁不做**（无消费方）：
> 事件源只收归了文件一条。裁决与依据见《主框架架构-插件可插拔》的 `Plugin` 类样例后注。

**禁止**：`QTimer` / `threading.Timer` / `QThread` / `while True + sleep`。（UI 内部交互用途除外，如 `autotype` 倒计时、`recognize` 剪贴板监听——它们不属于后台轮询，生命周期跟随窗口。）

**（2026-09-22 已收口）曾经的违规**：`ipad_tunnel/bridge.py` 曾自建 `threading.Thread` + `threading.Timer`，同时逃出了**调度管控**&#x4E0E;**`teardown()` 生命周期**。现迁为框架托管的 resident service（`RelayService` / `LinkProbeService`），插件侧不再 `import threading`（`tests/test_ipad_tunnel.py` 按模块属性钉住）。

但要注意：**`bridge.py` 不是轮询，是 select 多路复用的 TCP 透明中继**，把它塞进 `suggested_poll` 会破坏中继语义（一次 tick 抓不完一条连接上的数据）。正确归类：**它不是「调度器的例外」，而是「不该进调度器」**。登记 `start()` / `stop()` / `teardown()` 三钩子，由框架托管生命周期。

> 普适表述：**「禁止私起线程」管的是后台轮询；长驻连接型资源走框架托管的 resident service，两条路都收归框架，没有第三条。**

**（2026-09-30 补）周期型服务还有一条合法出口：`ctx.wake_service(name)`**（`Plugin.wake_service` 包装）。用户按下某个键要「现在做一次」时，插件不必（也不许）自起线程或自建时钟 —— 它请求框架把**某一拍提前**（`core/resident` 的等待是两路可打断的：到期与「有人叫」各占一枚事件，`stop()` 同时置位两者）。语义是**提前一拍**，不是插队并行；服务没在托管（组件被禁用 / 服务已熔断 / 名字写错）时返回 `0`，调用方据此如实降级（界面就别再说「正在做」）。首个消费方：hosts 管理窗的「更新」键。

#### 8.3.2 保留不动（踩坑结晶）

每插件独立单 worker 线程池（卡死不连坐）、心跳驱动 tick（相位错开，单 `Heartbeat`）、僵尸 tick 回收、熔断自愈（自退避）、watchdog 超时作废迟到结果、`FAIL_BREAK` 类熔断 / `FAIL_LOG` 类只记日志（原 `role` → `failure_policy`，2026-09-15 已落地，见【契约】D11）。**这些是实机踩出来的，本轮不改语义。**

> 原来这条里挂着「心跳 `last_ok`」一项（供面板判「守卫失联」）。该字段 2026-10-05 删了：写侧每次成功 tick 都记，读侧全仓为零，而「失联」实际按**状态 topic 多久没收到事件**判（`_check_stale` ＋ 组件 `stale_after`）—— 那是另一个量，与 tick 有没有跑通无关。现在 `status()` 只交 `broken` / `fail_count` / `running` / `dirty`。

#### 8.3.3 对齐机制（三层）

**（2026-09-22 / 2026-09-29 已收口）**收口前曾有**四套**彼此不知道对方存在的时钟：scheduler 的 QTimer 们（3s/5s/300s）、helper 主循环（1s 轻查 + 三套 cycle）、`bridge.py` 的 threading.Timer、插件私有的 QFileSystemWatcher。收口后：scheduler 的全部定时器 → **单一心跳**（`core/heartbeat`）；helper 主循环 → selectors 阻塞（空闲零唤醒）；`bridge.py` → 框架托管的 resident service（自持线程，**故意不挂心跳**，见 `core/resident.py`）；插件私有 watcher → 随文件事件源一并删除。

| # | 机制       | 问题                                      | 做法                                    |
| - | -------- | --------------------------------------- | ------------------------------------- |
| 1 | **相位错开** | `add_plugin()` 里启动即跑一轮 → 所有插件在 t=0 同时点火 | `phase = crc32(plugin.id) / 2**32 * interval`（**不取模**，理由与边界见（b）） |
| 2 | **节拍对齐** | N 个插件 N 个 QTimer，各自漂移                   | 单一 1s 心跳 QTimer 取代全部定时器，到期判定用累积式      |
| 3 | **并发闸门** | 现状理论上所有插件可同时跑 tick                      | ◷ **已裁不做**（批次 8），理由见（c）                |

两处实现要点：

**（a）到期判定必须累积，不能用取模。** `elapsed % interval == phase` 一旦因闸门排队、系统休眠、主线程卡顿错过窗口，就要等**整整一个 interval**。改为：

```python
if now - last_fire[pid] >= interval:
    last_fire[pid] += interval                       # 累加而非赋 now，避免漂移累积
    if last_fire[pid] < now - interval:              # 落后超过一个周期（休眠回来）
        last_fire[pid] = now
    fire(pid)
```

**（b）相位不要用 `hash()`，也不要对 `interval` 取模。** Python 3 对 str 的 `hash()` 默认启用随机化（`PYTHONHASHSEED`），行为不可复现、测试无法断言 ⇒ 改用 `zlib.crc32`。**取模同样不行**（2026-10-02 修）：`crc32` 是整数，`int % float` 的余数在整秒 `interval` 上只能落在整秒 —— `interval=1.0` 时 `n % 1.0` 恒为 `0.0` ⇒ **1s 档订阅的相位全体为 0**，与「不 lockstep」正好相反，且不报错、不留痕。相位按散列的整条 32 位取比例：`crc32(key) / 2**32 * interval`（除以 2 的幂在二进制浮点里精确，跨进程逐位可复现）。

另有一条**粒度边界**（心跳决定，相位公式修不了）：到期判定跑在心跳的整数拍上，细于一拍的相位会被量化掉 ⇒ `interval` 不大于心跳周期的订阅（生产里就是 1s 档）**无论相位取何值都在同一拍上**；相位能拉开的是 3s / 30s / 300s 这类跨拍节律（3s ⇒ 三个拍位）。**「相位错开」这条对 1s 档不成立，别照抄。**

**（c）并发闸门：◷ 已裁不做（批次 8）。**`core/scheduler.py` 的类注释写明两条否决理由 ——
全局「最多 2 个 tick 在跑」与 §8.3.2 的「卡死不连坐」**互斥**（一个卡死 tick 占住名额，会把其余插件
拖到 `TICK_TIMEOUT` 之后）；且会挡掉 Qt 事件循环启动前的**首轮同步点火**（那是首屏数据的唯一来源）。
**防惊群改由层 1 的相位错开承担**（边界：间隔不大于心跳周期的订阅拉不开，见（b）），不另设闸门。初稿那套「排队等待与执行超时共用同一 deadline」
的排队语义（入队即算 `_running` / 从入队计时 / 出队超时即丢弃）**没有实现，也不再排期**。

#### 8.3.4 事件 + 轮询对账

**事件一定会丢**：进程未运行时发生的事件、系统漏发、watcher 漏报。因此 `suggested_poll` 的语义是 **resync 兜底周期**，不是主要工作方式。规则：订阅了事件的插件**仍必须声明 `suggested_poll`**，不允许 0 或无限。即 Kubernetes informer 的 watch + resync 模式。

#### 8.3.5 不跨进程对齐时钟

app 侧 tick 与 helper 侧 cycle **各自独立**（观测由守护经会话推来），**天然解耦，不试图同步两个进程的时钟**。真正需要的是**状态新鲜度**而非对齐：判「守卫失联」看的是**某状态 topic 多久没收到事件**（面板 `_check_stale`，阈值由插件 `stale_after` 给），不再看任何文件 mtime。`notify_guard` 的 `STALE_S = 15`（poll 3s × 5 余量）即此模式。

#### 8.3.6 UI 刷新合并

`tick()` 产出的 `StateReport` 不直接触发重绘，进入渲染队列，**50ms 窗口内合并去重**（`core/scheduler.py::DIRTY_WINDOW_MS`），避免高频 tick 造成面板抖动。

取值理由（2026-09-19 核定为 50ms，初稿写的是 100ms）：窗口要大到足够把**同一瞬间到达**的多个标记合成一次点火（一条推送含多个 subject / 多状态插件逐 key 变更），小到让秒级刷新的观感不受影响；窗口内多次 `mark_dirty` 只点火一轮，计时从**首个**标记起算、不因后续标记顺延（避免持续风暴饿死点火）。（2026-09-30 改注：原理由「吃掉 helper 写临时文件 + rename 的 2 次目录变化」随文件通道下线而失效，窗口值不变。）

#### 8.3.7 克制清单（明确不做）

- 引入 APScheduler / RxPY 等第三方调度库 —— 1s 心跳足够，零依赖
- cron 表达式、持久化调度、跨设备同步
- 动态调频 —— 周期保持人工声明
