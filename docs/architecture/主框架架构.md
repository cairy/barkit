## 1. 为什么重写

BarKit 功能已完成，但它目前是**一个能跑插件的应用**，不是**一个框架**。四条判断依据：

### 1.1 扩展点是枚举的，不是开放的

`ContributionRegistry` 硬编码 4 个贡献方法（`panel_rows` / `header_chips` / `settings_pages` / `primary_actions`）。新增一个 UI 位置要同时改三处：`Plugin` 基类、注册中心、`ui/` 消费端。且 `panel_widget` 与 `panel_rows` 两条 API 并存（hosts_guard、\_template 用后者，其余用前者）。

### 1.2 UI 由插件自由绘制

`panel_widget()` 返回裸 `QWidget`，插件自己拼 `StatusRow` / `Switch` / `Badge`、硬编码 emoji（`"🧭"` `"✨"`）、手写设置页。框架没有渲染权——这是风格发散的结构性根因，不是审美问题。

### 1.3 系统能力被锁在插件里，root 通道无归属

| 能力 | 当前位置 | 行数 |
| ------------------------------------------ | ------------------------------- | ---- |
| 特权文件写 / LaunchDaemon / 路由 / DNS / 隧道（root） | `plugins/route_guard/helper.py` | 2223 |
| USB 隧道桥接（用户态） | `plugins/ipad_tunnel/bridge.py` | 573 |

`helper.py` 名义上属于 route_guard，实际已跑着三套 cycle（路由 / 隧道 / hosts），是**事实上的框架级 root 执行器**——却没人承认这个定位。后果：新插件要 root 能力就得往这个文件塞第四套逻辑；改任何一处都要 bump `HELPER_VERSION` 重装 daemon；删 route_guard 会连累另外两个插件。

### 1.4 附带问题

- `required_permissions` 是死 list，无运行时校验与引导 UI
- `badge_role="mute"/"alert"` 字符串魔法值散落
- `app.py` 263 行上帝接线，产品规则（徽标聚合）写在应用入口层
- 约 1400 行手写配置对话框（`manage_dialog.py` 571 + `config_dialog.py` 310 + 244 + 278）（**◷ 2026-09-19：四份里三份已随设置面收归整文件删除，`manage_dialog.py` 改名 `manager_view.py`，仅作历史基线保留**）
