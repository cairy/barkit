class Plugin:

  id: str = ""
  name: str = ""
  run_mode: RunMode = RUN_ON_DEMAND # RUN_PERIODIC | RUN_ON_DEMAND（见【契约】D10，2026-09-15 已落地）
  failure_policy: FailurePolicy = FAIL_LOG # FAIL_BREAK | FAIL_LOG（见【契约】D11，2026-09-15 已落地）

  required_permissions: list[str] = [] # 权限**名**（"accessibility" / "screen_recording" / "root"）。◷ 原设计是 tuple[Permission, ...] 枚举，未实装 → 《主框架架构-能力层》§7.1

  # ---- 生命周期 ----

  def stop(self) -> None: ... # 见 §7.4.7：依附型变更要拆除

  # ---- daemon ----
  def tick(self) -> "StateReport | None": ...
  # 框架在 tick 返回非 None 后自动 publish；插件不得自己 publish 该前缀

### 9.1 完全可插拔：资源清单、卸载与迁移

```python
@dataclass
class SystemMutation:
  """一条系统变更的声明，供卸载前展示与 stop() 决策使用。"""
  description: str # 人类可读，如「/etc/hosts 中的 BarKit 标记块」
  survives_app_exit: bool = True # 自持型(True) / 依附型(False)，见 §2.5

@dataclass
class DeferredRemoval: # 卸载收尾「延迟删除」声明，见下
  ready: Callable[[float], bool] # 收到 watermark，答「现在收尾安全吗」
  timeout_s: float = 5.0 # 等待上限；超时＝什么都不撤

@dataclass
class PluginResources:
  """插件持有的全部外部资源。框架据此做彻底卸载。"""
  data_files: list[str] = field(default_factory=list) # 相对 APP_SUPPORT
  seed_files: list[str] = field(default_factory=list) # C 类种子，必须是 data_files 的子集
  config_section: str = ""
  hotkeys: list[str] = field(default_factory=list)
  helper_tasks: list[str] = field(default_factory=list)
  system_mutations: list[SystemMutation] = field(default_factory=list)
  needs_root: bool = False
  root_binaries: tuple[str, ...] = () # A 类，见 §9.3
  deferred: DeferredRemoval | None = None # 收尾时机交给消费方，见下
```

**整个清单里只有 `deferred` 带行为，其余全是纯数据**（且只在卸载路径被读）：`data_files` 可能被
**另一个进程**读（root helper 独立轮询），框架当场删会让它读到「不存在」—— 按既有语义「不存在＝
冻结」，**撤销就永远不生效**（2026-09-17 实测 route_guard）。`ready()` 收的 `watermark`（＝本次
卸载开始时刻）用来排除**陈旧回报** —— 消费方上一轮写回的「早已撤干净」不算本轮的确认。

**`seed_files ⊆ data_files`**：C 类种子 =「随包提供了初始内容的 `data_files` 子集」，不是与它并列的第二份清单。卸载时删 `data_files − seed_files`；seed 保留（已是用户数据）。

**分类依据是清单声明，不是运行期状态**：凡声明在 `seed_files` 中的，无论是否被改写过，卸载一律保留。禁止实现成「运行期检测文件是否被修改」——那样行为随时间漂移且不可预测。

#### 卸载流程（框架统一编排）

```
1. disable() stop → 反订阅 → 移除贡献 → 刷新 UI
2. teardown() 插件复原系统状态（撤路由 / 删 hosts 块 / 拆隧道 / 停子进程）
3. 移除 helper task 从 `tasks` 那份意图里摘除该插件的 task（零重装）
3.5 移除排序项 从 plugin_order 移除该插件 id（§6.4）
4b. 回收 A 类资产 按 §9.3 对账（wanted 去掉本插件后重算），仅差集非空才需 root
── 以上一律**当场**跑 ──
4. 删数据文件 删除 data_files − seed_files；seed_files 保留（勾选才删）
5. 删配置段 plugins.<id> 与 hotkeys.<name>
6. forget() 从发现结果移除（内部即摘 helper task 并重算表）
7. 收尾 若已无插件 needs_root → 提示可卸载 helper
── 以上是**延迟区**：插件声明了 `deferred` 时挂到框架心跳上等消费方收敛 ──
```

第 2 步是**唯一需要插件自己实现**的（只有它知道自己改了什么系统状态），其余全由框架按清单执行。执行前把 `system_mutations` 展示给用户确认。

**延迟区的三条口径**（2026-09-17 落地，起因是卸载 route_guard 后静态路由撤不掉）：

- **必须覆盖整段收尾、不只删文件**：摘 helper task 的是第 6 步 `forget()`（写成
  `enabled: false`，顶掉内置默认值），只延迟第 4 步的话消费方**被敲醒也不会再跑那条 task**。
- **超时＝什么都不撤**（文件 / 配置段 / task 声明 / 发现结果全留），只记 ERROR ＋ 把原因交给
  界面。往回退安全（期望态还在，消费方下次自然轮次照样收敛），硬往前走才是既成事实。
- **`uninstall()` 返回 True 只表示「流程已受理」**，不再是「磁盘已清干净」：延迟那段成了没有、
  没成为什么，经 `on_uninstall_settled(plugin_id, problem)` 回报（界面先 `rebuild_pages`）。
  延迟期间插件**仍留在列表里、开关是关的**（task 没摘、文件还在，抹掉那行才是撒谎），通常 ≤5s 自刷。

#### 导出 / 导入

```python
def export_data(self) -> dict:
  """序列化本插件全部用户数据。不得含绝对路径与机器相关值。"""
def import_data(self, payload: dict) -> None:
  """恢复。框架保证在插件 stop 状态调用。"""
```

**secret 字段的处理**：`autotype` 的配置含明文密码。

- **不加密** —— 加密要引入口令管理，成本高于收益，且导出包本身已是 600 权限的本地文件。
- **默认排除** `FieldType.SECRET` 字段，用户需在导出时**显式勾选**才包含。这比「全量导出 + 警示」更进一步：**从源头降低暴露面**。
- 勾选包含时，导出包强制 `chmod 600` 并在 UI 明示；导入后校验权限位，非 600 则告警。

打包为 `barkit-plugin-<id>-<ts>.zip`：`manifest.yaml` / `config.json` / `hotkeys.json` / `data/`。导入时校验 `api_version`，不匹配即拒绝。

### 9.2 安装流程

**现状**：只有「发现」，没有「安装」。`core/loader.py` 扫到 `manifest.yaml` 后直接 import 并实例化，**没有资产部署、没有配置注入、没有失败隔离**。

四阶段：

```
1. 发现 discover 内置 pkgutil 扫描 + 外部 manifest（含 api_version 门禁）
2. 校验 validate api_version → SPEC_VERSION → root_binaries 是否在封闭集内
  → 权限声明 → Plugin 子类有效性
3. 装配 provision 部署 B/C 类资产（幂等）→ 合成配置默认值 → 实例化 → start()
4. 隔离 isolate 任一步失败 → 回滚该步、插件标记 failed、记入 UI 的「插件问题」列表
```

三条原则：

- **装配失败必须隔离**。一个插件装配失败不得影响其他插件或主程序启动。
- **每个阶段可独立失败并给出人类可读原因**。
- **不引入安装状态清单**。B/C 类资产部署幂等，配置默认值是运行时合成层，两者都不需要记住「装过没有」。少一份状态就少一份残留。

**isolate 只回滚运行时态，已部署资产不回滚**：

- 回滚范围：插件实例、已注册的贡献、helper task、resident service、UI 挂载点。
- 不回滚范围：B/C 类资产、A 类资产、已写入的配置。它们交给**幂等与对账**处理——下次装配自然收敛。强行回滚 C 类反而制造「删用户数据」的新风险。

#### 升级流程（仅外部插件；内置插件随 App 整体升级）

外部插件升级 = 目录覆盖文件：若新版 validate 失败，旧版已被覆盖——**升级没有原子性**。

```
1. 落暂存 新版本落到 <external_dir>/.staging/<id>-<version>/
2. 预检（不写盘） validate（纯检查）+ provision 的 dry-run：
  按资源清单列出将要部署的文件与目标哈希，与磁盘现状比对，不写任何字节
3. 原子切换 先 stop() 运行中的实例与 resident service → rename 替换 → 启动新版
4. 装配 真实 provision 在此执行（幂等写 B/C 类资产）→ start()
5. 失败处理 任一步失败 → 不动原目录，旧版继续可用，暂存目录保留供排查
```

**预检为什么要 dry-run 而不是真跑一遍 provision**：真执行会让新版 assets / 种子先于代码切换落盘；一旦后续 rename 失败、旧版继续运行，旧版读到的却是**新版 B 类资源**——「失败保留旧版可用」的承诺就成了漏洞。而不写盘却又叫 provision，则对 provision 的覆盖为零。故预检 = validate + dry-run，**真实 provision 后移到 rename 之后**。dry-run 与真实装配共用同一份清单计算逻辑，只差一个 `dry: bool`。

### 9.3 资产分发：三类资产的边界

| 类别 | **物理分发** | **执行授权** | 安装位置 | 权限 | 卸载时 |
| --------------------------------------- | -------- | ------------------------------- | ------------------------------------------ | ----------------------------------- | ----------------------- |
| **A. root 执行的二进制**（`hev-socks5-tunnel`） | 可随插件包提供 | **框架**封闭集登记（名字 + sha256），未登记不执行 | 系统域 `/Library/Application Support/BarKit/` | `root:wheel 0755` + ad-hoc codesign | 引用归零后删 |
| **B. 插件只读资源**（图标、模型、模板） | 插件 | 不需要 | `APP_SUPPORT/plugins/<id>/assets/` | 用户域 0644 | 随插件删 |
| **C. 种子数据**（初始规则、分类表） | 插件 | 不需要 | `APP_SUPPORT/`（`data_files` 所在处） | 用户域 0600 | **不删**（已是用户数据），除非用户显式勾选 |
> _理由见 「§9.3 物理随插件·授权归框架」。_
> _理由见 「§9.3 A 类授权不交插件」。_
> _理由见 「§9.3 hev 归属判断对一半」。_
```python
# 框架侧（capabilities/helper/rootbin.py）—— 与 ACTION_SCHEMAS 同级的封闭命名集
ROOT_BINARIES: Mapping[str, RootBinary] = {
  "hev-socks5-tunnel": RootBinary(sha256="<发行态基线>", upstream="hev-socks5-tunnel 9a06bc6"),
}
# proc.manage 的可选名从 ROOT_BINARIES 派生，禁止两处硬编码（否则漂移即事故）
ROOT_BINARY_NAMES = tuple(ROOT_BINARIES)
```

#### A 类的 root 授权路径
> _理由见 「§9.3 A 类授权路径」。_
设计要点：

1. `install()` 是**幂等的对账安装器**：装 helper → plist → 按差集部署/回收全部 A 类资产 → 重写完整性基线。
2. **仅在差集非空时才需要 root**。安装/卸载一个不涉及 A 类的插件**不弹授权**。

批次归属：硬依赖 helper 归位（批次 4）。批次 4 之前 A 类仍走现状 `route_guard/daemon.py` 路径。

#### 装配顺序与 codesign（一个实测推翻过方案的事实）

顺序：`名字 ∈ ROOT_BINARIES` → sha256 匹配**发行态基线** → `install -m 0755` + `chown root:wheel` + 删 quarantine → ad-hoc codesign。任一步失败 → 插件标记 `failed` 并隔离，**不做降级**。

**ad-hoc codesign 不是确定性的**——实测同一输入两次 `codesign -s -`，sha256 分别为 `00d267a8…` 与 `b1fcabf1…`。`codesign -s -` 会**改写文件字节**且结果不可复现，因此「构建期签名、签名后哈希即基线」技术上不可行，**已签名资产不能用文件哈希做运行期守卫**。

| 资产 | 是否签名 | 安装期校验（发行态） | 运行期守卫 |
| ------------------- | --------- | ------------------------- | --------------------------------------- |
| `helper`（Python 源码） | 否 | sha256 == 源码基线 | **sha256**（可复现） |
| `hev`（Mach-O） | 是（ad-hoc） | sha256 == **签名前**仓库内文件的基线 | **`codesign -v` + owner/权限**（哈希不可复现，不用） |

发行态基线记的是**仓库内、签名前**的文件哈希——稳定、可复现、可进 git、可人工 review。
> _理由见 「§9.3 装配顺序与 codesign」。_
> 顺带修掉一处现存降级路径：`daemon.py:250`「缺失不阻断安装」——正是它催生了 P0-1 的用户域 fallback。改为**缺失 / 哈希不匹配即安装失败并给出明确原因**。

#### 无状态对账（替代引用计数）

多个插件可声明同一个 A 类资产。删除时机**不用引用计数**（那等于引入一份安装状态），而是**重算差集**：

```
deployed = 系统域实际存在的 A 类文件名
wanted = ∪ 所有【已安装】插件（含 disabled、含 failed）的 resources.root_binaries
删除 deployed - wanted，部署 wanted - deployed（幂等）
```

**「已安装」的口径 = discover 成功的插件集合，与 validate / 运行时状态无关**（failed 也计入）。理由：外部插件升级失败时旧版**仍在运行**，若 failed 不计入，对账会删掉正在使用的 A 类资产。**资产回收宁可延迟，不可误删。**

**对账只在安装与卸载触发，禁用与启用不触发。** 按「已启用」推演会出事：禁用 ipad_tunnel（高频可逆操作）→ wanted 掉 hev → 对账删 hev（需 root + 授权）→ 重新启用 → 再部署 → **再弹一次授权**。

> 对称表述（与「禁用保留配置」完全同构）：**禁用降级的是运行状态，不是资产存在性。**

#### 新增一个 root 二进制的路径

与新增一个原语同源：改框架源码（登记 `ROOT_BINARIES` 条目 + 发行态基线哈希）→ bump `HELPER_VERSION` → 重装 daemon。**同一套摩擦力，同一个理由。**

**B / C 类的部署**：B 按内容哈希幂等覆盖（只读资源，插件升级应生效）；C **仅在文件缺失时写入**（一旦存在就是用户数据，永不覆盖）。

### 9.4 卸载流程

见 §9.1 的七步。关键澄清：`LaunchDaemon` 与 `helper` 是**框架资产**，卸载 route_guard / ipad_tunnel **不应**拆 helper——这是 §7.4 把 helper 归位框架的理由。七步里第 4~7 步是
**延迟区**：插件声明了 `deferred` 时不当场跑，改挂到框架心跳上等消费方收敛（见 §9.1）；没有声明的插件七步全当场跑完，与从前一致。

A 类二进制（`hev`）**不是**这个逻辑：它物理上随插件分发，按无状态对账处理。区分点在于：helper 是框架自己要跑的东西，hev 是「经框架授信后、由 root 代插件执行的东西」。

### 9.5 配置分发与合并

**问题**：现状 `config.default.yaml` 是集中文件，内含全部 `plugins.<id>` 段；插件自身**没有声明默认配置的途径**。引入 `config_schema()` 后出现两个默认值真源，必须选一个。

**决定：单一真源 = 插件的 `config_schema()`。** `config.default.yaml` 只保留框架级默认（`app.*`、`hotkeys.*`、`plugins.<id>.enabled`）。

理由：可插拔的前提是「插件自带它的一切」。若默认值散在框架的集中文件里，卸载插件还得同步改那个文件——与「删除后无任何残留」直接冲突。

```
runtime = deep_merge(
  deep_merge(framework_defaults, plugin_defaults), # 后两者都是内存层，不落盘
  user_config # config.yaml，只存差异项
)
```

三个直接好处：① 插件升级新增字段 → 自动获得默认值，且**不覆盖用户已改的值**；② 插件卸载 → 默认值随 schema 消失，用户差异项由 `remove_plugin_section()` 删除；③ 装配插件不产生任何写盘。

**写入时机**：只有用户主动改设置时才写 `plugins.<id>`，且走框架写盘路径（抑制热重载）。

**版本迁移**：`FormSchema.migrations`。当前版本记在 `plugins.<id>._schema_version`（下划线前缀 = 框架保留键，渲染器跳过）。记录缺失视为全新安装，直接取默认值。

| 场景 | 行为 |
| ----------------------- | ---------------------------------------- |
| 全新安装 | 默认值由 schema 合成，**不落盘** |
| 插件升级（schema version +1） | 按 `migrations` 迁移一次，回写 `_schema_version` |
| 用户改了某项 | 只把该项写入 `config.yaml` 差异层 |
| 禁用 | 配置**保留** |
| 卸载 | 配置段**删除**；如需保留先导出 |
