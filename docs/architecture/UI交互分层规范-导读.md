## 1. 设计哲学

1. **单一渲染出口**：所有可见控件由 Shell 渲染，插件只声明数据。杜绝插件各自 `new Badge / new Switch / 自绘圆点`（现状违规点）。
2. **信息密度自上而下递减**：托盘（看一眼知好坏）→ 面板（这一项现在怎样）→ 详情面（我要改/装/诊断）。
3. **就地优先 + 分层入口**：能就地 toggle 的就地解决，绝不弹窗；需填表/走流程的进详情页；只有全局与纯偏好进设置面板。
4. **状态同源**：健康态、模式态、托盘聚合态来自同一份数据，杜绝三套词汇并存。
5. **顺序同源**：标题栏图标条、中间组件条目、设置窗的插件分页，**三处渲染顺序由同一个来源决定**，框架不各自重排。
6. **双主题一致**：所有颜色取自 `styles.TOKENS`，浅/深自动换肤，不硬编码。

## 3. UI 分层模型

```
L0 Tray (NSStatusItem) 唯一对外出口：单点聚合角标
        │ 点击
  ▼
L1 Panel Header 组件图标条：每插件一枚取值图标染级别色（无角标）
        │ 点击图标展开
  ▼
L2 Panel Status Rows 行数由组件声明（0–n）：健康角标 + 模式徽标 + 实时值 + Switch
        │ 点击整行（有详情页才响应）
  ▼
L3 Detail Surface DetailForm（模态任务流）+ SettingsPage（常驻分页）
```

| 层 | 渲染权 | 现状缺口 |
|---|---|---|
| L0 Tray | Shell（聚合 L1 角标） | `compute_tray_badge` 是游离函数，与芯片级别脱钩 —— 已归并为纯函数 `shell/renderers/badge.py::tray_queue()`（框架方案 v3.0 §6.6，函数名按 2026-09-19 核对更正） |
| L1 Header | Shell（TitleBarIcon） | 现状是「状态值芯片」语义：由插件各自贡献、数量不定（当前 4 个插件在贡献），没有「每插件一枚」的保证 |
| L2 Rows | Shell（StatusRow） | 角标由框架绘制（取值图标染级别色），插件不自绘 |
| L3 Detail | Shell（托管 QDialog / 分页） | 模态表单与设置页边界模糊，各插件自管窗口 |

> **v2.0 修正**：v1.8 称现状「写死 通知/路由 两枚」，与代码不符。`panel.py:382` 是 `set_header_chips(contributions.header_chips())` 动态注入，当前有 route_guard / ipad_tunnel / hosts_guard / notify_guard 四个插件在贡献 chip。真实缺口是**语义**而非**数量**：chip 表达的是「某个状态值」，而本方案要的是「组件身份 + 最坏态」——一个插件一枚，与它有几个状态无关。

## 4. 状态模型（v2.0 核心修正）

### 4.1 分工：静态归 Spec，动态归 StateReport

这是与框架方案 v3.0 §5.3 对齐的关键，也是 v1.8 最大的问题所在——v1.8 的 `StateSpec` 把静态与动态字段混在一个 dataclass 里，导致「状态变了要不要重建 Spec」没有答案，状态流出现第二条路径。

```
StateSpec（静态，声明方法产出，只在加载/配置变更/启停时重建）
  key / states（取值枚举：每项带 level / icon / text / alerts）

StateReport（动态，tick() 产出，框架自动 publish）
  state / summary / updated_at

关联键：plugin.<plugin_id>.status.<key> ← topic 由 identity 派生，零新增概念
```

### 4.2 StateSpec

**字段定义见《组件契约规范》§2.2（状态）/ §2.3（级别）；本节只讲形态要点。**

| 要点 | 说明 |
|---|---|
| 一台状态机 | `StateSpec` 枚举它**全部可能的取值**，运行期只回报「现在在哪一格」——级别与文案由取值派生，收敛为单点 |
| 取值自带级别 | 每个取值（`StateOption`）自带 `level`、取值图标与默认文案；级别是颜色 / 角标 / 托盘的公共词汇 |
| 取值自带提醒意图 | 某个取值是否值得提醒到托盘，由该取值的 `alerts` 声明——**不允许靠 `key == "muted"` 这类字符串判断** |
| 静态 | 取值枚举属声明，不随状态变化重建；运行期数值一律走报告（见 4.1），不得塞回 Spec |

### 4.3 派生规则（全由框架算，插件不参与位置决策）

| 派生 | 规则 |
|---|---|
| **每插件代表态** | 该插件**全部状态机的当前取值**中取最坏 `level`；严重度相同时取**先声明**的那台（声明顺序 = 作者写的关注度顺序；状态模型与平局规则见《组件契约规范》§2.2） |
| **标题栏图标** | 取每插件代表态：图标 = 取值图标，颜色 = 级别色（**无角标**，见《组件契约规范》§1.4 / §2.4） |
| **L2 健康角标** | 同上，同一份数据，杜绝两套健康表达 |
| **托盘角标** | 取「最坏的那一级」里的组件，角标画该组件的**取值图标**、染其级别色；同级并列时按 `plugin_order` 在级内轮播（见《组件契约规范》§2.5）。**托盘是单点聚合** |

> **「要不要提醒」必须由取值显式声明**（`StateOption.alerts`），不允许靠 `key == "muted"` 之类的字符串判断——那正是要消灭的魔法值。托盘露出规则见《组件契约规范》§2.5。

### 4.4 与身份契约的对齐

- `StateSpec.key` 走 `Contribution.key`：`identity() = f"{plugin_id}.{key}"`。
- 渲染层按 key **就地更新、禁清空重建**；回调必须 `disconnect → connect` 或 `UniqueConnection`（否则一次 toggle 跑 N 次）。
- 框架是状态总线的**唯一发言人与周期兜底**：`tick()` 返回非 None 后，框架自动 publish `plugin.<id>.status.<key>`。
- 插件可经 `self.publish_snapshot()` **即时广播自身**的报告到**自身** status topic（手动操作后不等下一拍）；但不得直发他人 topic、不得广播裸 dict——边界由门禁 `test_plugin_publishes_only_own_status_snapshot` 守。

## 5. 组件规格

> **画法的目标形态见《组件契约规范》§1.4 / §2.4 与其附录 A**：标题栏改为「取值图标 + 级别色（无角标）」、列表行角标改为「取值图标染级别色」、托盘改为「单槽角标（最坏那一级）」。本节描述**现有视觉基因**，落地时以契约规范为准。
> 字段与控件个数同理：`controls` 0–2 个（契约规范 §2.6）。

### 5.1 TrayIndicator（L0）

- 形态：NSStatusItem **底图（应用标识）+ 右上角一枚角标**（最坏那一级里的组件**取值图标**，画在级别色实心圆上）。**不显示文字**（菜单栏空间稀缺）。同级并列时按 `plugin_order` 在级内轮播（见《组件契约规范》§2.5）。
- 渲染：`tray_queue()`（`shell/renderers/badge.py`）派生，无插件自绘。
- 单槽：一次只显示最坏那一级的一个组件；`ERR` 一律露出（用户阈值只能收紧到 `WARN`），见《组件契约规范》§2.5。

### 5.2 TitleBarIcon（L1，每插件一枚）

- 形态：插件的**取值图标**（当前代表态的取值图标，如网络切换（原「路由守卫」，§1.1 改名）=盾、通知守卫=铃），**级别色染在图标上，无角标**（见《组件契约规范》§1.4 / §2.4）。**准入：声明它需要状态机**（这一格画的正是代表态，没有状态机就没有代表态）——按需型组件（识别、一键输入）因此不声明标题栏，它们的入口是快捷区域按钮与热键。
- **标题栏只有图标条**：无应用名、无版本、无折叠控件、无状态文字行（仅末端溢出簇）。
- 级别色取该插件代表态（§4.3），与 L2 角标同源（同一份数据）：**`OK` 也照样染**——一切正常就是绿色。色值只认共享色表（`shell/design/levels`），面板不再另立一份「正常就中性」的口径。「ok 隐」是**列表行角标**的规则（健康不抢眼），不适用于标题栏：标题栏的位置本来就要一眼看出「这个组件现在好不好」。
- 交互：
  - **hover** → tooltip = **组件名：副标题**（与 L2 那一行**逐字相同**，决议 D18「文案只有一份」；副标题还没算出来时只报组件名）
  - **click** → 折叠态展开组件列表、展开态收起（再次点击收起）；**展开那一半附带「下探到该组件行」**（滚到该组件**首行**，仅当它看不全时才滚；见下 ◷）
- **排列顺序**：按 `registry.plugin_order()`，与 L2 条目、L3 设置分页一致。

> **◷ 2026-09-17（本节两次修订）**：① **文案**原为「组件名 + 状态列表（每行 `title` + `summary`）」，即**逐台状态机枚举** —— 第二条文案路径（面板行写「iPad 已连接 · 通知正常」、悬停却在列「第二屏：…」）；现改为与列表行**同一句**（用户裁定）。② **click** 原文写「面板下探到该组件行并锚定/滚动」，实现里只剩一个**没有任何接收方**的信号（从未生效）；查实现条件后判定**做不到** —— 面板状态区**没有滚动容器**（随内容长高、所有行一直可见），该信号连同参数一并删除。**连带真问题**：面板无滚动容器 ⇒ 内容超过屏幕时底部那些行没有可达路径（另案）。**◷ 2026-09-18 补**：那件「另案」已落地 —— 状态行外包了一层 `QScrollArea`（屏幕够高时逐像素等于改前），落点见；于是上面②删掉的那条承诺**具备了重启条件**（当时删它的唯一理由已不存在），但**重启与否是产品决定、本批未重启**；同时「随内容长高、所有行一直可见」这句自本批起不再成立 —— 内容超屏时状态区**可滚**。**◷ 2026-09-18 同日重启**：容器既已有了，②删掉的那条承诺当场重启（用户裁定）—— 点图标在**展开**那一半附带「下探到该组件行」（滚到该组件**首行**，且**只在该行看不全时**才滚，免得为一次折叠顺手把列表挪一下）；**展开态那一半不滚、仍只收起**（同一控件只做一件事，不按上下文分裂成两种行为 —— §2.6 否掉 S3 用的就是这条判据）；信号 `componentClicked` **依旧不恢复**，它的接收方就是面板自己，给自己发信号等于绕一圈为空。落点见。

### 5.4 DetailForm（L3 模态 · 详情页）

- **语义**：用户**常规要去用的操作面（高频）**——路由规则编辑、隧道诊断、配置文件编辑、安装向导等任务流。
- 形态：popover / 模态卡（圆角 10），标题 15/700，内容由插件 `build()` 提供。
- **入口**：点击 L2 整行（`DetailEntrySpec.trigger = "row"`，默认），或底部栏快捷唤起（`trigger = "action"`）。
- **弹出时显示 Dock 图标**：模态任务流需要能从 Dock 找回/切换。框架在弹出时 `NSApp.setActivationPolicy(.regular)` + `activate(ignoringOtherApps:)`；关闭时若本为 accessory 模式则恢复 `.accessory`。

> **迁移注意**：这套逻辑现状已有一份私有实现（`app.py:55` `_set_accessory_policy()` + `plugins/recognize/window_view.py:60` 的 `setActivationPolicy_(policy)`）。本轮是**收归**它，不是新造——迁移时要把 recognize 的实现删掉，避免两套并存。

- 托管：框架负责显示/置顶/点击外关闭（复用 `PanelDismissController` 的 200ms 竞态处理）+ Dock 图标显隐 + **窗比内容矮时给滚动区**（插件内容多高由插件定、窗多矮由框架定，两边下限对不上时 Qt 会把内容压变形且不报错 ⇒ `window` 形态的内容统一外包滚动区、开窗高度按内容自然高度算、页脚不进滚动区；`popover` 随内容长高故不包），插件只 `build()` 返回内容。

### 5.5 SettingsPage（L3 常驻分页）

- **语义**：**第一次设置后基本不再动的低频一次性配置**——全局、跨插件、纯偏好。
- **内联在框架设置面板中**：插件只声明 `SettingsPageSpec` 内容，**不自建独立窗口**；框架负责分页导航、搜索、双主题换肤。
- **排序编辑器 `PluginOrderEditor`** 由框架提供（非插件职责），支持拖拽调整顺序，保存为 `plugin_order`。
- **「插件」页每行的显示位芯片**（框架渲染，决议 D4）：最多四枚一组（标题栏 / 列表行 / 快捷区域 / 托盘角标），亮 = 显示中、点一下关；**只列该组件真有的显示位**；**「快捷区域」出厂是暗的**（该位默认关，◷ 2026-09-22 D37）。
  视觉 `pill-chip` / `pill-chip-on`（后者 = `accent_soft` 底 ＋ `accent` 字，与侧栏选中项同门语言），比 `pill-ghost` 更小更轻。

### 5.6 底部工具栏

- 一条 hairline 与插件区分隔；**三段式**：A 区（左，弹性）= 快捷按钮集群（app 级 + 插件 `ActionSpec` 贡献）；B 区 = `addStretch(1)`；**C 区（右，固定）= 设置 + 退出两个图标按钮，永久可见、永不进溢出**。
- **宽度是裁决者，枚数是派生量**：先按「图标 + 短标签药丸」（pill-ghost：透明 + 1px 描边 + 圆角 8，hover 转 `surface2` + accent 边）试摆，**枚数上界（`N_QA_VIS = 5`）与实测总宽两条都过**才用它；任一不过就**整区**转纯图标 ghost 方块（边长读 `metrics.BTN_ACTION`，不写 30）—— 「有的图标、有的文字」混在一行是最难认的一种，故不分区混排。A 区实得 224px（面板 320 − 底部栏边距 − C 区 − 区间距），装不下的折成末端「⋯」，**「⋯」自己的宽度要先留出来**。
- **纯图标态的字形回落链**：动作自带 → 组件身份图标（`ComponentSpec.icon`）→ 通用齿轮 —— 与状态行主位同一份判据；那一格画不出图形就是一个看不见的按钮。
- **溢出**：折起来的收进末端「⋯」，点击展开浮层。**工具栏高度固定不换行**（菜单栏 popover 忌增高）。
- **tooltip 兜底**：图标 + 标签态可省略 tooltip；**纯图标态与溢出「⋯」强制 tooltip**——面板窄时 tooltip 是文字缺失的唯一回退；图标取自设计系统图标集（**禁 emoji**），hover 统一 pill-ghost。
- **出厂 A 区是空的**：快捷区域默认关，摆哪几个由用户在「插件」页自己勾（◷ 2026-09-22 D37：原口径按**枚数**分档、与真实宽度无关 —— 三枚带图标的短标签实测 249px 从来装不下，没给图标的动作又在纯图标态降级成文字按钮，出厂因此长成「2 枚图标 ＋ 3 枚被压到 48px 的文字」；现改按**实测宽度**裁决 ＋ 字形回落链，见）。

## 6. 顺序规则

排序的唯一真源在框架方案 v3.0 §6.4，本文只讲三处渲染如何用它：

| 层级 | 用什么 | 谁决定 |
|---|---|---|
| **插件间** | `plugin_order: list[plugin_id]` | **用户在设置页拖拽** |
| **插件内多贡献** | `Contribution.order` | 插件声明 |
| **新插件默认插入位** | `Plugin.order` | 插件声明（进入 `plugin_order` 后失效） |

三处渲染（标题栏图标条、L2 状态行、设置窗插件分页）**全部调用同一个 `registry.plugin_order()`**，不允许各自重排。托盘徽标是单点聚合，不受顺序影响。

新增/卸载插件时 `plugin_order` 自动追加/移除对应 id（卸载移除见框架方案 v3.0 §9.1 第 3.5 步）。

## 7. 交互决策规则：什么进详情页，什么进设置页

### 7.1 判定树

```
入口判定树：
├─ 二元/即时、无需表单？ ─────────► 行内就地（Switch / ModeBadge），不弹窗
│     · 启用/禁用、允许/静音、隧道开/关 → Switch
│     · 自动 ↔ 手动 等模式切换          → ModeBadge(on_click)
├─ 多字段编辑 / 任务流 / 经常要用？ ─► DetailForm（详情页）
│     · route_guard：路由规则编辑
│     · ipad_tunnel：守护安装、隧道诊断、详细配置
│     · autotype：配置文件编辑
└─ 全局 / 跨插件 / 纯偏好 / 一次性？ ─► SettingsPage（内联框架设置面板）
  · 通用、插件管理、开机自启、权限、关于
```

### 7.2 互斥规则（v2.0 改判）

v1.8 的「一个插件只拥有一种主要深度入口（详情页**或**设置页）」**与框架方案冲突**：框架方案 v3.0 §8.1 规定 `config_schema()` 会自动生成设置页，而批次 3 的可度量收益正是「约 1400 行手写对话框转为 schema 声明」。若 ipad_tunnel 因为有详情页就不能有设置分页，它的 schema 化配置无处安放，**批次 3 的收益被吃掉**。

**改判**：

> **互斥的是「同一类配置只在一处可改」，不是「一个插件只能有一个深度入口」。**
>
> - **schema 生成的设置页 = 配置（低频）**，不受互斥约束，任何声明了 `config_schema()` 的插件都有。
> - **详情页 = 任务流（高频）**，**不得复制设置页里已有的字段**。
> - 判断标准：这个操作属于「改配置」还是「执行任务」？改配置 → 设置页；执行任务（编辑规则、跑诊断、走安装向导）→ 详情页。

反模式修正：`ipad_tunnel` 当前把 install / diagnostic / config **全塞设置页**，应改为 L2 行（Switch 启用 + ModeBadge 自动/手动）+ 点击行弹 DetailForm（含安装 / 规则 / 诊断），配置类字段留在设置页。
