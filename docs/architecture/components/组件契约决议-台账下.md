### D16 三处显示位的分工：图标 / 角标 / 颜色　✅ 已定稿（2026-09-12 用户裁定）

**议题**（用户提问）：「每个状态都自带图标，所以标题栏角标、列表角标、托盘角标都用状态对应的图标渲染吗？所有的角标都同源，每个状态要声明它的图标要不要显示到托盘上？」

**先答事实**：当前三处角标画的都是**颜色**，不是图标。

| 位置 | 画什么 | 出处 |
|---|---|---|
| 标题栏图标右上角 | 9px 圆点，色 = 代表态级别；`ok` **不画** | `shell/panel.py:110`（色表）、`:154-160`（绘制） |
| 列表行首 | 10px 双环圆点，同一张色表 | `shell/panel.py:163`、`:227-242` |
| 托盘 | 红底白「!」（alert）/ 灰底反色「静」（mute），**全局聚合** | `shell/status_item.py:262-272`、`:353-392` |

「同源」指的是**同一份级别**（各处都由 `_recompute_plugin` 的 `worst` 派生），**不是同一枚图标**。

**再答「状态自带图标」**：`StateSpec.icon` 今天**全仓零消费**——「图标随取值变」只有字段、没有渲染路径；
标题栏与列表行首画的其实是 `ComponentSpec.icon` / `StatusRowSpec.icon`（身份图标，固定不变）。

| | |
|---|---|
| **结论（用户裁定）** | 三处显示位这样分工：<br>· **标题栏**：图标 = 取值图标，颜色 = 级别色**染在图标上**，**无角标**<br>· **列表行**：主位 = 身份图标；角标 = 取值图标，角标颜色 = 级别色<br>· **托盘**：一枚角标画取值图标（初稿写的「每组件一枚并排」已在 D17 二次修订中否掉，以 D17 为准） |
| **对上一轮提案的修订** | 我上一轮提的「角标只画颜色、图标只进主图标位」被**否定**——角标改为画取值图标。理由是信息量：主位说「是谁」、角标说「什么状态」、颜色说「多坏」，三件事一次说完 |
| **随之删除** | `StateSpec.show_in`（状态机级开关在机制上不可能生效：角标与托盘都取代表态，按组件聚合，与「有几台状态机」无关）；`StatusRowSpec.icon`（身份图标只有一个来源 `ComponentSpec.icon`） |
| **随之新增** | `StateOption.icon` 成为真正的渲染数据源（取值图标）；省略时取 `ComponentSpec.icon` |
| **已确认的硬要求** | ① 颜色只有一个来源 = 代表态级别；② 图标有两个来源（身份图标 / 取值图标）各司其职、不互换；③ 行声明里不写 `icon` / `title` |
| **附带工作项** | **图标库要扩充**：现 8 枚全是领域语义（`ROUTE` / `SHIELD` / `BELL` / …），没有「状态变体」。不扩充则「图标随取值变」无从表达 |
| **影响面** | `specs.py`（删 `show_in`、`StatusRowSpec.icon`）/ `shell/panel.py:110,151,154-160,163,227-242,280`（角标改画图标 + **两张色表合一**）/ 6 个组件 / 测试 / UI 规范 §5.2·§5.3 |
| **状态** | **✅ 已落地（2026-09-15，与 D14 同批）** —— 标题栏＝取值图标 ＋ 级别色染在图标上（圆点角标已删）、列表行＝主位身份图标 ＋ 角标取值图标（圆点改 `_ValueBadge`）、两张色表合一（面板的级别→颜色映射直接取自共享 `design/levels.LEVEL_COLOR`）。托盘那半归 D17。◷ 落地口径：`OK` **也染级别色**（一切正常＝绿，按共享色表字面执行）；行内角标仍守「ok 隐」。门禁与落点表见 §A14。<br>**◷ 2026-09-17 补「准入」**（用户裁定，因 `recognize` 的实例被点名）：三处显示位里，**标题栏**与**默认渲染的列表行**两处的画材来自状态机（前者画代表态取值图标，后者取代表态级别 ＋ 那句副标题）⇒ **没有状态机的组件不声明它们**；`recognize` / `autotype` 的 `ComponentSpec` 随之删除。**自绘的行（`custom`）豁免** —— 它自己画，框架不往上叠级别与文案。同一轮里 **`StatusPanel.componentClicked` 删除**：它承诺的「下探到该插件行」前提是面板有滚动容器，而面板**没有**（状态区随内容长高、所有行一直可见），全仓也从无接收方。门禁 `test_display_slot_declarations_need_a_state_machine`；连带记下真问题「面板无滚动容器 ⇒ 内容超屏时底部行够不着」（另案）。 |

### D17 托盘 = 一枚角标，指向最该关心的那个组件　✅ 已定稿（二次修订 + 第三次澄清轮播范围，2026-09-12 用户裁定）

**用户原话（第一次）**：「托盘的角标：渲染所有组件的状态图标（不是级别），用户指定哪些组件哪些健康度的进行渲染。」
**用户原话（第二次，否掉并排）**：「？？托盘一次能显示多个图标？我的建议还是以角标的形式显示，显示已选组件的状态图标最不健康的那个，如果同级别有多个，轮流显示。」
**用户原话（第三次，澄清轮播范围）**：「其他同意，不按严重度我不同意。我说了只显示健康度最差的那一个级别的，而不是所有级别的一起轮播。」

**先答「一次能显示多个图标吗」**：技术上能（一个 App 可以建多枚 `NSStatusItem`），但**不该**——多枚状态项
用户能 ⌘ 拖走、顺序不再受控，宽度随状态变化还会推挤其它菜单栏项目。我上一轮的「并排」本意是画在
**同一张合成图**里（一条状态项内排多个图标），用户否掉「并排」后结论收敛为**单槽**，
上一版的「合成图 / 上限 + `+K` / 出场策略三选一」随之全部作废。

| | |
|---|---|
| **结论** | 托盘只有**一枚菜单栏项**，结构 = 「底图 + 右上角一枚角标」；角标内容 = **已选组件里最坏那一级里的取值图标**，画在级别色实心圆上。该级内有多个触发者 → 按 `plugin_order` 每 3 秒轮播 |
| **这正好是现有结构** | `shell/status_item.py` 今天就是「底图 + 右上角角标」：无角标走 template 图（`:330-335`），有角标手工合成（`:337-349`）。**本决议不改结构，只改角标的内容**（固定字符 → 取值图标） |
| **为什么单槽优于并排** | ① 菜单栏宽度是公共资源，抖动会推挤别人的图标；② 单枚状态项不存在被 ⌘ 拖走的顺序失控；③ 「最不健康的那一个」恰好回答最重要的问题——现在最该关心谁 |
| **角标画法** | 级别色**实心圆**（直径 14px，锚右上）+ **白描边简化字形**。与现状一脉相承：今天画的也是「红底白 `!`」「灰底反白 `静`」，只是把字符换成取值对应的字形 |
| **硬要求 1 · 画布尺寸** | 菜单栏画布 22 → **24px**。现状 22px 里角标直径仅 11px（`status_item.py:338` `size = 22`、`:378-379` `r = 5.5`），装不下「底图 + 可读角标」两件事 |
| **硬要求 2 · 角标字形与主字形分家** | 角标字形 = **12 网格、笔画 ≥1.6、≤3 段**的专用简化字形。24 网格主字形缩到 14px 后有效笔画约 0.7px，必糊。角标字形**可缺省**，缺省时回落该级别的通用标记（见 D19） |
| **硬要求 3 · 轮播不动宽度** | 所有角标字形按同一包围盒绘制；轮播**不改变菜单栏项宽度**，否则菜单栏每 3 秒抖一次 |
| **硬要求 4 · 队列只有一个级别** | 队列 = **最坏那一级的触发者**；级别先由「取胜」步定死，轮播**不跨级别**——`ERR` 与 `WARN` 永不混在同一队列里。更轻级别的触发者一律被压制，不上屏、不排队。级别变化（最坏的被处理掉）→ **整队更换**为新的最坏那一级 |
| **硬要求 5 · 轮播的启停与顺序** | 队列长度 ≥2 才启动；掉到 1 个或 0 个立即停（不留常驻计时器）；计时器归 shell 侧单一实例，不归任何组件。队列**内**顺序 = `plugin_order`，**不随机** |
| **硬要求 6 · 明暗适配** | 级别色破坏 template 图，不能再用系统单色渲染 → 底图与中性色必须按菜单栏**实际**外观取色（`status_item.py:282-309` 已有这套判定；系统外观设置不可信，全屏时菜单栏常是深色浮层） |
| **硬要求 7 · 悬停与点击** | 悬停提示跟随当前轮播项（组件名 + 该组件代表态 `summary`）；点击整枚图标 = 打开面板，不做逐图标交互 |
| **露出规则（三层）** | ① **候选** = 用户 `plugins.<id>.ui.tray.visible`（哪些组件）；② **触发** = 作者 `StateOption.alerts` + 全局 `tray.min_level`（哪些健康度）；③ **取胜** = 先取最坏的那**一级**（唯一队列），**该级内**并列才轮播 |
| **安全不变式** | **`ERR` 一律露出**，用户配置只能收紧到 `WARN`，不能屏蔽 `ERR`。守卫类工具的核心承诺是「出事一定看得见」 |
| **随之删除** | `BadgeRuleSpec`（被 `alerts` + 用户阈值取代）；`renderers/badge.py` 的 `ALERT` / `MUTE` / `NONE` 三态聚合；`_render_badge` 画字符的两段（`status_item.py:383-401` 的 `!`、`:403-410` 的 `静`） |
| **「静」的去向** | 通知静音从特殊通道降级为普通取值：`notify_guard` 声明 `StateOption(id="muted", icon=IconName.BELL_OFF, alerts=True)`。托盘不再有硬编码的「静」字 |
| **影响面** | `shell/status_item.py`（画布尺寸 + 角标改画字形 + 轮播）/ `renderers/badge.py`（改为「挑最坏那一级 + 该级内并列列表」）/ `shell/app_shell.py:371` / `specs.py`（删 `BadgeRuleSpec` 与 `show_in`，加 `StateOption.alerts`）/ `design/icons.py`（角标字形族，见 D19）/ 6 个组件 / 测试 / UI 规范 §5.6 |
| **状态** | **✅ 已落地（2026-09-16）** —— 角标 = 级别色圆盘 ＋ 取值字形；画布对齐 24px / 角标 14px；熔断保留**即时上屏**通道（用户裁定，不等失联超时）；全局 `tray.min_level` 只落读侧（默认 `warn`），每组件用户开关随 D4。两处现场裁定与决议文本的偏差：① 静音图标今天回落该机主图标（决议写的 `BELL_OFF` 字形随 D19 按需补）；② 「静音是否提醒」由级别默认（WARN 即提醒）＋显式 `alerts=True` 双保险。落点表见 §A15 |

> 上一版的两个「待拍板」已就地消解：**出场策略**退化为「没有触发者就不画角标」（即现状 `set_badge(None)` 路径），
> 单槽不存在宽度抖动问题；**点击语义**沿用「整枚点击打开面板」。

### D19 图标库：两族资源 + 五枚通用级别标记　✅ 已定稿（结构，2026-09-12 用户要求）

**用户原话**：「图标库要扩充」。

**问题**：`IconName` 在 D19 定稿时只有 8 枚（`contribution/specs.py:64-74`：`ROUTE` / `SHIELD` / `BELL` /
`KEYBOARD` / `SCAN` / `TABLET` / `DNS` / `GEAR`），**全是领域语义、零状态变体**。
而 D13 要求「图标随取值变」、D16 要求列表行角标画取值图标、D17 要求托盘角标画取值图标——
三处都建立在「同一个组件能拿出几枚可区分的图标」之上，而这批资源今天不存在。

> **◷ 2026-09-14 现状（批次 12 · P0① 落地后）**：**结构已全部落地**——主字形（24 网格）**13 枚**（8 枚领域语义 ＋ 批次 13 P0 的 `DISPLAY_ON`/`DISPLAY_OFF` ＋ 本批 5 枚 `MARK_*`）在 `shell/design/icons.py` 的 `_GLYPHS`；**角标字形族**（12 网格简化版）在 `_BADGE_GLYPHS`；级别 → 标记映射在 `_LEVEL_MARK`；解析入口 `badge_name()`（专用角标字形 → 该级别标记 → `MARK_IDLE`）与 `badge_pixmap()`；`IconName` 在 `contribution/specs.py`。
> **◷ 2026-09-19 增量**：**领域变体开张**——主字形「13 枚」这个数一直是错的（漏了 2026-09-17 加的 `POWER`），今天实测 **20 枚**：8 枚领域语义 ＋ `POWER` ＋ `DISPLAY_ON`/`DISPLAY_OFF` ＋ **`BATTERY` / `BATTERY_LOW` / `BATTERY_CHARGING` / `TABLET_WARN`** ＋ 5 枚 `MARK_*`。「不预先堆砌」不变，四枚各有出处：`TABLET_WARN` 的消费方是 `ipad_tunnel` 的 `error` 取值（那台机九个取值此前一个取值图标都没有、全回落主图标 ⇒ D13 在它身上等于没生效）；电池三枚的消费方是《组件契约规范-完整例子》那份「可以直接抄」的范例，由门禁 `test_doc_examples_reference_real_icons` 钉住（示例里原先写的 `BOLT` 在枚举里不存在 —— 这就是台账记的「跑不通」）。
> **仍待做**：① ~~**领域状态变体**~~ **已开张 2026-09-19**（口径不变：仍按需增量，不预先堆砌）；② **角标字形的消费方**——列表行角标与托盘角标今天仍画纯色圆点 / 字符，属 D16 / D17，不是 D19 的资源缺口。

| | |
|---|---|
| **结论（结构）** | 图标库分两族 + 一组兜底：<br>① **主字形**（24 网格线性，供标题栏 / 列表行 / 面板）<br>② **角标字形**（12 网格简化，供托盘角标，**可缺省**）<br>③ **通用级别标记 5 枚**：`MARK_OK` / `MARK_IDLE` / `MARK_OFF` / `MARK_WARN` / `MARK_ERR` |
| **命名规范** | 领域变体统一 `{DOMAIN}_{VARIANT}`，如 `BATTERY` / `BATTERY_LOW` / `BATTERY_CHARGING`。**组件名不进入图标名**（图标是语义资源，不是组件私产） |

### D20 声明入口：一个声明点一个方法　✅ 已定稿（2026-09-12 用户裁定）

**用户原话**：「组件的声明采用函数 `contributions` 是不是不太符合一般性规范？至少得是计算属性，有一定的结构约束，或者是类继承来约束？」

先摆两个前提事实（读了代码才知道，不是推测）：

- **类继承早就在用**：`Registry.discover` 取 `barkit.plugins.<pkg>.plugin.Plugin` 后做 `issubclass(cls, Plugin)`
  门禁（`core/registry.py`）；外部插件 manifest 要求 `entry: plugin:Plugin`，loader 里再做一次 `issubclass`
 （`core/loader.py`）。身份与模式是**类属性**，声明的平台是**实例方法**——这一层不用改。
- **声明入口必须是实例方法**：Spec 内嵌回调（`SwitchSpec(on_toggle=)` / `SettingsPageSpec(build=)` /
  `ActionSpec(on_click=)`）必须晚绑定到实例，类级纯数据声明表达不了 `self`。所以「类继承 + 实例方法」
  不是一种选择，而是唯一可行组合——`@property` 与类级常量都可排除。

**问题不在「是不是函数」，在 `contributions() -> list` 没有结构约束。** 今天的收集路径是
`_collect()` 调一次 `list(plugin.contributions())` → 缓存进 `_by_plugin`，之后 8 个门面
（`status_rows` / `states` / `components` / `hotkeys` / `actions` / `settings_pages` / `detail_entries` / `badges`）
