## 2.7 报告：文案只有一份

运行期组件回报一份 `StateReport`：

```python
StateReport(
  state="low", # 我现在处于哪个取值（必须在 StateSpec.states 里）
  summary="剩余 15%", # 可选。给了就覆盖 StateOption.text，成为副标题
  icon=None, # 可选。本轮的取值图标；None = 用 StateOption.icon
  updated_at=time.monotonic(), # 框架填写，供失联判定
)
```

**图标可以在报告里覆盖一次**（`StateReport.icon`）：取值集合是**声明期**定的，但有些图标只有**运行期**才知道该用哪一枚——同一格在不同轮次可能换图标。给了 `icon` 就以它为准，`None` 回落到 `StateOption.icon`。

> 它是**纯增补**（`None` 是默认值），存量组件零影响。同一字段同时供**面板行的取值图标**与**托盘底图**（见 2.5）——一处补、两处用。
>
> 与「静态归声明、动态归报告」一致：图标**随取值**变是静态的（归 `StateOption.icon`）；**同一个取值**在不同轮次用不同图标才是动态的（归报告）。多数组件用不到它。

**只有一份文案**：`summary`（不填则用该取值的 `text`）。它在三处出现，内容完全一致：

| 展示位 | 取数 |
|---|---|
| 列表行 · 副标题 | **该行的 `subtitle` 计算**（见下）；未声明时回退代表态的 `summary` |
| 列表行 · 副标题的悬停提示 | 同上，逐字相同 |
| 标题栏图标 · 悬停提示 | 组件名 ＋ **同一句**（取首个行的副标题；该行没声明 `subtitle` → 回退代表态 `summary`） |

> **◷ 2026-09-17（用户裁定）**：本表第三行原为「组件名 + 每台状态机的 `summary`，一行一台」。
> 逐台枚举是**第二条文案路径**——组件把几台机合成一句时，悬停还在逐台报，两处必然对不上
>（实测：面板行「iPad 已连接 · 通知正常」，悬停却是「· 第二屏：… / · 通知：… / · 自动化：…」）。
> 改为一句话：标题栏那一枚是**组件级**的（每组件一枚），取它的**第一个列表行**的副标题；
> 该行没有副标题（行级 `subtitle` 未声明、也无可回退的代表态 `summary`）时才空。算法只此一份，落点
> `shell/panel.py` 的 `row_subtitle_text` ＋ `_recompute_plugin`（行与悬停取同一份字符串）。

**一台组件可以一次报多台状态机**：`tick()` 返回 `dict[key, StateReport]`，框架逐 `key` 发布到
`plugin.<id>.status.<key>`。返回单份 `StateReport` 时按该组件的默认 `key` 发布——两种写法等价，
多台状态机时用 `dict` 能少写一轮循环。

**颜色与图标由框架从级别和取值派生**，你在声明里已经给过了：

| 展示位 | 取数 |
|---|---|
| 标题栏图标色 / 列表行角标色 / 托盘图标色 | 代表态的 `level` |
| 标题栏图标 / 列表行角标 / 托盘图标 | 代表态取值的 `icon`（报告给了 `StateReport.icon` 时以报告为准） |
| 列表行主位图标 | `ComponentSpec.icon` |

**需要更长的说明或操作引导**（「守护过期 · 点此重装」这类）时，写进**详情页**
（`DetailEntrySpec`）或**行内按钮**（`controls` 里的 `ButtonSpec`），不要塞进副标题——
副标题是「一眼扫过」的位置，塞进操作指令会让每一行都变长。

### 副标题：默认取代表态，需要时行自己算

单台状态机的组件**什么都不用写**：副标题自动 = 代表态的 `summary`。

多台状态机时，一行要同时说清"谁挑的 + 结果"，而代表态只是**最坏的那一台**——
它的文案未必是最该看的那句。这时声明行级回调：

```python
StatusRowSpec(
  key="main",
  subtitle=self._row_subtitle, # 每次刷新调用，返回整行文案
)

def _row_subtitle(self) -> str:
  """一行说完四台状态机的信息。次序由组件的判断决定。"""
  return f"{self._match_source()} · {self._profile_name()} · {self._routes_text()}"
```

| | 取数 | 什么时候用 |
|---|---|---|
| 不声明 `subtitle` | 代表态的 `summary` | 单台状态机；或多台但"最坏那台"恰好就是要看的那句 |
| 声明 `subtitle` | 回调返回值 | 多台状态机，需要一句话合并 |

三条约束：

| 约束 | 说明 |
|---|---|
| **纯读取** | 不得有副作用（见 3.1） |
| **同一份字符串** | 副标题与其悬停提示仍是同一份，不要两处各写一遍 |
| **与颜色无关** | 颜色**一律**取代表态级别——颜色聚合，文案不聚合（见 1.4） |

**拼装权在组件，框架只给位置。** 该显示几段、按什么次序取舍，是组件的判断
（例如面板 320px 放不下四段时先舍谁），契约不规定内容。

所以「根据当前状态算出副标题」有两种写法，按需选：

```python
# 写法 1：单台状态机——在 tick() 里算好放进 summary
def tick(self) -> StateReport:
  """采集规则数并上报，副标题就是这一句。"""
  n = len(self._active_rules())
  return StateReport(state="ok", summary=f"{n} 条生效")

# 写法 2：多台状态机——行级回调，把几台机合成一句
def _row_subtitle(self) -> str:
  return f"自动命中 · {self._profile} · 已叠加 {self._active_count} 条"
```

## 2.8 详情页与设置页

两个"打开一个界面"的声明点。区别只在**用户从哪里进来**：

| | `detail_entry()` → `DetailEntrySpec` | `settings_page()` → `SettingsPageSpec` |
|---|---|---|
| 用户从哪进 | **点组件列表的整行**，或**底部快捷按钮**（两处同源，见 2.4） | **设置窗左侧的组件页** |
| 打开时机 | 用户想看"现在怎么样、我要做点什么" | 用户想改配置 |
| 出场频次 | 随时 | 配一次就不再动 |
| 基数 | 0/1 | 0/1 |

```python
DetailEntrySpec(
  key="main",
  label="网络切换", # 入口名（工具提示 / 无障碍标签）
  build=self._build_detail, # 打开时构造界面
  reason="场景列表是集合型配置，声明式表单表达不了", # 用 build 必须说明原因
  presentation="window", # "popover"（面板内嵌）| "window"（原生独立窗）
  save=FormSaveSpec(commit=self._commit, dirty=self._dirty), # 可选：见下
  width=780, # 可选：window 形态的初宽（默认 620）
)
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `label` | 是 | 入口名，用户可见 |
| `build` | 是 | 构造界面的工厂。**详情页只有这一条路**——没有声明式形态 |
| `reason` | 是 | 为什么必须自绘。**`build` 是逃生舱，逃生舱要交代原因** |
| `presentation` | 否 | `"popover"` = 面板内嵌（默认，≤320px）；`"window"` = 框架托管的原生独立窗（居中、可 resize） |
| `save` | 否 | 这个窗体**怎么保存**（`FormSaveSpec`：`commit` ＋ `dirty`）。声明它就等于说「本窗体是改完攒着、点保存才写的」，框架据此多画一颗「保存」键并在关窗时拦一下。**只对 `window` 有意义**，配 popover 在声明期报错（决议 D35） |
| `width` | 否 | `window` 形态的**初宽**（px，正整数）。内容宽的页面（多列表格、工具条挤不下）声明一个更宽的初宽 —— 窗体多大本是框架的事，但**只有内容自己知道要多宽**。**只对 `window` 有意义**（浮层卡是固定宽的），配 popover 或给非正值在声明期报错（2026-09-22） |

`SettingsPageSpec` 的字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `label` | 是 | 设置窗左侧的页名 |
| `build` | 二选一 | 构造设置页的工厂。**今天唯一可用的路径** |
| `schema` | 二选一 | `FormSchema`：平坦表单的声明式写法。**字段保留、渲染器未接线**——只填它会在打开设置窗时崩（见附录 A） |
| `reason` | `build` 非空时必填 | 同上 |

`build` 与 `schema` **至少要有一个**；两个都不填 = 这个组件不出现设置页。

### 配置放哪：两个独立的问题，别压成一条

**问题一 · 要不要自绘？** —— 由**配置的形状**决定。

| 配置长什么样 | 写法 | 判据 |
|---|---|---|
| **平坦**：字段数固定、无嵌套集合 | `config_schema()` → `FormSchema`（声明式），或写进 `build` | 一屏能平铺完 |
| **集合型**：可增删的列表，每项自己是一组多字段 | **自绘 `build`** | 出现"第 N 项的第 M 个字段"这种两层索引就够格 |

自绘是**正规出口，不是例外**——但仍须在 `reason` 里自述，因为自绘意味着放弃框架的一致性（样式、校验、无障碍都要你自己保证）。

> **`FieldType.LIST` 今天没有渲染器**（`core/schema.py:28-39` 只定义了类型，无 UI 消费者）——
> 集合型字段填进 `FormSchema` 等于没有编辑器，自绘是唯一出路。

**问题二 · 放在哪？** —— 由**用户什么时候用它**决定，**与"是不是集合型"无关**。

| 用户什么时候用 | 落哪 | 机制 |
|---|---|---|
| **每天都用**：常规操作面 | `detail_entry()`（点整行 / 底部按钮） | 面板内嵌或独立模态窗（`presentation`，见下） |
| **配一次就不再动**：低频一次性配置 | `settings_page()` | 设置窗左侧一页 |

**两者都可以是自绘 `build`**——"集合型"只说明**要不要自绘**，不说明**该进哪个入口**。

- 一个"可增删的规则列表"，用户配完就走 → **设置页**；
- 一个"现在要处理的队列"，用户随时要看 → **详情页**。

**判据**：先按形状选写法，再按使用频次选入口。把两件事压成一条判据（"集合型 → 详情页"）
会让**低频配置占住高频入口**。

**`presentation` 怎么选**：只在 `detail_entry()` 这条路上有意义（设置页没有这个字段）。
先看宽度——面板 `popover` 的可用宽度约 320px；"左列表 + 右表单"这类编辑器实测要 560–640px，
**必须用 `window`**。先按 `popover` 设计、放不下再改 `window`，代价是表单要重排——**一开始就按内容宽度选**。

两种形态的实际长相（◷ 2026-09-18 订正）：`popover` 是**贴着菜单栏图标弹的浮层卡**（自绘圆角、
置顶、点外部即关）；`window` 是**原生标题栏的独立窗**（居中在触发它的那块屏上、关闭键归系统、
**不做点外部关闭**——一个居中的独立窗被点一下就没了比不给关更危险）。此前 `window` 也走自绘浮层卡，
于是它既没有关闭键、又带着浮层的关闭语义，两头不像用户见过的编辑器窗口。

**`save` 解决什么**：不声明它时，框架对「你什么时候把改动写进配置」一无所知——界面改了半天、
盘上没动，这件事在界面上看不出来。声明之后，组件把「什么算填完、怎么写」攥在自己手里，
框架只做三件机械的事：画键、拦关窗、转达结果（细节与理由见决议 D35）。

## 2.9 按钮与热键

两个"触发一个动作"的声明点——**用户主动发起，不是状态**。

```python
def actions(self) -> tuple[ActionSpec, ...]:
  """面板底部的快捷按钮。"""
  return (
  ActionSpec(key="cancel", label="取消识别", icon=IconName.SCAN,
  on_click=self.cancel_recognize),
  )

def hotkeys(self) -> tuple[HotkeySpec, ...]:
  """全局热键：你只给默认键位，用户在设置页里改。"""
  return (
  HotkeySpec(key="recognize", name="recognize", label="识别屏幕文字",
  default_combo="cmd+shift+2", callback=self.start_recognize),
  )
```

| `ActionSpec` 字段 | 必填 | 说明 |
|---|---|---|
| `key` | 同一点多条时必填 | 按钮名，本声明点内唯一 |
| `label` | 是 | 按钮文案 |
| `on_click` | 是 | **动作回调**，可以改变状态（与取值回调相反，见 3.1） |
| `icon` | 否 | 按钮图标 |

| `HotkeySpec` 字段 | 必填 | 说明 |
|---|---|---|
| `key` | 是 | 本声明点内的唯一名 |
| `name` | 是 | 配置键名 `hotkeys.<name>`。**发布后冻结**（同 2.1 的 `id`） |
| `label` | 是 | 设置页里显示的名字 |
| `default_combo` | 是 | 默认键位，用户可改 |
| `callback` | 是 | 动作回调 |

**按钮：只在用户会反复按、且此刻就有意义时才放。** 放多了会把面板底部变成工具栏。
一次性引导、需要解释的操作，写进详情页（见 2.8）。

**热键：`name` 是配置键，不是显示名。** 改 `name` 等于换一个热键——用户的键位丢失、重复注册。要改显示用 `label`。**`name` 与 `default_combo` 都必须与其他组件不撞**：键位被别的热键占了、或 `name` 被另一个组件的回调占了，框架一律**拒绝登记**（不静默顶掉），表现是两条里有一条「有时不灵」或干脆不触发。门禁 `test_no_two_shipped_plugins_share_a_default_combo` 守出厂默认键位；口径见。

**动作回调是同步的**（`Callable[[], None]`），装不下"需要授权、有延迟、可能只成功一半"的动作。
今天这类动作只能由组件自己弹窗反馈，与「组件不碰界面」相悖——已登记（见附录 A）。

# 三、必须做到的三件事

## 3.1 声明只放静态，动态走报告

| | 声明（静态） | 报告（动态） |
|---|---|---|
| 载体 | 声明方法返回的 Spec（`state_specs()` / `row_specs()` / `component()` …） | `tick()` 返回的 `StateReport` |
| 重建时机 | 加载 / 改配置 / 启停 | 每一轮 tick |
| 放什么 | 有哪些状态、取值枚举、图标、显示位、控件 | 当前取值、summary |

这条线保证同一个组件只有**一条**状态流。门禁 `test_statespec_is_static_only` 守着边界。

### 唯一的例外：纯读取回调

「声明只放静态」的准确含义是 **声明里不放静态数据之外的运行期数值**——**不是"不许有函数"**。
声明点可以携带**取值回调**，框架在每次刷新时求值：

| 声明点 | 取值回调 |
|---|---|
| `SwitchSpec` | `get_checked` / `get_enabled` |
| `MenuSpec` | `get_items` / `get_current` |
| `ModeBadgeSpec` | `get_state` / `get_items` |
| `StatusRowSpec` | `subtitle` |

| 允许 | 禁止 |
|---|---|
| **纯读取**：读自身内存状态、算一句文案、返回框架要画的东西 | **有副作用**：写文件、改配置、发请求、切模式、弹窗 |
| 返回值只取决于当前状态 | 依赖调用次数或时机（框架一帧内可能调多次） |
| 幂等 | 返回值逃逸（返回 widget、缓存引用） |

判据一句话：**回调只回答"现在是什么"，不改变"现在是什么"。**

要改变状态，走**动作回调**（`on_toggle` / `on_click` / `MenuSpec` 项的 `on_click`），或走 `tick()`。
三类回调的边界：

| | 谁调 | 能否改状态 | 例子 |
|---|---|---|---|
| 取值回调 | 框架，每次刷新 | **不能** | `get_checked` / `get_state` / `subtitle` |
| 动作回调 | 框架，用户触发时 | **能** | `on_toggle` / `on_click` / `callback` |
| `tick()` | 框架调度器 | **能** | 采集、上报 |

**为什么允许回调**：它不引入第二条状态流——回调**不产生**取值，只是把组件已有的状态翻译成框架能画的形状。
而 `tick()` 负责的是**产生**取值。两者分工不同，所以可以并存。

## 3.2 颜色由级别派生

颜色 = `f(level)`，框架统一取色。你挑级别，框架负责配色与双主题换肤——这样标题栏、
列表行、托盘三处永远同色。

同源的是**级别**，不是**图标**：三处显示位各画各的形状，颜色一律由同一份级别派生。

## 3.3 名字只有一个来源

组件的显示名只有一个来源：`Plugin.name`。标题栏提示、列表行名、设置页行名、溢出列表全部取它。
Spec 上的 `title` / `name` 只在**同一个组件的多个状态机需要各自命名**时才填。

组件的**图标**同理，也只有一个来源：身份图标是 `ComponentSpec.icon`。
`StateOption.icon` 是**取值图标**（随状态变），省略时取身份图标；`StatusRowSpec` 不单独声明图标。

# 四、落地检查
