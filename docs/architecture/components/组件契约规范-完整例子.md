## 1.5 一个完整例子

下面这个组件覆盖了绝大多数声明项。**每个方法都写了用途注释**，可以直接抄：

```python
# src/barkit/plugins/battery/plugin.py
from __future__ import annotations

from barkit.contribution.specs import (
    ComponentSpec,
    IconName,
    StateLevel,
    StateOption,
    StateReport,
    StateSpec,
    StatusRowSpec,
    SwitchSpec,
)
from barkit.core.plugin import FAIL_BREAK, RUN_PERIODIC, Plugin


def _read_percent() -> int:
    """读取当前电量百分比（0–100）。真实实现调 ioreg 或 PyObjC。"""
    return 15


class Plugin(Plugin):
    # ---------- 身份：类属性，加载时读一次，运行期不变 ----------
    id = "battery"              # 唯一标识；与目录名、配置段 plugins.battery 一致
    name = "电池守卫"            # 组件名。标题栏提示、列表行名、设置页行名都用它
    version = "1.0.0"           # 组件自身版本；安装 / 升级时用于版本比较与覆盖提示
    run_mode = RUN_PERIODIC     # 常驻轮询：框架按 poll 间隔调用 tick()
    suggested_poll = 30         # 建议周期（秒）：框架据此写配置默认值，用户可改
    failure_policy = FAIL_BREAK # 失败策略：tick 连续失败 5 次即熔断
    api_version = 3             # 契约版本，必须为 3

    def __init__(self, ctx):
        super().__init__(ctx)
        self._percent = 100     # 最近一次读到的电量，由 tick() 更新

    # ---------- 报告：tick() 是「采集 + 上报」的唯一入口 ----------

    def _report(self) -> StateReport:
        """把内部状态整理成一份报告。

        单独抽成一个方法，是因为它有**两个调用方**：tick() 的周期上报，
        以及用户手动操作后（如点了开关）需要立刻反映到界面时的手动上报。
        两条路径必须用同一份计算，否则手动路径与轮询路径会各说各话。
        """
        state = "low" if self._percent < 20 else "ok"   # 取值名，必须在声明表里
        return StateReport(state=state, summary=f"剩余 {self._percent}%")

    def tick(self) -> StateReport:
        """框架每隔 poll 秒在独立线程调用一次：采集状态并上报。

        返回非 None 时框架自动把它广播到 `plugin.battery.status.main`，
        界面据此刷新角标颜色与副标题；组件不需要自己广播。
        """
        self._percent = _read_percent()
        return self._report()

    # ---------- 声明：一个声明点一个方法，框架纯消费，组件不碰界面 ----------

    def component(self) -> ComponentSpec:
        """身份图标：进列表行主位；取值不填 icon 时也用它兜底。

        加载、改配置、启停时框架会重新收集；只放静态内容，运行期数值走 tick()。
        """
        return ComponentSpec(icon=IconName.BATTERY)

    def state_specs(self) -> tuple[StateSpec, ...]:
        """这台组件有哪些状态机：枚举全部取值，一个不少。"""
        return (
            StateSpec(
                key="main",                                 # 状态机名，本声明点内唯一
                initial="ok",                               # 首屏取值，避免第一帧空白
                stale_after=120.0,                          # 秒；超时未上报 → 框架判 ERR
                states=(                                    # 全部可能取值
                    StateOption(id="ok", level=StateLevel.OK,
                                text="电量正常"),            # 不填 icon → 用身份图标
                    StateOption(id="low", level=StateLevel.WARN,
                                icon=IconName.BATTERY_LOW,  # 取值图标：随状态变
                                text="电量低", alerts=True),  # 值得提醒到托盘
                    StateOption(id="charging", level=StateLevel.OK,
                                icon=IconName.BATTERY_CHARGING,  # 同一只电池，框内换成闪电
                                text="充电中"),
                ),
            ),
        )

    def row_specs(self) -> tuple[StatusRowSpec, ...]:
        """组件列表里出现一行，右侧挂一个开关。"""
        return (
            StatusRowSpec(
                key="main",                      # 行名；与上面状态机的 "main" 同名只是巧合
                controls=(SwitchSpec(checked=True, on_toggle=self.toggle_low_mode),),
            ),
        )

    def toggle_low_mode(self) -> None:
        """切换低电量模式（业务逻辑示意）。"""
        ...
```

这几条声明分别意味着：

| 声明方法 | 返回 | 效果 |
|---|---|---|
| `component()` | `ComponentSpec` | 身份图标（进列表行主位） |
| `state_specs()` | `StateSpec` | 声明「我有台状态机叫 `main`」，它的取值、级别、图标、文案见 `states` |
| `row_specs()` | `StatusRowSpec` | 组件列表里出现一行，右边挂一个开关 |
| 取值上的 `alerts=True` | — | 这一格值得提醒到托盘（见 2.5） |
| `tick()` 的报告 | `StateReport` | 决定当前取值、各处颜色与那一行的副标题 |

> 三个方法里都没写 `plugin_id`：**身份由框架注入**（见 1.3）。

> 例子里 `title` / `name` 一个字都没写：组件名的唯一真源是 `Plugin.name`。
> 图标也只写了两次——`ComponentSpec.icon`（身份图标）与两个 `StateOption.icon`（取值图标），
> 行不再单独声明图标。见 3.3。
>
> 例子用到的 `IconName.BATTERY` / `BATTERY_LOW` / `BATTERY_CHARGING` 三枚均已落地
> （◷ 2026-09-19，`contribution/specs.py::IconName`；有门禁
> `test_doc_examples_reference_real_icons` 钉住「文档里的图标名必须真实存在」）。

# 二、逐项声明

## 2.1 身份：我是谁

写在 `Plugin` 子类的**类属性**上：

| 声明 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | 是 | str | 唯一标识，同时是配置段键 `plugins.<id>`。**与目录名保持一致** |
| `name` | 是 | str | 组件名的唯一真源：标题栏提示、列表行名、设置页行名、溢出列表都取它 |
| `version` | 是（框架不强制） | str | 组件自身版本（如 `"1.2.0"`）。安装 / 升级时与已装版本比对，向用户提示「用 1.2.0 覆盖 1.1.0」。**外部插件以清单为准**（见下节）；两者都没写就读作「未标注」，**不拒载**——版本号不进任何门禁 |
| `run_mode` | 是 | `RUN_ON_DEMAND` / `RUN_PERIODIC` | **执行方式**：按需触发不轮询；或常驻轮询，框架按 `poll` 间隔调用 `tick()` |
| `failure_policy` | 否 | `FAIL_BREAK` / `FAIL_LOG` | **失败策略**：连续失败达阈值熔断，或只记日志继续跑。默认 `FAIL_LOG` |
| `suggested_poll` | `RUN_PERIODIC` 时必填 | int（秒） | **建议轮询周期**：组件自认的合理节拍。**用户可在设置窗覆盖**——组件给的是建议，不是命令。那个覆盖控件（组件页页尾「运行间隔」卡里的「框架检查间隔」下拉）由框架自动生成，你不声明任何字段；`config_schema()` 里写 `poll` 会被门禁拦下（D21）。`RUN_ON_DEMAND` 时填了也不生效 |
| `api_version` | 是 | `3` | 契约版本。不等于 3 会在加载期被拒载（旧插件给出拒绝原因，不标记隔离） |
| `required_permissions` | 否 | `list[str]` | 需要引导的系统权限，如 `["accessibility"]` |
| `order` | 否 | int | **默认插入位**：仅当你的 `id` 还没进过用户的 `plugin_order` 时生效。用户一旦在设置页拖过顺序，它就永远归用户 |

**`id` 一旦发布即冻结。** 它同时是四样东西的锚：

| 它是什么的锚 | 改了会怎样 |
|---|---|
| 配置段键 `plugins.<id>` | 用户已配的值全部找不到家 |
| 用户顺序表 `plugin_order` 的条目 | 用户在设置页拖过的顺序丢失 |
| helper 任务的编排键 | 只属于旧 `id` 的那些任务不再被合成 |
| `resources/` 里 A 类二进制的归属 | 部署到系统域的二进制失去主人 |

四条合起来只有一个后果：**改 `id` 不是改名，是卸载重装**——新组件从零注册，旧组件写入系统的期望态没人再维护。
所以**面向用户的改名只动 `name`**。`name` 是显示名的唯一真源（见 3.3），改它三处显示位自动跟随，零风险。

`run_mode` 与 `failure_policy` 是一对正交的开关，各答一个问题：

| | 答什么问题 | 取值 |
|---|---|---|
| `run_mode` | 框架要不要周期性叫我 | `RUN_PERIODIC` = 要（轮询型） / `RUN_ON_DEMAND` = 不要（触发型） |
| `failure_policy` | 我失败时框架怎么办 | `FAIL_BREAK` = 熔断并标红 / `FAIL_LOG` = 只记日志 |

**谁在什么时候调用 `tick()`**（`RUN_PERIODIC` 时）：

| 问题 | 答案 |
|---|---|
| 谁调用 | 框架的调度器。组件**永远不自己调 `tick()`**、不起线程、不排时钟 |
| 多久一次 | 配置 `plugins.<id>.poll`（默认由 `suggested_poll` 生成），用户在设置页可改 |
| 跑在哪 | 每个组件一个独立 worker 线程，互不阻塞，也不占界面线程 |
| 什么时候提前跑 | 注册后**立刻跑一轮**（首屏不空白）；事件到达时由框架在合并窗口后点火，走**同一个入口** |
| 上一轮还没跑完 | 跳过本拍（不排队、不并发）；超时按失败处理 |
| 失败了怎么办 | `FAIL_BREAK` 连续 5 次熔断、标红并提供「重试」；`FAIL_LOG` 只记日志 |
| 返回值给谁 | 框架接收并广播到 `plugin.<id>.status.<key>`，组件不自己广播 |

### 外部插件清单：`manifest.yaml`

外部插件（放在用户插件目录里的包）不是子包，**多一份清单**描述包的身份与入手方式。
清单是**包元数据的权威**：读到的值覆盖类属性上的同名字段。

| 字段 | 必填 | 取值 | 说明 |
|---|---|---|---|
| `id` | 是 | str | 同 `Plugin.id`，**以清单为准**（loader 强制对齐，不改就按清单走） |
| `version` | 否 | str | 组件版本，登记到 `Plugin.version`，用于「用哪个版本覆盖哪个版本」的提示。缺省 = 未标注 |
| `api_version` | 是 | int | 契约版本，须与框架支持的版本**精确相等**；不等即拒载（**读清单即可判定，不 import 插件代码**） |
| `entry` | 否 | str | `"模块:类"`，默认 `plugin:Plugin` |
| `order` | 否 | int | 默认插入位；兼容旧键名 `panel_order`（见 2.1 的 `order`） |

> 清单里的 `name` **不生效**：显示名的真源永远是 `Plugin.name`（见 3.3）。数据导出包
> 的 `manifest.yaml` 是**另一份东西**（带 `format_version`），不能当插件包装。

## 2.2 状态：我有哪些状态

一个状态（`StateSpec`）是**一台状态机**：它枚举出全部可能的取值，运行期回报当前处于哪一格。
一台状态机就是组件状态的一个单点——它的级别与文案只有一条出处，见 1.4。

```python
# 由 state_specs() 返回；plugin_id 由框架注入，组件不写
StateSpec(
    key="main",                                  # 状态机名，本声明点内唯一（只有一台时可省）
    initial="idle",                              # 首屏取值：未收到第一份报告前显示它
    stale_after=30.0,                            # 秒；超过这么久没上报 → 框架判 ERR
    icon=IconName.BATTERY,                       # 状态机**主图标**：给了它才进菜单栏来源候选（见 2.5）
    states=(                                     # 全部可能取值，一个不少
        StateOption(id="idle",  level=StateLevel.IDLE, text="空闲"),
        StateOption(id="busy",  level=StateLevel.OK,   text="工作中"),
        StateOption(id="err",   level=StateLevel.ERR,
                    icon=IconName.TABLET_WARN, text="出错", alerts=True),
    ),
)
```

**取值（`StateOption`）的四个字段**：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 取值名，状态机内唯一。报告里用它指名「我现在在这一格」 |
| `level` | 是 | 这一格的严重程度，见 2.3 |
| `icon` | 否 | **取值图标**：随状态变——「充电中」和「电量低」用不同图标。省略时取身份图标 `ComponentSpec.icon` |
| `text` | 是 | 这一格的默认文案（如「电量低」）。报告给了 `summary` 时以报告为准 |
| `alerts` | 否 | 这一格是否值得提醒到托盘，见 2.5。省略时 `WARN` / `ERR` 为真，其余为假 |

**`key` 的规则**（通用作用域见 1.3；这里只加状态机特有的）

| 规则 | 说明 |
|---|---|
| `key` 是**这台状态机的名字** | 写 `"main"`、`"tunnel"`；**不写成** `"route_guard.main"`——`plugin_id` 由框架拼装，不需要重复 |
| 组件只有一台状态机时可以省略 | 状态 topic 的保留键是 **`"main"`**，与 `Plugin.status_topic()` 同源。多数组件属于这一类 |
| 有多台状态机时必须填，且彼此不重名 | 典型场景是「隧道」「DNS」两个独立维度各自成机。撞名在收集期即报错，不静默覆盖 |
| `key` 决定事件 topic | `plugin.<id>.status.<key or 'main'>`——这是状态流的路由地址。**保留键是 `"main"`，不是 `identity()` 那个 `"default"`**：两处取不同兜底键时，手动即时广播与框架自动发布会落到两条不同 topic 上，订阅方只看到其中一条（`core/plugin.py::status_topic` 的 docstring 记了这段）。组件另一个声明点（如 `row_specs()`）用同名 `key` 不冲突 |

**报告未声明的取值**：框架记一条日志，并把该状态判为 `ERR`（不会静默忽略、也不会崩）。

**取值集合可以来自用户数据。** `states` 由 `state_specs()` 在每次收集时重建，所以它可以随配置变化——
例如「用户配的每个场景各占一个取值」。允许，但有三条硬要求：

| 要求 | 为什么 |
|---|---|
| `states` 里**必须有一个兜底取值**（无数据 / 无匹配） | 用户删掉最后一条配置时，组件不能因为"集合空了"而标红 |
| `initial` 必须指向一个**恒存在**的取值（通常就是兜底取值） | 首屏不能依赖用户数据——它可能还没被读出来 |
| 报告必须落在**最近一次收集**的集合内 | 否则按上面那条判 `ERR`；配置变更窗口是唯一的高危时段 |

**反例**：把用户数据当取值又不给兜底取值——用户删掉最后一条配置，组件立刻变红，而它其实什么都没坏。

**更稳的写法**：把取值收敛成一个固定闭集（`{ok, none, conflict}` 这类），用户数据放进 `summary`。
闭集让「有哪些取值」在声明期就确定，兜底、`initial`、校验三件事同时变得平凡。
**只有当你确实需要按取值换图标 / 上色时，才把用户数据抬成取值。**

**前提不满足必须是一个显式取值。** 组件的运行前提——依赖没装、系统能力没有、引导没走完——
**不得表现为静默空转**：必须落成一个取值，出现在面板上。

| 要求 | 为什么 |
|---|---|
| 前提不满足有**自己的取值**（如 `absent`「未安装 OpenDisplay」） | 否则用户看到的是"组件像没事一样"，而它的行为可能已经变了（例如某项策略因此恒定生效） |
| 该取值有 `text`，并且能被副标题取到 | 状态可见是唯一的出口：用户要能读出"它现在为什么不接管" |
| 级别可以是 `IDLE` / `OFF` | 前提不满足不是"出错"——组件没坏，但它必须**看得见** |

**反例**：把"依赖没装"折叠成一个内部 `False`，策略照旧生效而界面看不出来——用户既不知道策略在生效、也不知道为什么。

> 与上一条的关系：上一条管**取值集合来自用户数据**时的兜底，本条约管**前提不满足**。
> 两者是同一件事的两面——**闭集必须含一个"我现在不适用"的格子**。

## 2.3 级别：状态有多严重

级别是 5 值枚举，它是**颜色、角标、托盘、代表态**四件事的公共词汇：

| 级别 | 意思 | 严重度 | 前景色 | 背景色 |
|---|---|---|---|---|
| `OK` | 一切正常 | 0 | green | green_soft |
| `IDLE` | 开着，但没有事情发生 | 1 | text3 | surface3 |
| `OFF` | 功能是关着的 | 2 | text3 | surface3 |
| `WARN` | 需要注意 | 3 | orange | orange_soft |
| `ERR` | 出错了 | 4 | red | red_soft |

- **你只需要挑级别**：颜色由级别派生，框架统一取色，浅色 / 深色主题自动换肤。
- **`OFF` 与 `IDLE` 是两个级别**：严重度不同（2 与 1）。「隧道关着」和「隧道开着但没状态」是两种情况。
- 通用词映射：**info** 对应 `OK` / `IDLE` / `OFF`（看语义），**warn** 对应 `WARN`，**error** 对应 `ERR`。

**代表态**：框架会给每个组件挑**一个**代表态，供「标题栏图标色 = 列表行角标色 = 托盘图标色」
三处共用——取**全部状态机当前取值**里严重度最高的那个；严重度相同时取**先声明**的那台
（声明顺序 = 作者写的关注度顺序）。这一步由框架完成。
