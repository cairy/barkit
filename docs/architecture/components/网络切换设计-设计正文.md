# 一、先定三件事

## 1.1 改名只改 `name`，`id` 冻结

| 项 | 改名后 | 动？ |
|---|---|---|
| `Plugin.name` | `"网络切换"` | **改**（契约 §3.3：组件名唯一真源，三处显示位自动跟随） |
| `Plugin.id` | `"route_guard"` | **不动** |
| 目录名 `plugins/route_guard/` | 不动 | 契约 §2.1 要求「`id` 与目录名一致」，没说与 `name` 一致 |
| 配置段 `plugins.route_guard` | 不动 | 用户已改过的差异项全部在用户 YAML 里 |
| `plugin_order` 里的 id | 不动 | 用户拖过的顺序不能丢 |
| `helper_tasks` 的 `route_guard.sync` | 不动 | **最硬的理由，见下** |

**为什么 `id` 必须冻结（可验证）**：`route_guard.sync` 这个名字硬编码在 4 处生产代码 + 20 余条测试断言里：

- `src/barkit/capabilities/helper/tasks.py`　`BUILTIN_TASKS` 里的 `{"id": "route_guard.sync", "action": "route.sync", "subject": "route"}`
- `src/barkit/core/helper_tasks.py:50`　同一条声明
- `src/barkit/plugins/route_guard/plugin.py:188`　`helper_tasks=["route_guard.sync"]`（本组件声明"我拥有这条 task"）
- `tests/test_helper_tasks.py`（20+ 处）、`tests/test_helper_contract.py:172`

改 id → 框架汇总 helper_tasks 时这条 task 消失 → root helper 不再执行 `route.sync` → **下一轮就把你系统里所有 BarKit 写入的路由撤掉**。这不是"重命名"，是"卸载 + 重装"，而且副作用发生在后台、无声。

> **这条建议写进契约 §2.1**：`id` 一旦发布即冻结；改名只动 `name`。约束理由就是上面这段。

## 1.2 定位变了：从"管路由"到"管场景"

| | 改名前 | 改名后 |
|---|---|---|
| 一等公民 | 路由规则（`rules[]`） | **配置项**（`profiles[]`，一个场景） |
| 组件管什么 | 往路由表里加/撤条目 | **网卡配置（IP/掩码/网关/DNS）+ 路由** 一起管 |
| 用户的心智 | "我怎么把这条路由加上" | **"当我在这个网络里，我要什么"** |
| 触发条件 | 网卡在线 + 网关匹配 | **监控网卡 + 生效网段**（你给的） |

后面那一行就是整份文档的判据。**配置项 = 一句自包含的意图：「在某网络里，配某 IP，加某些路由」。** 它不需要再去别处找上下文——这是它值得当一等公民的原因。

# 二、领域模型：配置项是一等公民

## 2.1 配置项的结构

```
配置项 Profile（用户可增删，列表顺序 = 优先级，n 个）
├── name          名称           "office"
├── ifaces        监控网卡列表    [en5, en6]        ← 只在这些网卡上做匹配
├── match         触发条件
│   ├── subnet      生效网段      192.168.110.0/24   ← 网卡上存在落在该网段的 IPv4 → 命中
│   └── gateway     网关匹配      10.208.195.254      ← 兼容旧配置用（见 §6.2），可省
│                                                    它兼任第二件事：某行 via 留空时取它当下一跳
│                                                    （2026-10-09，见计划《留空下一跳回落网卡网关》）
├── net           网络配置
│   ├── mode = static   手动：ip / mask / gateway? / dns?
│   └── mode = dhcp     DHCP
│       └── pin?（可选子项）  命中时把 DHCP 拿到的地址固化为静态
│              pin.ip(必) / pin.mask(必) / pin.gateway? / pin.dns?
│              ＋ 照抄开关二枚（可选，只写 true）：gateway_from_lease / dns_from_lease
│                 —— 勾了才把租约里那一位一并固化；留空是「不固化」，见 §2.5
└── routes        路由规则（本套的总开关 + 清单）
    ├── enabled   本套是否叠加（§4.7 一，缺省 true）
    └── items[]   { destination, via?, enabled }
                   via 留空 = 用 match.gateway；那一格也空时只有「固化租约」的场景放行
                   （2026-10-09）——彼时取「本场景固化那块网卡时 DHCP 给过的网关」，
                   取到过就记着（跨重启不丢），从未取到过则这条路由一条都不动并报警告
```

> **2026-09-17 定案（伴随第 4 步落地）**：``routes`` 是**映射**（``enabled`` + ``items``），
> 不是裸列表。原因：§4.7 一 / 裁决 8 要「整套关掉但配置还在」，这一级塞不进列表里；
> 而 §2.1 原先的树与 YAML 示例把它画成了列表，与 ``routes.enabled`` 的点号写法自相矛盾。
> 列表 + 平级键（``routes_enabled``）那条路被否：同一件事出现两种命名。

对应到 YAML：

```yaml
plugins:
  route_guard:                    # ← id 不变
    automation: on                # on | off       自动化总闸
    pinned: ""                    # 手动指定生效的配置项名；空 = 自动按匹配
    fallback: keep                # keep | dhcp    无匹配时：保持现状 / 交还系统
    poll: 5                       # 框架轮询 tick() 的间隔（秒）；默认由 suggested_poll 生成，用户可覆盖
    helper_poll: 30               # 本组件后台 helper 自己的节律（秒）——一个配置键只服务一个消费者

    profiles:                     # ← 顺序即优先级（列表第一个命中者胜）
      - name: office
        ifaces: [en5, en6]
        match: { subnet: 192.168.110.0/24 }
        net:
          mode: static
          ip: 192.168.110.5
          mask: 255.255.255.0
          gateway: 192.168.110.1       # 可选
          dns: [8.8.8.8]              # 可选
        routes:
          enabled: true
          items:
            - { destination: 10.201.51.0/24,     via: 10.208.195.254 }
            - { destination: 10.202.0.0/16,      via: 10.208.195.254 }
            - { destination: 192.168.200.5/32, via: 10.208.195.254 }
      - name: home
        ifaces: [en6]
        match: { subnet: 192.168.21.0/24 }
        net:
          mode: dhcp                  # mode 只有 static / dhcp 两个值
          pin:                        # pin 可选；不写 = 纯 DHCP，一根手指都不碰网卡
            ip: 192.168.21.88          # 命中时把租约固化成这个地址
            mask: 255.255.255.0
            # 下面两枚是「照抄开关」（可选，只写 true）：不写 = 不固化那一位（见 §2.5）。
            # 与上面同名的写死值互斥——要写具体网关就别勾照抄，反之亦然。
            gateway_from_lease: true  # 把 DHCP 拿到的网关一并固化
            dns_from_lease: true      # 把 DHCP 拿到的 DNS 一并固化
        routes:
          enabled: true
          items:
            - { destination: 172.16.0.0/16, via: 192.168.21.1 }

      - name: cafe                    # 同为 DHCP，但不固化（连 pin 都不写）
        ifaces: [en0]
        match: { subnet: 192.168.1.0/24 }
        net: { mode: dhcp }
        routes: { enabled: true, items: [] }
```

**多配置项同时命中怎么办？**（你的模型必然遇到：两个配置项都监控 `en5`、网段重叠）
建议规则：**按 `profiles` 列表顺序，第一个命中者胜**；用户在配置窗体里拖拽排序。这比"优先级数字"好——数字要用户自己维护，顺序是拖一下就有的。（顺带说明：这落在**配置窗体**，不是设置页。）

## 2.2 两处真源冲突，必须先收敛

这两条不定，写代码时必然打架。

### 冲突 A：全局「网卡配置：DHCP/手动」 vs 配置项里的「网络配置」

你的描述里，**同一件事出现在两个地方**：全局配置项说"网卡配置：DHCP 还是手动"，每个配置项里又说"网络配置：DHCP 或者手动"。

> **裁定：取消全局的"网卡配置"维度。** 它天然是配置项的属性（office 用手动、home 用 DHCP，这才是你想要的）。再放一个全局开关 = 第二真源，两者冲突时无从裁决。

那全局该留什么？留**真正全局**的三项：

| 全局项 | 取值 | 为什么它必须全局 |
|---|---|---|
| `automation` | 开 / 关 | 总闸。关掉 = 什么都不碰（不碰 IP、不碰路由） |
| `fallback` | 保持现状 / 交还系统 | "所有配置项都不匹配时怎么办"——这句话没有配置项可以归属 |
| `poll` / `helper_poll` | 秒 | 装置节律，与配置项无关：`poll` 是**框架**轮询 `tick()` 的间隔（默认由 `suggested_poll` 生成），`helper_poll` 是组件**后台 helper** 自己的节律。**一个配置键只服务一个消费者**——不再有 `state_poll`（面板刷新就是框架 `tick()` 的节拍） |

### 冲突 B：「生效的配置」是配置项，还是结果？

> **裁定：它是运行期结果，不是配置。** 用户不能"设置"它，只能"手动指定"来覆盖自动选择。

这一句区分开了两个东西，你需求里原本是混在一起的：

| | 是什么 | 落在哪 | 谁能改 |
|---|---|---|---|
| 配置项列表 | 输入（用户定义的场景） | 配置窗体 | 用户 |
| **生效的配置** | **输出（当前命中的那一个）** | 面板副标题 + 配置窗体顶部（只读回显） | 没有人——它是算出来的 |
| 手动指定 | 覆盖开关 | 配置窗体（列表项 [固定使用]） | 用户 |
