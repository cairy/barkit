## 1. 组件是什么

一个组件 = `src/barkit/plugins/<your_id>/` 下的一个**子包**，其中 `plugin.py` 暴露一个名为 `Plugin` 的 `barkit.core.plugin.Plugin` 子类。

发现机制（`core/registry.py`）：框架用 `pkgutil.iter_modules` 扫描 `barkit.plugins` 下的所有子包（`_` 前缀子包跳过，不加载），对每个子包尝试 `import <pkg>.plugin` 并取其中的 `Plugin` 类；外部插件走 `core/loader.py` 的 manifest 驱动发现。两类插件在加载闸门汇合：**`api_version` 低于 3 的直接拒载**（v1/v2 适配层已删除，旧插件给出拒绝原因）。所以**新建组件 = 新建一个子包目录**，零注册代码。

```
src/barkit/plugins/
├── __init__.py
├── _template/       # 官方脚手架模板（_ 前缀不加载，复制改名即用）
├── autotype/        # 已有组件范例（action 型）
│   ├── __init__.py
│   └── plugin.py    # 暴露 class Plugin(Plugin)
├── notify_guard/    # 已有组件范例（daemon / execute 型）
├── route_guard/     # 已有组件范例（daemon / observe 型）
└── your_component/  # ← 你新建的
    ├── __init__.py
    └── plugin.py
```

组件按 `config.default.yaml` 里 `plugins.<id>.enabled` 控制启停；缺省为启用。

> 💡 入口方法是**声明点方法**（一个声明点一个方法），见文首阅读须知与《组件契约规范》§1.3。目录骨架的完整规则（白名单、六面骨架、模板双骨架）见《插件结构规范》§2、§10。

## 2. 最小可运行组件

```python
# src/barkit/plugins/hello/plugin.py
from __future__ import annotations

from barkit.contribution.specs import ActionSpec, HotkeySpec
from barkit.core.plugin import RUN_ON_DEMAND, Plugin

class Plugin(Plugin):
  id = "hello" # 与目录名一致（不一致时回退用目录名）
  name = "示例组件"
  run_mode = RUN_ON_DEMAND # 按需触发，不进调度器
  api_version = 3 # v3 贡献契约；缺失/低于 3 会在加载期被拒

  def actions(self) -> tuple[ActionSpec, ...]:
  return (ActionSpec(label="打个招呼", on_click=self.greet),)

  def hotkeys(self) -> tuple[HotkeySpec, ...]:
  return (HotkeySpec(name="hello_greet", label="打个招呼",
  default_combo="ctrl+alt+h", callback=self.greet),)

  def greet(self) -> None:
  print("hello from BarKit component")
```

**两个不写的东西**：Spec 的 `plugin_id`（框架在收集期注入）、你没覆写的声明点（基类各有默认值）。

放进 `src/barkit/plugins/hello/plugin.py`（含空的 `__init__.py`）后，`uv run barkit` 启动即会自动加载它。

> 💡 **热键默认键位随插件声明**（`HotkeySpec.default_combo`），用户可在 `config.yaml` 用 `hotkeys.<name>` 覆盖。启动时框架经贡献注册中心统一收集 `HotkeySpec` 并注册全局热键，插件不自己注册。想暴露更多交互，再覆写对应的声明点方法：`component()`（标题栏图标）/ `state_specs()`（状态机）/ `row_specs()`（面板行）/ `detail_entry()`（详情页，点整行打开）/ `settings_page()`（设置页）。逐项见 §3.4 与《组件契约规范》§1.3。

## 3. 插件契约详解

契约定义在 `core/plugin.py` 的 `Plugin` 基类。子类用**类属性**声明身份，用**方法**贡献行为。

### 3.1 类属性（声明式）

> 本表锚定**当前源码**。契约目标形态（`version` 等尚未落地的改名与新增）见《组件契约规范》§2.1 与其附录 A。`run_mode` / `failure_policy` 已于 2026-09-15 落地（D10 / D11）、`suggested_poll` 已于 2026-09-16 落地（D21），下表即新名。

| 属性 | 取值 | 含义 |
|------|------|------|
| `id` | `str` | 组件唯一标识，也是配置段键名 `plugins.<id>`；留空则回退为目录名 |
| `name` | `str` | 面板/菜单展示名 |
| `run_mode` | `RUN_ON_DEMAND` / `RUN_PERIODIC` | **框架要不要周期叫我**：按需触发不进调度器；常驻轮询则由 scheduler 按 `poll` 间隔驱动 `tick()`。声明 `RUN_PERIODIC` 就必须自己写 `tick()`（门禁守这条一致性） |
| `failure_policy` | `FAIL_LOG` / `FAIL_BREAK` | **我失败时框架怎么办**：只记日志，或连续失败达阈值熔断（见 §7）。**仅 `RUN_PERIODIC` 有意义** |
| `required_permissions` | `list[str]` | 声明所需系统权限（如 `["accessibility"]`），用于引导 |
| `api_version` | `int` | 贡献契约版本，**必填 `3`**；缺失或低于 3 在加载期被拒（v1/v2 适配层已删） |
| `order` | `int` | 新插件的默认插入位（越小越靠前）；已进 `plugin_order` 的以用户排序为准（默认 0） |

常量从 `core.plugin` 导入：`RUN_ON_DEMAND, RUN_PERIODIC, FAIL_LOG, FAIL_BREAK`。
**判定一律与常量比，别写字符串字面量**（`run_mode == "periodic"` 这类写法在常量改名时不报错、
只是永远不成立；门禁 `test_mode_literals_never_used_in_comparisons` 会抓）。

### 3.2 生命周期

| 方法 | 线程 | 说明 |
|------|------|------|
| `start()` | 主线程 | 加载并启用时调用。daemon 不要在这里自起线程——轮询交给 scheduler |
| `stop()` | 主线程 | 停用/退出时调用，做清理（如退订事件） |
| `tick()` | **worker 线程** | 仅 daemon。`scheduler` 按 `poll` 间隔在独立线程池调用，**绝不可直接操作 Qt UI**。`tick()` 返回 `StateReport`（或 `None`）：**只报取值名**（＋可选的覆盖文案 `summary`），级别 / 图标归 `StateOption` 声明；返回非 None 时框架自动 publish 到 `plugin.<id>.status.<key>`，插件禁自 publish。见 §6 |

### 3.3 配置访问

**读自己声明过的配置键，一律走 `self.cfg.value("某键")`**（`core/plugin_config.py`）：

```python
def retry_times(self) -> int:
  return int(self.cfg.value("retry_times")) # 默认值来自你自己的 config_schema()
```

`cfg` 是本组件配置的 typed 门面（`Plugin.cfg`，惰性构造），它把「类型 / 默认值 / 取值域」三件事全部回读 `config_schema()` 的声明：

| 你想要的 | 写法 | 说明 |
|---|---|---|
| 某一个键的**当前值** | `self.cfg.value("k")` | 值缺失、为 `null`、或通不过 `FieldSpec.check_value()` 时**回落到声明里的默认值**（`plugin_config.normalize`）。返回值**只读**，直接改它不影响配置 |
| 某个键的**默认值** | `self.cfg.default_of("k")` | 例如「用户填的值小于下限就用默认值」这类判据 |
| 这个键**有没有声明** | `self.cfg.declared("k")` | 未声明的键调 `value()` 会抛 `PluginConfigError`（报出组件 id 与键名），不静默返回 `None` |
| **整段**配置（少见） | `self.cfg.section()` | 等价于 `self.plugin_config()`；只在「遍历自己的全部键」这类场景用 |

**别在调用点写 `self.plugin_config().get("k", 兜底)`** —— 那个 `兜底` 是**第二份默认值**：与 `config_schema()` 漂移时不报错，界面上也看不出分叉（方案见）。门禁 `test_plugin_config.py::test_plugins_do_not_read_their_section_by_hand` 扫 AST 拦这条。

**写配置也走同一个门面**（三个写口，语义与判据见 §4.3「写用户配置」）：

| 你想要的 | 写法 | 说明 |
|---|---|---|
| 写一个键 | `self.cfg.set("k", v)` | 校验类型与 `choices`；**等于声明默认值即删键**（用户 YAML 是差异层） |
| 一次写一组键 | `self.cfg.update({"k": v, …})` | 逐键同上；先整批校验再落盘 |
| 嵌套子键 / 连带删除 / 框架键 | `self.cfg.mutate(fn)` | 逃生舱：`fn` 拿到**用户差异段**就地改；不带那两条规则 |

**组件侧不许自己取 `ctx.config`**（门禁 `test_plugins_write_config_only_through_the_facade` 扫 AST）：`ctx.config` 在哪不归组件知道，搬实现、换存储、加审计都只改门面那一处。

**框架的键不在 `cfg` 里**：`enabled`（加载门控，读 `Plugin.enabled`）、`poll`（调度节拍，`core/scheduler.py` 唯一消费者）、`ui.*` / `states.*`（显示位与状态持久化，各由渲染层读）。`value()` 取这些键会抛错——**一个配置键只服务一个消费者**（决议 D27）。

`enabled` 默认 `True`；`config.default.yaml` 写 `plugins.<id>.enabled: false` 即不加载。

### 3.4 声明点方法：插件能贡献什么

**一个声明点一个方法**，各自有明确的返回类型与基数（方法名与基数的唯一真源是 `contribution/points.py::declaration_points()`，字段语义的唯一真源是《组件契约规范》§1.3）。两条纪律：

- **签名即结构**：拼错方法名、返回类型不符、元素不是该声明点的 Spec、违反基数（例如两枚身份图标）→ 收集期报错并隔离该组件，**不静默丢弃**。
- **只覆写你有的声明点**：其余走基类默认值（空元组 / `None` / 空 schema）；每个方法必须廉价、无副作用、反复调用返回等价内容。

按「一次收集产出什么」分两族。

**第一族：贡献点（收集期产出 Spec，框架据此渲染界面）**

| 声明点方法 | 返回类型 | 基数 | 贡献到哪 |
|---|---|---|---|
| `component()` | `ComponentSpec \| None` | 0/1 | 标题栏图标条（每组件一枚）—— **前提：有状态机**（◷ 2026-09-17，那格画的是代表态取值图标，见契约规范 §2.4） |
| `state_specs()` | `tuple[StateSpec, ...]` | n | 状态机（取值闭集 ＋ 级别 ＋ 图标） |
| `row_specs()` | `tuple[StatusRowSpec, ...]` | n | 状态面板的一行（不声明也有 1 行） |
| `detail_entry()` | `DetailEntrySpec \| None` | 0/1 | 详情页入口（点组件列表整行打开） |
| `settings_page()` | `SettingsPageSpec \| None` | 0/1 | 设置窗的一页 |
| `actions()` | `tuple[ActionSpec, ...]` | n | 面板底部操作区按钮 |
| `hotkeys()` | `tuple[HotkeySpec, ...]` | n | 全局热键（配置键 `hotkeys.<name>`，用户可改键位） |

**第二族：非 UI 声明（框架拿去做托管 / 校验 / 诊断，不画界面）**

| 声明点方法 | 返回类型 | 基数 | 框架拿它做什么 |
|---|---|---|---|
| `config_schema()` | `FormSchema` | 1 | **配置默认值的唯一真源**（§4.1）；`cfg.value()` 也从这里取类型与取值域 |
| `resources()` | `PluginResources` | 1 | 卸载时彻底清理（数据文件 / 系统变更 / root 二进制） |
| `resident_services()` | `tuple[ResidentService, ...]` | n | 长驻服务的起停与差量收敛（线程 / 时钟归框架） |
| `subjects()` | `tuple[str, ...]`（**领域名**，不是文件路径） | n | 订阅守护推来的事实，到达时转交 `on_observed(subject, observed)` |
| `intent_subject()` | `str`（空串 ＝ 不声明） | 1 | 期望态挂到哪个领域；「立即检查」靠它让守护现在跑一轮 |
| `event_topics()` | `tuple[str, ...]` | n | 系统事件（唤醒 / 外设 / 网络 / 屏幕）订阅，转交 `on_system_event(topic, payload)` |
| `diagnostics_text()` | `str \| None` | 0/1 | 返回非空才画「复制诊断」按钮；**只读**，不得改系统状态 |

**没有「header chip」这个贡献点**（`ChipSpec` 已随声明式 UI 重构删除，`contribution/points.py` 里只剩 `POINT_MENU_ITEM` 常量、未进 `declaration_points()`）。想在标题栏加东西，今天只有 `component()` 一个入口。

**能力（`capabilities/`）不是声明点**，是「框架提供的可选能力基类」，靠 `class Plugin(AutomationCapability, ...)` 继承获得，见 §3.6。

> **字段总表见《组件契约规范》§4.2**（「你想做的事 → 写在哪」）；下表只列几个 Spec 的关键字段。

| Spec | 关键字段 |
|------|----------|
| `ComponentSpec` | `icon`（IconName）/ `name` |
| `StateSpec` | `key` / `states`（**取值闭集**，每值带 `level` ＋可选 `icon`/`text`）/ `initial`（取值名，留空取第一个）/ `stale_after`；运行期数值走 `StateReport`，**不写回本类** |
| `StatusRowSpec` | `icon` / `title`；`controls`（**0–2 个**，声明式接线：Switch/Button/Menu）或 `custom` 工厂逃生舱（**必须填 `reason`**）。整行点击由 `on_click` 声明，**优先于**详情入口（见本表下方的说明） |
| ~~`BadgeRuleSpec`~~ | **已删除**（◷ 2026-09-16，决议 D17）—— 「值得提醒」改由**取值**声明：`StateOption.alerts`（省略时 `WARN` / `ERR` 为真），全局阈值 `tray.min_level` 只由用户改（◷ 2026-09-19 补上写侧：值域归 `contribution/specs.py::TRAY_MIN_LEVELS`，入口在设置窗「通用 → 菜单栏」）。旧写法 `BadgeRuleSpec` / `StateSpec.show_in` 均已移除 |
| `DetailEntrySpec` | `label` + `build` 工厂（**必须填 `reason`**）+ `trigger`（`"row"`/`"action"`）+ `presentation`（`"popover"`/`"window"`）+ `save`（可选 `FormSaveSpec` = `commit` ＋ `dirty`，**只对 `window` 有意义**；声明了才有「保存」键、关窗时才拦一下，◷ 2026-09-18 决议 D35）。**只承载框架内的界面**；集合型配置**可以**走这里，也可以走 `SettingsPageSpec`——见契约规范 §2.8 与《决议》D30 |
| `SettingsPageSpec` | `label` + `build` 工厂（**必须填 `reason`**）；`schema` 保留但不接线（见插件结构规范 §7.1）。**低频一次性配置（含集合型）的正式落点** |
| `ActionSpec` | `label` + `on_click` |
| `HotkeySpec` | `name` / `label` / `default_combo` / `callback` |

**identity 铁律**（一次定死）：

- `key` 是**同一声明点内唯一**的语义名（如 `"main"`/`"tunnel"`），不要写成 `"your_id.main"`——plugin_id 不该重复出现；跨声明点同名是正常写法（状态机与它的行都可以叫 `"main"`）；
- 全局唯一标识由框架拼装：`identity() == f"{plugin_id}.{key or 'default'}"`；
- 同一贡献点只有一个贡献时 key 可省略；有多个时 key **必填且唯一**，重复即启动报错；
- 状态 topic 由 identity 派生：`topic == f"plugin.{plugin_id}.status.{key or 'default'}"`，不另设一套标识。

**整行点击给谁？** `StatusRowSpec.on_click` **优先**——框架先看它，为空才合成「打开详情页」（`shell/panel.py:803-806`）。
所以：**唤起外部应用** / 就地做一件事 → `on_click`；要打开**框架内**界面 → `DetailEntrySpec`。
声明了 `on_click` 就等于放弃框架合成的详情入口（这是优先级决定的，不是 bug）。见契约规范 §2.4 与《决议》D28。

渲染层按 identity 就地复用 widget 重绘（禁清空重建）；`custom`/`build` 工厂里的回调由框架在首次构造时接好、复用时稳定不重连。

### 3.5 PluginContext（注入的运行时上下文）

基类构造时收到 `ctx: PluginContext`，含两个字段：

- `ctx.config`：`core.config.Config` 实例，配置中心（读 `get(dotted)`、写 `save_user`、订阅 `changed`）。
- `ctx.events`：`core.events.EventBus | None`。**跨线程安全**：在 worker 线程 `publish`，事件自动以 queued 方式回到总线所在线程（主线程）分发。v2 下**状态不走这条总线由插件自 publish**（见 §6：tick 返回快照，框架统一 publish）；总线仍用于手动操作后的同 topic 快照广播与订阅。offscreen 测试环境下可能为 `None`，组件需判空。

### 3.6 能力基类（`capabilities/`）

框架在 `core/`（引擎，UI 无关）、`shell/`（渲染原语）、`plugins/`（具体组件）之外，提供显式的
**能力层** `capabilities/`：这里放「框架提供的可选能力基类」。每个能力基类 = **单一正交关注点**，
只暴露该关注点所需最小面；具体组件**需要什么能力就继承什么能力基类**，并实现其抽象钩子。

> ✅ **改名已落地（2026-09-14）**：能力基类叫 **`AutomationCapability`**（模块 `capabilities/automation.py`），
> **旧名 `Guard` / `capabilities/guard.py`**。归属与语义不变——它只提供「自动化开关 + 模式徽标」，
> 与是否常驻轮询无关。依据见《插件结构规范》§5.1–5.2。

- **存放**：`src/barkit/capabilities/`，与 `core/`、`shell/`、`plugins/` 并列。该层**可以**安全
  `import` 渲染原语（`shell/`），而 `core` 仍保持 UI 无关；依赖方向单向 `capabilities → core + shell`，无循环。
  但「允许」不等于「需要」：`AutomationCapability` 本身**零 UI 依赖**——它只产出 `ModeBadgeSpec`，
  徽标怎么画由框架决定。
- **边界**：一个能力只拥有自己的关注点，**不**包含具体组件领域逻辑（后端写、规则解析、信号），
  也**不**接管组件的整块 UI。例：`AutomationCapability` 只管「自动化运行态 + 状态行的自动化徽标」，领域开关
 （通知的允许/静音、路由的规则覆盖）仍由组件自己贡献。
- **组合**：能力写成**协作式 mixin**（`__init__` 调 `super().__init__(ctx)`，钩子用 `super()` 解析），
  组件用 `class Plugin(AutomationCapability, Scheduled, ...)` 多重继承即 MRO 干净、无菱形冲突。`Plugin` 始终是唯一根。
- **扩展**：后续加能力 = 在 `capabilities/` 下新增一个模块（如 `scheduled.py`），不动 `core`、不动现有
  组件（除非它们选择继承）。框架贡献消费完全基于 `Plugin` 契约 duck-typing，与新能力无关。

例：`notify_guard` / `route_guard` 都继承 `AutomationCapability`，把原先各自的 `auto_enabled` / `is_paused`
极性别名收敛为统一的 `automation_active` 属性；徽标点击统一走 `AutomationCapability.toggle_automation`。
新写一个守卫类组件时，直接 `class Plugin(AutomationCapability)` 即可免费获得这套「自动化开关 + 徽标」能力。
