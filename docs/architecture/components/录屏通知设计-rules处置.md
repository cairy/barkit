## 3.4 `rules` 怎么处置：**不改数据结构，只改编辑器**

现状结构（`config.default.yaml` 已迁至 `config_schema()`，`plugin.py:244-249`）：

```yaml
rules:
  - { name: 会议,  reason: 腾讯会议进行中, processes: [tencentmeeting, wemeet] }
  - { name: 直播,  reason: OBS 推流中,    processes: [obs] }
```

有人会想把它改名成 `scenarios`（对齐《网络切换》的 `profiles`）。**建议不改**，三条理由：

1. **语义没变**：它本来就是"一组进程 → 一个静音理由"，不是"网络场景"那种自带 IP/路由/匹配条件的复合体；
2. **改名 = 迁移**：用户 YAML 里的 `rules` 得搬，等于把"零迁移"变成"有一次迁移"，换来的只有措辞；
3. **现状代码已经容忍两个键名**（`decider.py:35`：`r.get("reason") or r.get("name")`），说明结构本身够用。

**真正要改的是它现在"没有编辑器"这件事** —— 见 §6.4。这是本次"可视化配置"的全部内容。

**一个值得补的规则能力（裁决项 5）**：现状 `match_rules` 是**裸子串包含**（`signals.py:169`：`any(pat in path for pat in patterns for path in snapshot)`）。它表达不了"排除"。真实诉求：「录屏时静音，但 **我自己的截图工具 CleanShot 在跑不算**」。补法很轻：规则加一个可选 `except: [clean shot]`（命中 processes **且** 不命中 except 才算命中）。**要不要加，你定。**

# 四、状态设计

## 4.1 三台状态机（严格按契约 §2.2 枚举闭集）

| key | 取值 | 级别 | 文案 | 取值图标 |
|---|---|---|---|---|
| **`display`** ★新 | `extended` | OK | 第二屏已连接 | **实心屏** |
| | `running` | IDLE | OpenDisplay 运行中 | 空心屏 |
| | `idle` | IDLE | OpenDisplay 未运行 | 空心屏 |

**1 行，不是 3 行**（契约 §2.4：行数与状态机数解绑）：三台机的信息在副标题里一句话说完。**理由与《网络切换》同**：面板行数不该随组件内部复杂度增长。

## 4.2 停用时全部降到 IDLE（不撒谎）

沿用《网络切换》§3.2 的判据：**用户主动关掉自动化 = 组件该变灰，而不是继续满屏红。**

| 状态机 | 停用前 | `off` 时 | 级别 |
|---|---|---|---|
| `display` | 任意 | 不变（**连接态是客观事实，不该被组件开关改写**） | 压到 IDLE |
| `notify` | `muted`/`desync`(ERR) | `frozen`（新增取值：冻结，保持现状） | IDLE |
| `automation` | `on` | `off` | OFF |

> **`display` 的处置与《网络切换》有一处刻意的不同**：路由/网卡的 `frozen` 是"组件不碰了但状态还在"，而**第二屏连没连跟本组件开关毫无关系**——它是世界的状态，不是我造成的。所以取值**不换**（仍报 `extended`），只把级别压灰。措辞上也不该说"已冻结"。
> 这也意味着 `display` 是唯一一个**纯观察、无副作用**的状态机——**它可以是本组件的身份主状态**。

### 5.2.2 契约增补（3 处，供《组件契约规范》收录）

**① `StatusSnapshot` 增加动态图标字段**

```python
@dataclass(frozen=True)
class StatusSnapshot:
    level: StatusLevel
    summary: str
    detail: str = ""
    updated_at: float = 0.0
    icon: "IconName | None" = None      # ★新增：本快照当前的取值图标（None = 用 StateSpec.icon）
```

> **为什么放在快照而不是 Spec**：契约 §5.2 的铁律是「**静态归 Spec，动态归快照**」。"屏在线 → 实心 / 离线 → 空心"随取值变，是动态的。
> **一处补、两处用**：这同一个字段同时满足 ① 面板行取值图标（§6.3）与 ② 托盘底图（本节）——**不需要为托盘单开一套机制**。
>
> **◷ 2026-09-15（决议 D18）**：上面那版代码里的 `detail` 字段已删除——文案只有 `summary` 一份。本节结论（取值图标放快照而不是 Spec）不受影响，字段清单以《组件契约规范》为准。

**② `StateSpec` 增加一条义务声明**

```python
StateSpec(
    plugin_id=..., key="display",
    icon=IconName.DISPLAY_OFF,          # 静态默认（快照 icon 为 None 时回落）
    as_tray_base=True,                  # ★新增：本状态"愿意义务提供托盘底图"
    ...
)
```

框架**只从声明过 `as_tray_base` 的状态里让用户挑**；未声明的状态永远不出现在配置项里。这是"组件只声明意愿，框架决定呈现"的既有分工（同 `show_in` 的思路）。

**③ 主框架设置项（落**设置窗「通用」页**，**不在本组件的设置页**）**

```yaml
tray:
  base_source: ""      # "" = BarKit 默认底图；否则 "plugin.<id>.status.<key>"
```

- **为什么是主框架设置**：它是**托盘的外观**，与任何单个组件无关。放组件设置页会出现"同一个框架开关在 N 个组件的设置页各有一份"。
- 取值列表 = `BarKit 默认` ＋ 所有"声明了 `as_tray_base` 的状态"（显示为 `组件名 · 状态名`，如「录屏通知 · 第二屏」）。
- **★落点已核实（2026-09-14）：不新建页。** 主框架设置窗**已有「通用」页**（`shell/settings.py:78` 注册、`:366-372` 实现），当前是**占位页**，其文案甚至自带伏笔——「更多通用设置（如启动行为）后续开放」。落地时在「通用」页内新增一张 Card「菜单栏图标」，把占位文案换掉即可。
- **回落规则（必须硬性）**：快照缺失 / `icon is None` / 该状态失联 → **回落默认底图**，**不报错、不留空白格**、不出现"菜单栏那一格消失了"。
- **配置项必须自述的两句话**：① 选它之后 BarKit 身份在菜单栏不再可见；② 该状态正常时你看到的图标由它决定。

## 6.1 判定线

沿用《网络切换》§4.1 的三条判定线（它们与组件无关，是通用规则）：

```
判定线 1：这个字段属于「这条规则」，还是属于「整个组件」？
          ├─ 某条规则 ──▶ 规则编辑器（在规则的编辑语境里）
          └─ 整个组件 ──▶ 判定线 2
判定线 2：这是「造/改领域对象」，还是「运维这个装置」？   → 两者都落设置页（§6.4）
判定线 3：高频、二元、即时？ ──▶ 面板行就地，不弹窗
```
