## 5. 基类与能力选择

| 基类 | 定义位置 | 本质 | 何时用 |
|---|---|---|---|
| `Plugin` | `core/plugin.py` | 所有插件的**契约基类** | **必须**继承（直接，或经由能力 mixin 间接） |
| `AutomationCapability` | `capabilities/automation.py:33` | **「自动化开关」能力 mixin**（提供 `automation_active` / `set_automation_active` / `toggle_automation` / `mode_badge_spec`） | 仅当插件有「自动运行 / 手动接管」概念 |
| `HelperOpsCapability` | `capabilities/helper_ops.py:59` | **「装置运维」能力 mixin**（立即重跑 / 安装 / 卸载 ＋ 设置页页尾运维卡） | 仅当插件装同一个 root helper |
| `NotifyCapability` | `capabilities/notify.py:198` | **「系统通知」能力 mixin**（弹通知 ＋ 按钮按归属回投） | 仅当组件要在面板收起时说一句话 |

### 5.1 归属：`capabilities/` 就是能力 mixin 的家

`capabilities/__init__.py:1-22` 已明文定义该包语义：**「框架提供的可选能力基类」**，每个能力 = 单一正交关注点，写成协作式 mixin，可 `class Plugin(AutomationCapability, Scheduled, …)` 多重组合；并**明文列出唯一例外** `capabilities/helper/`（那是随包部署到系统域的 root helper 源码包，stdlib-only）。所以 `automation.py` 放在这里**符合既有契约**，不需要移动。

### 5.2 改名：`Guard` → `AutomationCapability`

理由（实测成立）：`Guard` 易被读成「常驻守护基类」，但它只提供自动化运行态开关 + 模式徽标，与是否常驻轮询无关。

反例即证据：

| 插件 | 继承 | `run_mode`（2026-09-15 前的 `kind`） |
|---|---|---|
| `route_guard` | `AutomationCapability`（§5.2 改名前叫 `Guard`） | `RUN_PERIODIC` |
| `ipad_tunnel` | `AutomationCapability` | `RUN_PERIODIC` |
| `notify_guard` | `AutomationCapability` | `RUN_PERIODIC` |
| **`hosts_guard`** | **裸 `Plugin`** | **`RUN_PERIODIC`** |

`hosts_guard` 是常驻 daemon 却不继承 `Guard` → 「是否 `Guard`」与「是否常驻轮询」**已经解耦**，本规范**固化**此解耦。是否常驻由 `run_mode=RUN_PERIODIC` + 实现 `tick()` 决定（两者必须同时成立，有门禁守这条一致性）。

**实施**：纯 find-replace，行为零变。**模块名与测试文件名一并改**（§13.1 决议）——两者同属一个原子步，分开做只会制造第二次无意义 diff；而「`guard`」的误导性在模块路径上同样存在（`from barkit.capabilities.guard import …`）。

| 类型 | 文件 | 改动点 |
|---|---|---|
| 框架 | `capabilities/guard.py` → `capabilities/automation.py` | 类名 + 模块 docstring（`class Guard(Plugin)` → `class AutomationCapability(Plugin)`） |
| 框架 | `capabilities/__init__.py:13` | docstring 举例 `class Plugin(Guard, Scheduled, …)` |
| 插件 | `route_guard/plugin.py:33,77,260` | import + 继承 + 「Guard 能力统一 seam」注释 |
| 插件 | `notify_guard/plugin.py:25,50` | import + 继承 |
| 插件 | `ipad_tunnel/plugin.py:33,83,333` | import + 继承 + 注释 |
| 测试 | `tests/test_guard_base.py` → `tests/test_automation_capability.py:17,27,57,130` | import + 用例名 |
| 文档 | `组件开发指南.md:150,153,156,160,161,162` | 全部是「当前怎么用」，**必须**改 |
| 文档 | | 同上；`:16`、`:138` 是历史记账，**保留原名**并加新旧名对照，不改写历史 |

## 6. 样板代码：按「谁保证语义」分派

### 6.1 分派原则

| 判据 | 归属 |
|---|---|
| 与**框架契约**强相关（涉及「框架如何消费你」「发布边界」「框架保证的语义」） | `Plugin` **基类默认方法** |
| **纯横切手艺活**（显式参数、无 ctx、任何插件可复用） | 独立自由函数模块（不继承 `Plugin`、不持 ctx）。**当前无此类代码**：曾设 `core/plugin_support.py`，2026-09-30 随零调用方删除 |
| 需要一个**框架还不存在的 API** | **先补框架**（下表的 `_load_user_config`），不得机械替换 |

### 6.2 处置表（频次口径见 §0.1：6 个真实插件，不含 `_template`）

### 6.3 `_load_user_config` 不是「已存在」，是框架缺 API

**语义不可互换**：

| | 实际语义 | 证据 |
|---|---|---|
| `_load_user_config()` | 读**整份用户 YAML 根**，供 read-modify-write **回写** | `route_guard/plugin.py:277-279` 读 `self.ctx.config.user_path`；`:244-248` 改 `plugins.route_guard.paused` 后 `save_user` |
| `plugin_config()` | 合并默认值后的**只读**插件段 | `core/plugin.py:91-93` |

机械替换的后果：`paused` / `force_apply` / `tunnel_enabled` / `ignore_link` 这些开关「点了没反应、还不报错」。

**真正的问题是范围被低估了**。这套「读用户 YAML → 改 `plugins.<id>` 子段 → 原子写」的把式在插件侧散落 **18 处**（读 9 / 写 9）：

| 层 | 读（`yaml.safe_load(...user_path...)`） | 写（`save_user`） |
|---|---|---|
| `plugin.py` | `route_guard:279`、`notify_guard:93`、`ipad_tunnel:414` | `route_guard:248,430`、`notify_guard:111`、`ipad_tunnel:136,360,394` |
| `config_dialog.py` | `route_guard:138,148`、`ipad_tunnel:55,155`、`autotype:153,165` | `route_guard:157`、`ipad_tunnel:179`、`autotype:173` |

**为什么现有 API 不够**：`Config.set_plugin_section()`（`core/config.py:280-291`）要求调用方提供**完整段落**（内部对已有段做顶层 `update`）；插件要改的是**单个嵌套键**，必须先把现存段落读出来，而读侧的 `_read_user_raw()`（`config.py:190`）是**私有**。

**收口动作（框架侧，前置）**：

```python
class Config(QObject):
  def update_plugin_section(self, plugin_id: str, mutate: Callable[[dict], None]) -> None:
  """对 plugins.<id> 用户差异段做「读—改—写」。

  读原始用户 YAML（不合并 defaults）→ 取出 plugins.<id>（缺失传空 dict）→
  mutate(section) 就地修改 → 原子写 + chmod 600 → 重载。
  mutate 抛异常则不落盘（调用方负责提示）。整段为空时删除该键。
  """
```

收口后：18 处散点 → 1 个 API；§4 跨面禁令第 3 条（UI 不得直改 config）才**有可能**被满足。该 API 同时是将来 `schema` 自动渲染器的**唯一写回路径**（§7.1），因此它的落地不依赖接线决定。

### 6.4 `_snapshot()` 不提取公共算式（收益为负）

5 份 `_snapshot()` 的主体是**各自独立的 level / summary 决策树**，输入状态互不相同（路由表 / 通知模式 / hosts 规则校验结果 / 隧道激活态），**没有可提取的公共算式**——最极端的 `ipad_tunnel/plugin.py:557-617` 是 60 行多分支。

真正重复的只是**尾部装配**：`updated_at` 取值、rows 装配。曾拟抽 `plugin_support.snapshot(level, summary, *, updated_at=None, rows=())` 大约每处省 1 行（该模块 2026-09-30 已删，此议作废）。

> **◷ 2026-09-15**：装配里原有的 `detail` 拼接随决议 D18 删除（文案只有 `summary` 一份），这层装配只剩两个字段 ⇒ 包一层的收益进一步趋近于零，本节的「不进阶段 0」结论更强了。

**结论：列为「可选、收益待证」，不进阶段 0。** 第 1 稿把它列为 `plugin_support.build_snapshot(**fields)`，是把「一行构造 `StateReport`」包了一层，等于没减重复。

### 6.5 状态读取的降级策略要显式化

现有三份的降级行为**不同**，抽象时必须保留差异、不得抹平：

| 插件 | 读取失败 / 文件缺失 | 处理 |
|---|---|---|
| `route_guard:64-75` | 返回 `{"ok": False, "error": "<具体原因>"}` | **区分**缺失 / JSON 坏 / 其它 OSError，三类文案各异 |
| `ipad_tunnel:70-80` | 同上（文案换成 `tunnel_state.json`） | 同 |
| `hosts_guard:42-51` | 返回 `{}` | 合并所有异常为一种降级 |

因此这类抽象的签名应允许调用方指定降级值，例如
`read_json(path, *, on_error: Callable[[Exception], object]) -> object`，而不是硬编码一种行为。
（`plugin_support` 2026-09-30 已删；本条保留作抽象设计口径。）
