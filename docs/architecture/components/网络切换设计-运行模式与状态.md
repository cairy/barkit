## 2.3 运行模式三态

收敛掉冲突 A、B 之后，「自动化开关 + 网卡配置 + 生效的配置」三个概念收敛成**一个三态**：

| 模式 | 含义 | 谁决定 | 徽标文案 | 徽标样式 | 开关 |
|---|---|---|---|---|---|
| `auto` | 自动：按匹配条件选配置项 | 插件按网络变化算 | **生效配置项名**（`office`） | accent（命中生效）/ neutral（无匹配） | 开 |
| `pinned` | 手动指定：忽略匹配，强制用某个配置项 | 用户指定 | `office ▾`（同文案，**靠 accent 表示"你锁定的"**） | **accent**（提示"这是你锁定的"） | 开 |
| `off` | 停用：不碰 IP、不碰路由，**保持现状** | 用户关自动化开关 | `已停用` | neutral | 关 |

> **微调（2026-09-13，见 §4.6）**：徽标文案从「自动 / 手动」改成**生效配置项名**。
> 根因：「自动」是**默认态**，把默认态写进一个带 accent 的控件位，等于把开关那句话说了两遍；而"现在用的是哪一套"才是这一行真正缺的信息。来源信息（自动命中 / 手动指定）挪到副标题首词。
> accent 覆盖「你锁定的」与「规则命中的」——两者都是"这一行当前有东西在管"，都应强调；
> 只有停用 / 无匹配才 neutral（2026-09-18 修正：命中却显示灰色看着像"禁用"，与"规则已生效"矛盾）。

> **◷ 落地进度（2026-09-18，第 7b 步）**：三态**已实装**，落点 `route_guard/plugin.py::mode_badge_spec`
>（徽标文案 `_badge_label` ＋ accent `_badge_accent`），决策侧在 `intent.compute_apply`：
> `paused` → 沿用上轮（冻结）｜ `pinned` 非空 → **忽略匹配**，只有被指定那条生效｜ `manual_only` → 恒不生效
>（只能被 `pinned` 点亮）｜ 否则 → 命中即生效。三点实装口径：
> ① `auto` 与 `pinned` 的徽标文案**同名**（都是生效场景名），差别**只在 accent** —— 这正是上表那一行；
> ② 停用（`off`）时一律 **neutral**，与上表一致（"它没在管"再上色自相矛盾）；
> ③ **停用态下面板那枚 Switch 禁用**（不是本表的内容，是配套口径）：那时 helper 整体冻结，翻这一下只是
> 写个不会生效的覆盖 —— 开关当场翻过去、路由一条没动，用户会以为撤掉了，而 §3.2 的裁决恰恰是
> "停用不回滚"。徽标**仍可点**（可点性是构造期定死的，与运行期能否改配置不同源），列入真机目测。
> 判据与踩坑见 §A32。

**你要求界面支持的三条，正好一一落位**：

| 你说要支持 | 落位 | 形态 |
|---|---|---|
| 自动化的停用与启用 | `off` ⇄ (auto/pinned) | **设置页顶部**（低频、破坏性）；面板副标题写「已停用」做状态回显（§4.6） |
| 网卡配置：DHCP / 手动选某个配置 | `auto` ⇄ `pinned` + 选哪个 | **面板徽标可点 → 场景列表**（每项带网段与路由摘要），选中即生效（§4.5） |
| **取消（撤掉）已叠加的路由** | **覆盖层「本次」** | **面板行 Switch = 本次叠加**（§4.8）；"以后都不要"走配置层 `routes.enabled` |
| 路由规则是否已叠加 | **结果**只读 | 副标题（§4.7） |

> 面板那个唯一控件位给了「本次叠加」而不是「自动化总闸」：**撤路由是当场的动作，停用整个组件是装完就不再碰的决定**。两个并列 Switch 在 320px 宽的行里无法分辨谁是谁（只能靠 tooltip），所以只留频率高的那个。

## 2.4 两个"网关"不是一个东西

这是最容易埋雷的地方，必须写进领域模型：

| 名字 | 含义 | 举例 | 谁的路由表项 |
|---|---|---|---|
| `net.gateway` | **网卡自己的默认网关** | 走 en5 出去经 192.168.11.1 | 默认路由 `0.0.0.0/0` |
| `routes[].via` | **这条目标网段的下一跳** | 去 10.1.51.0/24 经 10.8.195.254 | 明细路由 `10.1.51.0/24` |
| 本场景固化那块网卡时 DHCP 给过的网关 | **`via` 与 `match.gateway` 都留空时的下一跳来源**（2026-10-09） | 同上那条明细路由，下一跳取租约里的那个 | 明细路由 `10.1.51.0/24` |

两者可以相同（同一网关出两个方向），也可以不同（走 VPN/专线的旁路网关）。**现状代码里只有后者**（`rules[].gateway` 兼作触发匹配条件），而"网卡网关"从来没人管——用户自己在系统设置里配。本次新增前者，所以两个名字必须分开取。

第三行是后加的（2026-10-09），它**不是**第二行的别名，而是它的一个来源：某行 `via` 留空时取 `match.gateway`；
那一格也空着时，**只有「固化租约」（`mode: dhcp` + `pin`）的场景才放行**，值取本场景固化那块网卡时
DHCP 给过的网关。取到过就记进 helper 那本账（跨 barkit 重启不丢），**从未取到过**则那条路由一条都不动、
面板报警告类状态。非固化租约的场景里留空仍然在保存那一刻报错。

> 为什么不顺手让它回落 `net.gateway`（静态/写死网关那一支）：那个值用户在配置里**写得出来**，
> 让他直接填就行；多一条回落等于多一条「界面上看不见它取的是谁」的隐式规则。见计划《留空下一跳回落网卡网关》§1.4。

## 2.5 DHCP 下的可选子项 `pin`（固化）

**它不是第三种模式，是 `mode: dhcp` 下的一个可选开关。**

| | 配置 | 行为 |
|---|---|---|
| 纯 DHCP | `mode: dhcp`，无 `pin` | 一根手指都不碰网卡，跟随 DHCP（最常见） |
| DHCP + 固化 | `mode: dhcp` + `pin` | 平时跟随 DHCP；**该配置项命中时**，把拿到的租约固化为静态 |
| 手动 | `mode: static` | 直接写入指定 IP，与 DHCP 无关 |

模式枚举只有两个值 `static` / `dhcp`——固化是 DHCP 的**修饰**，不是它的兄弟。

"获取到 IP 后"说明固化是**两个时刻**的动作，不是一份静态配置：

```
网卡以 DHCP 运行
      │  拿到租约（IP / 掩码 / 网关 / DNS）
  ▼
该配置项命中？
      ├─ 未声明 pin ──▶ 什么都不做（纯 DHCP）
      └─ 声明了 pin ──▶ 按 pin 固化
                           ├─ pin.ip      必选  留空 = 用 DHCP 拿到的值
                           ├─ pin.mask    必选  同上
                           ├─ pin.gateway 可选  留空 = 不固化这一位
                           ├─ pin.dns     可选  同上
                           ├─ pin.gateway_from_lease  可选（true）照抄租约里的网关
                           └─ pin.dns_from_lease      可选（true）照抄租约里的 DNS
  ▼
  网卡切为 Manual + 写入固化值
```

> **`gateway` / `dns` 留空是「不固化」，不是「继续跟随 DHCP」**（2026-09-18 真机实测后更正；
> 本节原先写的是后者，那是错的）。固化这个动作本身就把服务切成 Manual，**DHCP 随之停止**，
> 它给的网关也一起消失（`networksetup -getinfo` 读到 `Router: (null)`）。所以「留空」只能
> 解释成「这张网卡不带网关 / 不改 DNS」，不是「还在跟着 DHCP 走」。
>
> 要把租约里的值也一并固化，用 `gateway_from_lease` / `dns_from_lease`（只写 `true`）。
> 三个纪律：① 只认 `true`（写 `false` 与不写等价，不留多余语义）；② 与同名的写死值**互斥**，
> 同时给 ⇒ 整份拒绝（一个照抄、一个写死 = 用户自己也没想清，不猜哪个优先）；③ 租约里没有
> 那一位（或读到 `(null)` 这种本地化残留）⇒ **当成没这项**，不编值；照抄来的网关仍走既有的
> 「不在本网段就不写」硬拦。**不用「留空 = 照抄」的原因**：那会静默改掉已有配置的含义 ——
> 已经写着 `pin: {ip: '', mask: ''}` 的场景会突然开始钉网关，而用户一个字都没动过。

**"留空 = 用 DHCP 拿到的值"就是"获取到 IP 后设置为固定 IP"的字面实现**：用户不用预先知道地址，命中后照着租约抄。

**必须配套的三件事**（否则这个功能会变成一个坑）：

1. **退出配置项时要还原。** 固化前网卡是 DHCP，离开该网络后应能回到 DHCP。所以 helper 侧必须维护一份 `baseline`（进入前的网卡配置快照）。
2. **"会断开自己"的风险。** 改的如果正是当前在用的那块网卡，配置一落就是一秒级的断网。所以必须有**回滚窗口**：落盘后 N 秒内若失联（探活不到网关），自动回滚到 baseline。
3. **UI 上要有"交还系统"。** 一个已经固化的配置项，用户在配置窗体里要能看到「当前：静态 192.168.11.5（由 DHCP 固化）」并一键回到 DHCP——就是 §4.7 二的 `[交还系统]`。

> ⚠️ **工程后果**：现状 helper 只有 `route.sync` 一个作用域。本需求新增「网卡配置」作用域 + `baseline` 快照 + 回滚窗口。
> **helper 的 schema / version 必须与 app 同步升级**——按你既有的纪律，二者不同步时 helper 会拒绝整份意图。

> **◷ 落地进度（2026-09-18，第 8 步）**：上面三件**全部已实装**（`capabilities/helper/routeops.py`
> ＋ `plugins/route_guard/{intent,plugin,settings}.py`；`HELPER_VERSION` 2.11.2 → 2.12.0、
> `INTENT_VERSION` 2 → 3）。与设计的三处偏差／补充，口径真源在代码注释里，此处只列结论：
> ① 回滚窗口取 **20s**、且加一个 **3s 宽限期**——刚 `setmanual` 完地址还没落定，立刻探必然「探不到」
> 而误回滚；四条判据**缺一不回滚**（宁可不回滚，也不误回滚）。
> ② 固化后的**运行形态**叫 `dhcp+pin`，与配置层的 `mode` 分开——落到系统上 `static` 与 `dhcp+pin`
> 都是「切 Manual ＋ 写死地址」，差别只在它从哪来；配置层多一个 `mode` 会让用户以为有两种静态地址。
> ③ 本表没写、但落地必须补的一条：**网关不在本网段 ⇒ 落笔之前拒绝**。这种坏法回滚窗口**探不到**
>（地址确实在网卡上、默认路由看着也正常），探不到就只能在写之前拦住。另：`baseline` **只留最早那份**，
> 否则「交还系统」交还回去的是我们自己写过的值。完整决策表与判据见。

> **◷ 落地进度（2026-09-18，「照抄租约」）**：用户问「固化租约里网关 / DNS 留空代表不固化，
> 要固化 DHCP 的结果怎么配」——答案是上面那两个显式布尔键（`HELPER_VERSION` 2.13.0 → **2.14.0**、
> `INTENT_VERSION` 3 → **4**）。同日还更正了本节原先的一句错话（「留空 = 继续跟随 DHCP」）。
> 界面落点在配置窗体的「固化租约」两行：各一枚「照抄 DHCP」勾选，勾上即清空并置灰该行输入框
>（两者互斥，留着旧值等于同时给两个答案）。收口记录见。

> **◷ 落地进度（2026-09-19，契约版本真锁）**：本节那句「二者不同步时 helper 会拒绝整份意图」
> 此前**只对形状变化成立** —— `version` 位只是个名字（`validate_routes` 收下就扔，
> `validate_intent` 末尾还反过来盖自己的号），于是「两侧不是同一代」在 root 侧**看不出来**。
> 现在是**真锁**：文件写的版本 ≠ `INTENT_VERSION`（**含缺位**）⇒ 整份拒绝 ＋ 冻结
>（`HELPER_VERSION` 2.14.0 → **2.15.0**，须重装才生效）；检查排在「未知字段」之前，
> 用户先看到的是「契约版本不符 ＋ 两侧各是哪一版」。`hostsops` 早就是这个口径，routes 是补上的那一侧。
> 详见。

> **◷ 落地进度（2026-09-29，命令通道 ＋ 真租约）**：本节第 3 条那个「一键回到 DHCP」此前
> **点不动** —— 它与「没有任何场景要接管时才交还」共用顶层 `handback`，于是被那个**策略前提**
> 挡在门外；而命中判据恰恰是我们自己固化出去的地址（本节 §2.6 的自证循环）⇒ 命中一次永远为真
> ⇒ 命令一直排队，用户看到的就是「点了没用」。
> 现在**命令与策略分家**：顶层新增 `ops`（`INTENT_VERSION` 4 → **5**），命令排在场景判定**之前**、
> 执行且**只执行一次**（按 `seq` 配对回执）、**不受停用影响**（停用的语义是「自动化别再动网卡」，
> 不是「用户也不许动」）；`handback` 退回成纯策略（每轮可重复、幂等）。
> 同版还改掉两处**同源**的病：① 固化时读的「租约」原本是 `read_service_config` —— 那是网卡**此刻**
> 的配置，也就是我们自己上次写下去的那份 ⇒ 永远只抄出同一个地址（真机 IP 冲突的一个来源）；
> 现值走**真租约** `ipconfig getpacket`（`read_lease`），读不到就报错、绝不猜；② 交还与再固化
> 合成**一轮内的原子序列**（`setdhcp` → 等新租约落到网卡 → 用新租约重算并 `setmanual`），
> 中间不留一条「没人负责」的窗口。收口记录见。

## 2.6 手动 IP 场景：它**不能**参与自动匹配

（2026-09-13 新增。起因：你指出"如果某个场景是手动 IP，自动化无论如何都无法命中"）

**你的观察是对的，而且它不是缺陷，是必然。** 根因是判定依据与写入字段重叠：

| 判定读什么 | 谁提供的 | 组件会不会写 |
|---|---|---|
| `iface_up(iface)` → 网卡是否在线 | `routeops.py:317` | ❌ 不写 ← **唯一安全** |
| `current_gateways(iface)` → 网卡上的默认网关 | `routeops.py:331`（静态 IP 下走 `route -n get default`） | ✅ **会写**（`net.mode: static` 的 `gateway`） |
| `match.subnet` 判定 → 网卡上的 IP 落在网段内 | 新增 | ✅ **会写**（`net.mode: static` 的 `ip`） |

> **判定依据 ∩ 组件可写字段 ≠ ∅ ⟹ 自证循环。**

后果三条：
1. 判成真的那一刻起**永远为真**（IP / 网关是它自己写的）；
2. 若组件写的 IP 不在 `match.subnet` 内 → 每轮 **5 秒**（`intent.py:52` 的 `PROBE_INTERVAL`）在「命中 → 写 IP → 不再命中 → 回滚 DHCP → 又命中」之间抖；
3. 离开该网络也**退不回来**（路由表里的静态默认网关还在，判定继续为真）。

**建议方案 S1**：手动 IP 场景标 `manual_only: true`，**退出自动匹配，只能手动切**。

配置项结构补一个字段：

```
配置项 Profile
├── name
├── ifaces          监控网卡列表
├── manual_only     bool  缺省 false。true = 不参与自动匹配，只能手动指定
├── match           仅当 manual_only = false 时有效
├── net             网络配置
└── routes          路由规则列表
```

**配置窗体行为**：勾上 `manual_only`（文案「仅手动使用（不参与自动匹配）」）后，**「生效网段」输入框置灰**，并直接说明原因——"该场景会写入网卡 IP，用它做判定会自证"。

**DHCP 场景不受影响**：`mode: dhcp` 且不写 `pin` 的场景不写 IP，判定是安全的，自动匹配照旧。

**顺带的硬结论**：手动场景**无法自动触达** ⟹ **面板上必须有选场景的入口**。§4.5 / §4.6 的"徽标只读"因此**反转**（裁决 10 已改判）。

**备选（2026-09-13 已选 S1）**：

| 方案 | 含义 | 代价 |
|---|---|---|
| **S1（已采纳）** | `manual_only`，退出自动匹配 | 需要面板选场景入口 |
| S2 | 改用"组件不写的线索"做判定（如**另一块**网卡的网段） | 哪些线索安全要逐个论证，语义变复杂 |
| S3 | 保留匹配 + 锁存（生效后不再重评，直到用户切走） | 等于运行期的 S1，但多一个需要向用户解释的状态 |

# 三、状态设计
