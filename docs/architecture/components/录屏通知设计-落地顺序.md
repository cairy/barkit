#### ★ 未安装 OpenDisplay ⟹ **永久静音**

这是你规则字面的必然结果（"其余情况都是静音"），但它有一个**你可能没料到的后果**：

| 场景 | 结果 |
|---|---|
| 用户启用本组件，但**从未安装 OpenDisplay** | `S1` 恒假 ⟹ `allow=False` ⟹ `dndMirrored=True` ⟹ **通知永远静音，直到卸载本组件** |

**两个候选**：

| | A（保持字面，★建议） | B（"未安装"视为不适用） |
|---|---|---|
| 行为 | 静音 | 不静音（组件不接管） |
| 理由 | 组件的前提本就是"有第二屏可管"；且面板会**明写**"未安装 OpenDisplay · 通知已静音"，可见、可解 —— 这正是"状态可见"的价值 | 避免"装了 BarKit 反而通知全静了"这种会被骂的场景 |
| 代价 | 用户若"装了组件又不装 OpenDisplay"，会被一直静音（但**面板上看得见**） | 组件在"未安装"时完全空转，与"装了就该有用"的直觉冲突 |

**我的建议：A（保持字面）**。因为 B 会让"未安装"成为一个**静默的空转态**，而 A 至少把后果**显示出来了**——这与本文通篇的"要让状态可见"一致。**但这是需要你点头的一条**，因为它涉及"用户会不会觉得被坑"。

我原来的理由是"录屏时静音，但我的截图工具不算"。**这个理由站不住**：`rules` 是**"勾选哪些进程算录屏"**的白名单（`signals.py:166-167`，命中即算），**"不勾它"本身就是排除**。

## 已实现现状（2026-08 落地，as-built 基线）

> 本节记录本重设计提案定稿前的**原始 notify_guard 已实现形态**，作为"现状基线"。
> 核心决策规则（`allow = S1 AND NOT S2`）与 backend 路径在本重设计后仍沿用；UI/状态机部分由本文前述设计取代。来源：`方案文档.md` §4.2（2026-09-15 文档重构时并入）。

### 决策规则（已定案）

```
信号：
  S1 = OpenDisplay 虚拟显示器在运行（仅 extend 模式，mirror 模式一期不做）
  S2 = 任一规则命中（规则统一为进程存在性检测，任一命中即算）

决策：allow = S1 AND (NOT S2)
  True → 允许通知（dndMirrored=False）
  False → 静音通知（dndMirrored=True）
```

注：`dndMirrored` 仅在系统处于镜像/共享状态时实际生效，轮询提前写对即可，无需卡时机。

### 信号源

| 信号 | 检测方式 |
| --- | --- |
| S1 虚拟显示器 | `system_profiler` 找 OpenDisplay vendor/product 指纹，前置 `CGDisplayIsBuiltin` 预检 |
| S2 规则 | 统一为进程存在性检测，规则列表放 YAML（飞书 Iron、录屏软件名单等均为其中一条），`reason` 字段供面板原因文案 |

### 执行细节

- 手动切换 = 一次性覆盖：点击立即生效并持续保持；当信号组合下一次变化自动逻辑重新接管。
- 面板区分自动/手动两种状态；手动覆盖态提供"恢复自动"按钮。
- 防抖：连续 2 个轮询周期（3s×2）结果一致才写入，避免反复重启 `usernoted`。
- 写开关以 `screen_capture_guard.py` 为准（`defaults write -data` 走 cfprefsd IPC + `kickstart usernoted`），隔离成可替换 backend；不用 `notification_guard.py` 的 `killall cfprefsd`。
- 进程检测：每轮 tick 只取一次 `ps` 快照，多条规则在内存里匹配。
- 硬约束：全 app 只有这一个决策者写 `dndMirrored`。

### macOS 15 回归验证结论（2026-08 实测）

`defaults write -data`（cfprefsd IPC）仍有效（写后读回正确）；但 `launchctl kickstart -k gui/$UID/com.apple.usernoted` 被 SIP 拒绝（error 150）→ backend 顺序尝试 kickstart → `killall usernoted`（launchd 自动拉活，实测可用），行为变化只改 backend.py 单点。

### 飞书诊断结论（2026-08）

- "真在共享屏幕"的信号不存在：共享期间无新进程/连接/socket，CPU 涨幅仅 ~6% 属噪声；屏幕捕获走 ScreenCaptureKit mach 通道，lsof 不可见。
- "参会中"信号干净可靠：`Lark Helper (Iron)` 进程随会议出现/消失（二值、生命周期同步）。
- 飞书规则定案：存在 `Lark Helper (Iron)` 进程 → 视为录屏风险源。已知代价：开会但未共享时也静音（保守取向，可接受）。
- 配置结构定案：专属信号不存在后，飞书规则与录屏软件名单检测机制已无差异，统一收敛为 `rules` 列表（每条 = name + reason + processes）。

### 配置段（示意）

```yaml
plugins:
  notify_guard:
  enabled: true
  poll: 3
  debounce: 2
  rules:
  - name: lark
  reason: 飞书会议中
  processes: ["Lark Helper (Iron)"]
  - name: screencast
  reason: 录屏软件运行中
  processes: [OBS, Kap, zoom.us]
```
