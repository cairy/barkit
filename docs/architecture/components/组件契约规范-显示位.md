## 2.4 显示位：我出现在哪里

组件可以出现在四个地方，**其中三处由你声明什么决定**；组件列表那一处**恒有**：

| 显示位 | 靠什么声明 |
|---|---|
| 标题栏图标条 | `ComponentSpec`（每组件一枚）且 `in_header=True`（默认）—— **前提：你有状态机**（见下） |
| 组件列表（面板行） | **恒有一行，不必声明** —— 行是组件在面板上的**落脚点**；`row_specs()` 只决定它长什么样 |
| 底部快捷按钮 | `ActionSpec`，或 `DetailEntrySpec`（声明入口即同时接管整行与快捷按钮，见下） |
| 托盘角标 | `StateSpec.icon` ＋ 该取值标了 `alerts`（挑选规则多，单独见 2.5） |

**「声明了什么就出现在哪」有个前提：那处的画材你得真能提供。**

| 那一处画的是 | 你得先有 | 没有会怎样 |
|---|---|---|
| 标题栏：**代表态的取值图标 ＋ 级别色** | 状态机 | 永远同一枚身份图标、永远中性灰、悬停只说组件名 —— 说不出任何事，白占一格。**故没有状态机的组件不声明标题栏** |
| 默认渲染的行：**代表态级别**（角标 ＋ 颜色）＋ 那句副标题 | 状态机 | 框架的「无状态机」分支会把副标题**清空**（连行级 `subtitle` 回调求出来的那句也一起清），你得到一行永远空的副标题 |
| 默认渲染的行：**主位那格画身份图标** | `ComponentSpec` | 那个图标位回落一枚**齿轮占位**（`IconName.GEAR`）—— 认得出来「这是个组件」，但说不出是谁 |

**身份 ≠ 标题栏那一格。** 这两件事此前被绑成一体，于是「按需型、无状态机」的组件陷入
死锁：声明身份 ⇒ 标题栏多一格恒灰图标（上面第一行说不许）；不声明 ⇒ 行主位是空框（下面
第三行）。结果这类组件只能用 `custom` 自绘行绕开。**`ComponentSpec.in_header=False` 把它
们拆开**：有身份（行主位图标、组件名都取它），但不占标题栏那一格。

**自绘的行不受前两条约束**：`StatusRowSpec.custom` 是你自己画整行，框架不往上叠级别与文案。
门禁 `test_display_slot_declarations_need_a_state_machine` 抓的是上面三类「声明了却画不出」
——无状态机但**没声明 `subtitle`** 的行不算缺口（图标 ＋ 名称 ＋ 行内控件就是它的全部，
框架有专门的「无状态机」分支渲染它）。

> **◷ 2026-09-20**：autotype 已不再走自绘行（行内下拉由第四种行内控件 `ChoiceSpec` 表达后
> 收归声明式），并以 `ComponentSpec(icon=…, in_header=False)` 声明身份：行有图标、标题栏
> 不出现。本节的死锁即由此解开。

> **◷ 2026-09-17**：本节原写「组件可以出现在三个地方」，列的是面板内的三处（标题栏 / 列表行 /
> 底部快捷按钮）；而下方「用户层的字段」表列的是标题栏 / 列表行 / **托盘角标** —— 两张表用着
> **不同的三个元素**，读者无从判断到底有几处、哪处能关。现统一为四个**出现位置**（面板内三处
> ＋ 菜单栏一处），用户层也就跟着能关四处。
>
> **别把这里的「四」与 D16 的「三处显示位」混起来**：那一处说的是**状态**画在哪 —— 标题栏图标 /
> 列表行角标 / 托盘角标，三处同色；底部快捷按钮是**入口**、不画状态，故不在那三处之列。

**行数与状态机数解绑**：`row_specs()` 返回几行就是几行，**与你有几台状态机无关**。
**一行都不声明 ⇒ 框架合成一行**（名字取 `Plugin.name`、图标回落齿轮、无角标无副标题无行内控件）：
行是落脚点、不是可选贡献，「要不要**额外**东西」才是声明的事。

| 你有几台状态机 | 建议 |
|---|---|
| 1 台 | 1 行。这是绝大多数组件 |
| 多台，但用户只需要一个结论 | **1 行**——多台的信息在副标题里用一句话说完（见 2.7）。`route_guard` 是这类：4 台机，1 行 |
| 多台，且每台都需要各自的控件 / 可点区域 | n 行。**须在 `reason` 里说明为什么面板必须同时看到它们** |

面板不是控制台：**面板行数不该随组件内部复杂度增长**。每加一行都应回答"用户在这一行上要做的决定，别的行能不能替"。
行与状态机之间**没有机制上的绑定**——同名 `key` 只是可选的命名约定，方便人读。

**整行点击的落点：`on_click` 优先，其次是详情页。**

| 优先级 | 声明 | 干什么 | 例子 |
|---|---|---|---|
| 1 | `StatusRowSpec.on_click` | 就地点一下做**一件事**——**可以是唤起外部应用** | 打开 OpenDisplay 窗体 |
| 2 | `DetailEntrySpec` | 打开**框架内**的一个界面看更多 / 改配置 | 打开配置窗体 |

框架实现：`spec.on_click` 非空即执行它，为空时才合成「打开详情页」（`shell/panel.py:803-806`）。
所以**声明了 `on_click` 就等于放弃框架合成的详情入口**——这是优先级决定的，不是 bug。

**声明详情入口 ⇒ 两处入口同时开，而且是同一个过程。** 点整行与点底部快捷按钮触发的是同一条
`detailRequested`、开同一个界面，差别只在用户怎么找到它。两处各受显示位开关（`row` / `action`）
单独管辖：关掉 `action` 只是少一枚按钮，整行照旧可点。

> **◷ 2026-09-22（D36）**：`DetailEntrySpec.trigger` 字段**已删除**（它原让作者二选一：入口长在行上还是长在快捷区域）。**是行为变更** —— 三个原写 `trigger="row"` 的组件现在**也会**多出一枚底部快捷按钮；理由与落点见。

判据一句话：**要不要给用户一个可以停留的地方，而且这个"地方"是本框架提供的？**

| 想做的事 | 落哪 |
|---|---|
| 打开一个**框架内**的界面（面板内嵌 / 独立模态窗） | `detail_entry()`（见 2.8） |
| **唤起外部应用**（打开别的 App 的窗口） | 属**动作**，不属详情页——落 `StatusRowSpec.on_click` / `ActionSpec` / `ButtonSpec` |
| 就地做一件事（不打开任何界面） | `StatusRowSpec.on_click` |

**为什么不把"唤起外部应用"塞进 `detail_entry()`**：`build` 的返回类型是框架托管的 `QWidget`（见 2.8）——
机制上装不下另一个进程的窗口。

（`route_guard` 今天把 `on_click` 接到了「重装 / 诊断」上——「重装」是就地动作，没问题；
「诊断」要打开**框架内**界面，重写时这半改回 `DetailEntrySpec`。）**✅ 2026-09-17 已改回**（`route_guard` 第 7 步：新增 `detail_entry()`，删掉整行 `on_click`；设置页同时撤掉「打开规则配置」——配置项集合归详情页）。

**颜色一律取代表态级别**（见 1.4）：框架从该组件全部状态机里挑最坏的那一个取值，据此上色。
颜色表达的是「这个组件**整体**有多坏」，所以按组件聚合，与「有几台状态机」无关。

托盘角标**怎么挑**（`alerts` ＋ 全局 `tray.min_level` ＋ 级别取胜 ＋ 同级轮播）规则较多，
单独见 2.5；本节只把它当作四个显示位之一，由同一条用户层开关管着。

**显示位的两层控制**：

| 层 | 谁说了算 | 落点 |
|---|---|---|
| 声明层 | 组件作者 | 行**恒有**（不靠声明）；`StatusRowSpec` 只决定这一行**长什么样** |
| 用户层 | 使用者 | 设置窗「插件」页每行最多四枚芯片（只列该组件**真有的**显示位）：`plugins.<id>.ui.<slot>.visible` |

用户层的字段：

| 配置 | 默认 | 效果 |
|---|---|---|
| `plugins.<id>.ui.titlebar.visible` | `true` | 关掉 = 标题栏不出现这枚图标（顺序位保留） |
| `plugins.<id>.ui.row.visible` | `true` | 关掉 = 组件列表不出现这个组件的行。**按组件生效**：声明了多行的组件，整组行一起隐藏（没有「只关第几行」这一档） |
| `plugins.<id>.ui.action.visible` | **`false`** | **打开** = 面板操作区出现这个组件的快捷按钮（◷ 2026-09-22，D37 —— 原默认 `true`）。`ActionSpec` 与 `DetailEntrySpec` 是**同一个位置**（见本节首表），同由这一位管 |
| `plugins.<id>.ui.tray.visible` | `true` | 关掉 = 这个组件**不参与**托盘角标的挑选（最坏的那个也轮不到它） |

> **◷ 2026-09-22（D37）**：**默认值从此逐位不同**（真源 `core/config.py::PLUGIN_UI_SLOT_DEFAULT`）—— 前表三处沿用「声明即出现」，**只有快捷区域默认关**：它是**快捷方式**而非入口（声明了详情入口的组件，行上本来就点得进，见 D36）。摆哪几个由用户自己挑；理由与实测见。

另有一项**全局**配置（不属于任何组件）：`tray.min_level`，默认 `warn`——级别低于此的取值即使标了
`alerts` 也不进托盘（`ERR` 不受此限，见 2.5）。可选值域只有 `warn` / `err` 两档，归契约
（`contribution/specs.py::TRAY_MIN_LEVELS`，读侧 `core/config.py`、写侧 `set_tray_min_level`、
渲染侧 `renderers/badge.py` 读同一份）；**落点**：设置窗 → 「通用」→「菜单栏」→「角标最低级别」，
改回默认档自动删键（默认值不落盘）。

用户层的三条语义：

| 规则 | 说明 |
|---|---|
| 隐藏 ≠ 停用 | 隐藏只影响该显示位的渲染，**不影响状态聚合、轮询与副作用**。要停整个组件请用 `plugins.<id>.enabled` |
| 隐藏保留顺序 | 不删 `plugin_order` 位，重新显示时顺序不变 |
| 允许全隐藏 | 用户可以把四处全关掉，框架不自动回退 |

**落点**：设置窗 → 「插件」页，每个组件一行小芯片（标题栏 / 列表行 / 快捷区域 / 托盘角标，顺序即 `PLUGIN_UI_SLOTS`），
亮 = 显示中、点一下关；只列该组件**真有的**显示位（「列表行」这枚**恒在** —— 行是普适的；
其余三处按声明）。落盘只发生在**偏离该位默认**时（写侧判据是「**等于默认就删键**」，不是「为真就删键」——
默认值逐位不同后这两句话不再等价）：标题栏 / 列表行 / 托盘角标默认可见 ⇒ 关掉写 `false`；
**快捷区域默认关 ⇒ 打开写 `true`**（◷ D37）。改回默认一律删键，不留残渣。
键名只有 `core/config.py` 知道（`plugin_ui_visible()` / `set_plugin_ui_visible()`）。

组件之间的顺序归用户（设置页拖拽 → `config.plugin_order`）；标题栏超过 7 枚图标会自动收进末尾的「+K」。

## 2.5 托盘与模式徽标

两件事，别混。

### 托盘：一枚角标，指向最该关心的那个组件

托盘只有**一枚菜单栏项**，结构固定为「底图 + 右上角一枚角标」：

| 层 | 画什么 |
|---|---|
| 底图 | 应用标识（**可由用户改指某个状态的取值图标**，见本节末）。没有值得提醒的组件时走 template 图，随菜单栏明暗自动单色渲染 |
| 角标 | **最坏那一级里的组件取值图标**（该级有多个时轮播），画在级别色实心圆上 |

角标一次说完三件事：**是谁**（图标）、**什么状态**（图标）、**有多坏**（圆底色）。
没有组件需要提醒时，角标不画，只剩底图。

**怎么挑出「最不健康」**

1. **候选**：用户没关掉托盘显示位的组件（`plugins.<id>.ui.tray.visible`）；
2. **触发**：候选组件的代表态取值标了 `alerts=True`，且级别不低于全局 `tray.min_level`（默认 `warn`）；
3. **取胜**：触发者里级别最坏的**那一个级别**——它是唯一允许上屏的级别；
4. **并列**：只有落在第 3 步选出的那一级里的触发者，才进入轮播队列。级别更轻的触发者被**压制**，
  始终不上屏；等这一级消失（被处理掉或自动降级）后，队列整体换成新的最坏那一级。

作者这样声明「这一格值不值得提醒」：

```python
StateOption(id="muted", level=StateLevel.WARN, icon=IconName.BELL,
  text="通知静音", alerts=True) # 静音生效 → 值得让用户看见
```

省略 `alerts` 时，`WARN` 与 `ERR` 的取值为真，其余为假。

**`ERR` 一律露出**：用户配置只能收紧到 `WARN`，不能屏蔽 `ERR`——「出事一定看得见」
是这条显示位的承诺。

**并列轮播**（最坏那一级里有多个触发者时）

| 规则 | 要求 |
|---|---|
| 队列内容 | **只含最坏那一级的触发者**。级别由上一节第 3 步定死，轮播**不跨级别**——任一时刻队列里只有一个级别，`ERR` 与 `WARN` 永不混排 |
| 顺序 | 队列内按 `plugin_order`（组件顺序）排，同级内**不随机** |
| 启动条件 | **只**在队列长度 ≥2 时启动；掉到 1 个或 0 个立刻停，不留常驻计时器 |
| 间隔 | 固定 3 秒一换 |
| 宽度 | 所有角标字形按同一包围盒绘制，**轮播不改变菜单栏项宽度** |
| 悬停 | 提示跟随当前轮播项：组件名 + 该组件代表态的 `summary` |
| 点击 | 不变：点整枚图标 = 打开面板 |

**角标尺寸与字形**（本节唯一有硬数字的地方）

现有角标直径 11px，里面画的是 9pt 的「!」「静」两个字符。要放进一枚图标，三件事必须一起定：

| 项 | 值 | 为什么 |
|---|---|---|
| 菜单栏画布 | **24×24px** | 现 22px 装不下「底图 + 可读角标」两件事 |
| 角标直径 | **14px**（实心圆，锚右上） | 12 网格的字形在 14px 下笔画约 1.6px，是线性图标可读的下限 |
| 角标字形 | **专用简化字形**：12 网格、笔画 ≥1.6、不超过 3 段 | 24 网格的主字形缩到 14px 会糊；角标与主图标是两套资源 |

角标字形**可以不给**：没提供时框架回落到该级别的通用标记（见 2.3 的五个级别）。

**颜色**：角标底色 = 代表态级别色（`OK` 不画角标）；字形一律白描边。
非 template 图不会自动适配菜单栏明暗，所以底图与中性色按菜单栏**实际**外观取色
（系统外观设置不可信：全屏时菜单栏常是深色浮层而系统仍是浅色）。

**「静」已经下线**：通知静音不再是特殊通道，而是 `notify_guard` 的一个普通取值
（`icon=BELL_OFF` + `alerts=True`）。

### 托盘底图：默认是应用标识，可由用户改指某台状态机

底图默认画 BarKit 的应用标识。**用户可以让它改画某台状态机的取值图标**——这样菜单栏那一格就能替掉
某个外部 App 自己占的图标（典型场景：外部工具在菜单栏占两格，用户想只留 BarKit 这一格）。

**准入判据只有一条：这台状态机在声明里给了主图标。**

| 层 | 谁说了算 | 落点 |
|---|---|---|
| 声明层 | 组件作者 | `StateSpec.icon` 非空 = 这是本状态机的**主图标**，同时构成**被选资格**。没给主图标的永远不出现在配置项里 |
| 用户层 | 使用者 | 设置窗**「通用」页**的下拉；落盘 `tray.base_source` = 该状态机的**身份**（`{组件 id}.{状态机 key}`，如 `battery.main`）；`""` = BarKit 默认底图 |

**为什么准入用「有没有给主图标」而不是一枚 `as_tray_base` 开关**：同一件事写成两个字段，就会出现
「给了图标却没表示愿意」与「表示了愿意却没有图标可画」两种自相矛盾的状态，而**后者根本无法渲染**——
用户选了它，菜单栏那一格没有任何东西可画。准入直接问「你能不能画出一枚图标」，这个矛盾在结构上就不存在。

**取值是状态机身份，不是事件总线地址**：`tray.base_source` **不存** `plugin.<id>.status.<key>`。
指向的是「哪个组件的哪台机」，故配置层不必认识 pub/sub 的命名规则，组件改名 / 改 topic 拼法也不会让
用户已选的来源失效。（首版落的是 topic 形态，读路径会**就地折算**成身份键、不回写。）

取值列表 = `BarKit 默认` ＋ 所有"给了主图标的状态机"（显示为 `组件名 · 状态名`，如「录屏通知 · 第二屏」）。

**回落规则（硬性）**——缺一条就是「菜单栏那一格撒谎 / 消失」：

| 情形 | 结果 |
|---|---|
| 未配置来源 | BarKit 默认底图 |
| 来源状态机**不在册**（组件被禁用 / 卸载） | BarKit 默认底图 |
| 该状态机还没报过状态 / 报告没给取值图标 | 它声明的**主图标** |
| 该状态已失联 | 同上（主图标） |

后三条刻意**不**掉回 BarKit 默认底图：既然有主图标，就该画它。**尤其失联**——继续画上一次的取值图标
（如「实心屏」）才是撒谎；回落主图标既如实、又仍是**该组件**的信息，比换成 BarKit 自己的牌子更少误导。
无论走哪条，那一格都**不得消失、不留空白**。

**配置项必须自述的两句话**：① 选它之后 BarKit 的身份在菜单栏不再可见；② 该状态正常时，你看到的图标
由它决定（不正常时回落它声明的主图标）。

**与角标的关系**：底图与角标是两个独立图层，**换底图不影响角标**——`alerts` 那条"出事一定看得见"的承诺
原样保留。所以**唯一代价是丢掉"这是哪个 App"这一眼**，出厂默认因此是 `""`（不改变所有人的现状），
由用户主动开启。

### 模式徽标

**行内模式徽标**——`StatusRowSpec.mode` 挂一枚（每行一枚），表达运行模式。
**点它会发生什么，两种形态二选一**：

```python
# ① 二元切换：点一下直接切到另一档（「自动 ⇄ 手动」）
ModeBadgeSpec(
  label="自动", # 初始文案
  accent=True, # True = accent 底 + accent 字；False = 灰底灰字
  on_click=self.toggle_mode, # 有它才可点；点击直接切档，不弹窗
  get_state=self._mode_state, # 运行时重读 → (label, accent)
)

# ② 候选列表：点一下展开列表、选中即生效（「现在用哪个场景」）
ModeBadgeSpec(
  label="office", # 初始文案，**兼任当前项**（按 MenuItem.label 匹配）
  accent=True,
  get_items=self._profile_items, # 运行时重读 → tuple[MenuItem, ...]
  get_state=self._mode_state, # 运行时重读 → (label, accent)
)
```

`get_state` 让徽标在每次状态刷新时自动与你的内部状态对齐，**你不需要持有任何 widget 引用**。

`on_click` 与 `items` / `get_items` **互斥**，同时声明在**构造期报错**（`ValueError`）：
有列表时点击就是「展开列表」，「选中某项做什么」写在各自的 `MenuItem.on_click` 上。
**不设优先级**——这是两条不同的路，不是一条路的两种配置：隐式取优先级会让写了
`on_click` 的人以为他那条还会跑。

**`label` 是自由文本，不限于枚举。** 它回答「现在用的是哪一套」，所以可以填运行期数据
（如"当前生效的场景名"）。「自动 / 手动」只是最常见的写法，不是规定。
**候选列表形态下它同时就是"当前项"**：框架拿它匹配 `MenuItem.label` 决定列表里谁打点，
故**不另设 `current` 字段**——徽标上写着谁，谁就是当前项（决议 D33）。

**`on_click` 的语义**是「点击**直接切模式**，不弹窗」。这句里的"弹窗"指**对话窗**（模态对话框、独立窗口）——
**点击弹出模式候选列表不算破例**：列表里选中即生效、不做二次确认，正是"直接切模式"。
候选列表与 `MenuSpec` 同款（见 2.6）：**每项必须带 `hint` 副文案**——只给名字，用户在
"选哪个"的时刻看不出它管什么，等于没有信息；候选集合可来自运行时。

**只有一枚徽标位**：`ModeBadgeSpec` 每行最多一枚。放什么由你定——但判据是
**它是一个"现在是哪一套 / 哪一档"的名词**，不是开关（开关走 `controls`，见 2.6）。
