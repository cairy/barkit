## 6.5 "点击本组件"到底点哪：一处契约争议（要你拍）

你说"点击本组件直接弹出 OpenDisplay 的窗体"。但契约 §2.4 写的是：

> **点整行 = 详情页**：整行点击的落点是 `detail_entry()` 返回的 `DetailEntrySpec`，**不是** `StatusRowSpec.on_click`。
>
> **★ 该条款已于 2026-09-14 修订**（《组件契约决议》**D28**）：实际行为从来是 `on_click` **优先**
> （`shell/panel.py:803-806` 的 docstring 逐字如此），契约已改为**优先级表**并补上「唤起外部应用属**动作**」。
> **本节下方那段"建议澄清契约"已按 D28 落地**，此处保留原条款以存证。

而《网络切换》§5.1 刚把 `route_guard` 用 `on_click` 接"重装/诊断"判为**违规**。看起来本组件要再犯一次。

**但它不是同一个问题。** 关键在于 `DetailEntrySpec` 的机制装不下这件事：

```python
DetailEntrySpec(label=..., build=self._build_detail)   # build 必须返回一个 QWidget
```

`build` **只能返回框架托管的 QWidget**。而"打开 OpenDisplay 窗体"是**唤起另一个进程的窗口**——**机制上装不进去**。

所以建议**澄清契约一句（而不是放宽字段）**：

> **§2.4 补充**：`detail_entry()` 承载的是**框架内**的界面（`build` 返回 `QWidget`）。
> **唤起外部应用**属于**动作**，落点是 `ActionSpec` / `ButtonSpec` / `StatusRowSpec.on_click`——
> 判据从"要不要给用户一个可以停留的地方"细化为"**要停留的地方是不是本框架提供的**"。

**落点分配 —— ★已按你的原话采纳 A（整行开 OpenDisplay）；配置窗体已按 §6.4 改判归设置页**：

| | **A（已采纳）** | B（更正统） |
|---|---|---|
| 整行点击 | **打开 OpenDisplay 窗体**（`on_click`） | 打开本组件规则编辑器（`detail_entry`） |
| 打开 OpenDisplay | 同上（一步） | 规则编辑器里的按钮 / `actions()` 底部按钮（两步） |
| 本组件规则编辑器 | **设置页「录屏通知」页**（§6.4 ★改判；**面板不留入口**） | 整行点击（一步） |
| 优点 | 满足"点击即弹 OpenDisplay"，**这是你要的一步到达** | 契约零争议 |
| 代价 | 需要契约澄清（上面那句） | 规则编辑是"配一次不再动"的低频项，却占了整行这个高频入口 |

**采纳 A 的理由**：规则编辑确实低频（配一次就不再动），把它放在整行点击上是**把低频动作用高频入口承载**；而"OpenDisplay 现在怎么样 / 我要打开它"是每天都发生的事 —— **因为你正要撤掉 OpenDisplay 自己那两格菜单栏图标，BarKit 这一行就成了它唯一的入口，必须一步可达**。B 更守规矩，但规矩用在这里是错配。

**采纳 A 的代价（要认）**：契约 §2.4 需要补那句澄清（"`detail_entry` 只承载**框架内**界面；唤起外部应用属动作"）。这是**扩张契约的适用范围，不是绕开它** —— 已在 §7.2-① 登记。

> **★ 原文档在这里留了一个尾巴，现已消除**：§6.4 原文曾把"配置窗体"排给 `detail_entry(trigger="action")` → 底部快捷按钮，那需要**面板底部工具栏多挂一格**。§6.4 改判后（配置归设置页），**面板不再有任何配置入口**，这一格也就不需要了 —— 与"不加行尾 `›` 提示"（§6.3）同一个指向：**面板只做高频的事**。**◷ 2026-09-22（D36）：`DetailEntrySpec.trigger` 字段本身也已删除**（声明入口即两处同源），本节引用的 `trigger="action"` 写法均为历史存证。

## 6.6 就地在 `notify_guard` 改，不新建组件

一个自然的想法是"新建一个 `opendisplay/` 组件专门管 OpenDisplay"。**不建议**，三条理由：

1. **信号同源**：`S1`（虚拟屏）已经是 `notify_guard` 的决策依据，拆开就得让两个组件各自探测同一件事（重复 `system_profiler`）；或者抽成共享能力——那要为一个组件加一层抽象。
2. **你的目标相反**：你要的是**省菜单栏空间**。多一个组件就多一行面板、多一枚标题栏图标、多一份设置页——**与省空间背道而驰**。
3. **用户心智是一件事**："我在录屏/用第二屏" 是一个场景，不该被切成两个组件。

| # | 缺口 | 本组件是否被卡住 | 建议 |

| ① | **集合型配置的"默认值"载体**：`config_schema()` 是平坦单例表单，却能塞进 `FieldType.LIST` 为一个集合型字段提供默认值（`plugin.py:248`；`test_config.py:148` 正在断言 `rules == []`）。而编辑入口按契约在 `detail_entry().build` —— **默认值在 A 处、编辑器在 B 处**，契约没说这算不算双真源 | **会撞到**：我建议保留 `rules` 字段（只作默认值载体，不作编辑入口），但这句话契约里没写 | 契约补一句：「集合型配置**可以**在 `config_schema()` 里保留字段以承载默认值，但**不得**有渲染器消费它；编辑入口唯一是 `detail_entry().build`」 |
