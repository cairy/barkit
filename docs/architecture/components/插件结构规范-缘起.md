## 0. 为什么需要这份规范

> **字段定义不归本文。** 本文只管「**插件包内部怎么组织**」——文件放哪、模块怎么分、能力怎么选。
> 组件的对外契约（声明方法、Spec 字段、枚举取值、命名规则）一律以 `组件契约规范.md` 为准；
> 本文凡提到 Spec，只借用其名字说明**归属与放置**，不重述字段。

### 0.1 计数口径（先钉死，否则整张表不可复现）

> **真实插件** = `src/barkit/plugins/` 下**不以下划线开头**的直属子包，共 6 个：`autotype` / `hosts_guard` / `ipad_tunnel` / `notify_guard` / `recognize` / `route_guard`。
> `_template` 是脚手架，**不计入「样板频次」**（否则等于把模板本身当成一个抄袭者），但**计入「模板覆盖度」**（§10）。
> 发现器规则见 §2.1——「直属子包 + 入口名 `plugin.py`」不是习惯，是写死在框架里的。

四类问题：

1. **`plugin.py` 是神文件**：`ipad_tunnel` 773 行、`route_guard` 586 行、`hosts_guard` 449 行，同时装着框架钩子、领域决策、UI 构建三样东西。而 `recognize` 的 83 行证明「薄契约面」不是幻想——它把识别逻辑全放在 `recognizer.py` / `window.py`，`plugin.py` 只剩契约与委托。
2. **样板跨插件手抄，且抄得不一致**：`_publish_state` ×4、`_touch_trigger` ×3（逐字相同）、`_load_user_config` ×3（逐字相同）；更糟的是**状态文件读取有 3 套不同命名**（读侧 `_read_state_file`×2 + `_read_state`×1，mtime 侧 `_stat_mtime`×1 + `_state_mtime`×2）。命名分叉说明这些函数是「各写各的」而非「复制粘贴同一份」。
3. **运行期 UI 无家可归**：`recognize/window.py`(671)（**◷ 2026-09-19 改名 `window_view.py`**） + `selview.py`(320)、`autotype/countdown.py`(307)（**◷ 2026-09-19 改名 `countdown_view.py`**）、`hosts_guard/manage_dialog.py`(571)（**◷ 2026-09-19 改名 `manager_view.py`**）是 HUD / 浮层 / 独立窗口，不是设置页。本稿之前的骨架只给了 `settings.py`，这几个文件按规范**没有合法归处**——对包内最大的两个 UI 文件（`window.py` 671 行、`manage_dialog.py` 571 行）失语。
4. **`_template` 失修**：只演示裸 `Plugin` + `_do_action` + `_snapshot` + `_build_settings_page`，不覆盖 `RUN_PERIODIC` / `tick` / `resident_services` / 状态文件读写 / 自动化徽标——而 6 个真实插件里有 4 个是常驻轮询形态。

### 0.3 目标与一条元规则

**目标**：让「一个插件包长什么样」无歧义；契约 / 领域 / UI 三层不串味；样板只写一次。

**元规则**：本规范中任何「N 处重复」「M 个文件受影响」的断言，必须写明**计数口径 + `文件:行` 出处**。第 1 稿的频次表因未声明「是否含 `_template`」而不可复现，直接导致其中三条判据选错了收口对象——这条元规则就是那次教训的产物。

## 1. 适用范围与强制等级

- **适用**：`src/barkit/plugins/<id>/` 下的每一个插件包（含内部与外部插件）。
- **不适用**：框架层（`contribution` / `shell` / `core` / `capabilities`）。它们已分层，本规范不改其分层，只在§6.3、§8 两处指出**框架侧缺失的 API**。
- **强制等级**：

| 标记 | 含义 |
|---|---|
| **硬** | 由 §12 门禁机器强制，违反即 CI 红 |
| **迁移目标** | 存量插件按 §11 分阶段达标；期间由白名单 + reason 显式挂账 |
| **约定** | 人评，无门禁（如命名语义） |

## 2. 标准包骨架

### 2.1 先记住发现器写死的三件事

这三条不是约定，是框架实现，违反就等于插件不存在：

1. **必须是 `barkit.plugins` 的直属子包**——`core/registry.py:67` 用 `pkgutil.iter_modules(pkg.__path__)` 只扫一层，不递归。
2. **入口模块名写死 `plugin.py`，且必须暴露名为 `Plugin` 的类**——`core/registry.py:74-76` `import_module("…plugin")` + `getattr(mod, "Plugin")`。
3. **`_` 前缀的子包不加载**——`core/registry.py:71`。所以模板 / 脚手架**必须**用 `_` 前缀隔离，否则会被当成真插件导入。

### 2.2 六面骨架

```
plugins/<id>/
  __init__.py # 只放 docstring；零 import、零逻辑
  plugin.py # 【契约面】唯二被框架按名调用的文件（另一个是贡献里的工厂）
  <domain>.py # 【领域面】engine / resolver / decider / backend / signals / intent / rules …
  settings.py # 【设置面】经贡献体系渲染的设置 UI（含其子对话框）
  <name>_view.py # 【运行期面】插件自己在业务时刻打开的窗口/浮层/HUD
  state.py # 【可选】持久化状态的读写封装（若插件自己维护状态文件）
  resources/ # 【资产面】A 类二进制 / 种子 / 只读资源（框架部署，勿手改）
  *.md # 【资料面】本插件自带的设计/协议/排障文档
```

### 2.3 目录白名单（硬）

`plugins/<id>/` 内**只允许**四类条目：

| 条目 | 判定 |
|---|---|
| `*.py` | **仅限包根**（唯一子目录是 `resources/`，故子目录内不出现 `.py`） |
| `*.md` | **仅限包根**；每包 ≤3 个；须与包内模块或包本身对应 |
| `resources/` | 唯一允许的子目录（其内部不受本规范约束，见 §3.3） |
| `__pycache__/` | Python 产物，须在 `.gitignore` 内 |

**其余一律不允许**：`.DS_Store`、`*.pyc.*` 残骸、`notes.txt`、随手丢进去的 `.json` 快照、临时脚本、`__init__` 之外的子目录。

> 说明：`.DS_Store` 与 `*.pyc.*` 当前**已被 `.gitignore` 覆盖且未被 git 跟踪**（`git ls-files` 命中 0），所以这条门禁的历史价值有限；它的真实价值是**拦住未来新增的「非代码非资料」文件**。

### 2.4 铁则

- `plugin.py` **必须薄**：只含框架契约方法（§4）+ 动作回调，业务与 UI 一律在别的模块，`plugin.py` 只 import 并接线。
- `__init__.py` **只放 docstring**：不得 import、不得绑定名字、不得放逻辑。反例见 §8.2。
- 领域模块**按职责命名**，禁 `utils` / `common` / `helpers` / `misc`。
- 包内自引用一律用**相对导入**（`from . import engine`）或**直指子模块**（`from barkit.plugins.<id>.engine import foo`）；**禁止经包 `__init__` 转手**（即禁止靠在 `__init__.py` 里 import 子模块来提供名字，见 §8.2）。

## 3. 资产与文档归属

### 3.1 按「归属域」切，不按扩展名切

| 文档描述的对象 | 去处 | 判定依据 |
|---|---|---|
| **单个插件的内部实现**（协议 / 时序 / 字段语义 / 排障 / 设计） | **留包内** `plugins/<id>/*.md` | 改这个插件的人必须先读到；跨版本协议与实现强耦合 |
| **某份资产本身**（放置方式 / 获取来源 / 许可 / 被 root 部署的约束） | **留资产旁** `resources/README.md` | 警示必须在动手现场 |
| **跨插件 / 仓库级**（分层契约、规范、踩坑、Roadmap、任务跟踪） | `docs/` | 不属任何一个插件，无争议 |
| **面向最终用户** | 仓库根 `README.md` 或 `docs/` | 与实现不同生命周期 |

仓库里已有此范式的正确样本：`example/README.md` 就地放在 `example/`，用「本目录…**不参与打包与运行**」自我隔离——**用打包/发现规则隔离，不用搬文件隔离**。

### 3.2 为什么不是「包内禁 `.md`」

第 1 稿的 §2 写了「设计文档一律放 `docs/`，禁止留在包内」，并以「包体」为理由。经实测，这个理由在量级上不成立：

- 构建出的 `barkit-0.1.0-py3-none-any.whl` 共 521 KB，其中非 `.py` 项**只有 5 个**：`dist-info/*`（必须）、两个 `.md`（46 KB）、`resources/README.md`（4.9 KB）、`resources/hev-socks5-tunnel`（**316 KB，占 60.6%**）。移走全部 `.md` 只省 9.6%，而留下的那个大件占六成。
- 真要 wheel 不含文档，`pyproject.toml` 加一行 `exclude = ["**/*.md"]` 即可——**这是构建配置问题，拿它推架构规则是范畴错误。**
- 包内真正的垃圾（`.DS_Store`、`*.pyc.*`）实测**都没进 wheel**，hatchling 默认已排除。也就是说「包内只装运行时代码」这句自我描述**今天就已经成立**。

而「留包内」在本仓库**已有既存决议**——`ipad_tunnel/design.md:4-5` 逐字写着：

> 位置：本文件随插件代码同目录存放（`plugins/ipad_tunnel/design.md`），**便于插件整体迁移 / 改造 / 删除时自洽，不依赖仓库 `docs/design/` 的悬空引用。**

插件是可插拔单元，文档是它的一部分。第 1 稿把它反过来，既没引用这条既存决议也没反驳它。

### 3.3 `resources/`：唯一禁区，任何情况下不挪

`resources/` 不是「素材目录」，它是**框架的 A 类二进制部署源**，位置被写死在框架里：

- `core/rootbin_reconcile.py:37` `RESOURCES_DIRNAME = "resources"`；
- `:98` `src = base / RESOURCES_DIRNAME / name`，其中 `base` = **声明该资产的插件的包目录**（`:68`）；
- 源缺失时 `resolve_sources` 返回非空缺失原因，**安装器遇到缺失即拒绝安装**。

所以把 `resources/` 挪出插件包，后果不是「文档归类」，而是 `ipad_tunnel` 装不上、守护拿不到 `hev-socks5-tunnel`。§2.3 的白名单允许 `resources/`，§3.1 又要求 `resources/README.md` 留原地，两者一致。

`resources/README.md` 是**该目录自身的操作契约**（写明唯一分发位、`cp` + `chmod 0755` 的落位、哈希不符即拒绝安装绝不静默降级、这里的文件会被 root 部署执行、以及「缺失不阻断安装 → helper 去用户域找二进制」那段本地提权面历史）。它在全仓**零外部引用**——这恰恰证明它的价值在**位置**而不在内容。删掉它等于把现场警示撤走。

### 3.4 若将来要挪：代价清单

`design.md` 现有 **12 处引用、横跨 9 个文件**，其中 1 处跨层：

| 层 | 位置 |
|---|---|
| L5 包内 | `plugin.py:1`、`tunnel_spec.py:3`、`config_dialog.py:1`、`config_dialog.py:6`、`bridge.py:13`、`__init__.py:4`、`design.md:4`（自述路径）、`hev-tunnel.md:3` |
| **L2 能力层** | `capabilities/helper/tunnelops.py:35`、`:1013` |
| 仓库级文档 | `../主框架架构.md:1413`、 |

**结论：本稿决定 `design.md` / `hev-tunnel.md` 原地不动。** 若将来要改，那是一次独立原子步（12 处引用须同批更新，否则注释开始撒谎），不是「顺手项」。

## 4. 职责边界（硬规则）

| 面 | 文件 | 允许 | 禁止 |
|---|---|---|---|
| **契约面** | `plugin.py` | 框架钩子；构造并返回 Spec / `StateReport`；委托领域模块；动作回调 | **import PySide6**；领域决策逻辑；构建 widget |
| **领域面** | `<domain>.py` | 取 config + ctx，做决策 / 解析 / 匹配 / 同步，返回数据或报告 | 构建 widget；直接读写用户配置文件（须经插件方法或 §6.3 的框架 API） |
| **设置面** | `settings.py` | 构建经贡献体系声明的托管界面（设置页 + 详情页 / 配置窗体 + 其子对话框），经**插件实例方法**读写配置 | 持有业务状态；绕过插件直接改 config |
| **运行期面** | `<name>_view.py` | 构建业务时刻打开的窗口 / 浮层，数据由插件方法注入 | 私有线程 / 时钟 / 文件监视（§7.4） |

**跨面禁令**：

1. `plugin.py` 内**不得出现任何 `PySide6` import**（含函数内惰性 import——AST 可判）。UI 构建一律在 `settings.py` / 运行期 UI 模块。
2. 除 `plugin.py` 外，任何模块**不得**重写框架契约方法——**方法名清单以《组件契约规范》§1.3「声明点 ⇄ 方法」表为唯一真源**。本文不复述该清单：同一份清单存在两处，就是漂移的成因（审计 A4）；删掉复述后，「漂移」在结构上不可能发生。
3. **UI 一律不直接读写 config 文件**（`ctx.config.user_path` 及其 `read_text` / `yaml.safe_load` / `save_user`），须经插件方法。实测当时**三处配置对话框全部违规**：`route_guard/config_dialog.py:138,148,157`、`ipad_tunnel/config_dialog.py:55,155,179`、`autotype/config_dialog.py:153,165,173`。**◷ 2026-09-19：三份文件已全部删除**（分别于 2026-09-17 / 09-18 / 09-19 随各自设置面收归，见《插件结构规范-UI面》§7.2）；该禁令现由门禁 `tests/test_architecture.py::test_no_config_io_in_ui`（AST、零白名单）扫 UI 文件守住。同类问题还有 UI 直读**状态文件**：`hosts_guard/manage_dialog.py:202`（**◷ 2026-09-19 该模块已改名 `manager_view.py`**）直接 `json.loads(paths.HOSTS_STATE_FILE.read_text(...))`（同批改为经 `plugin.status_index()`）。
