# 一、认识组件

## 1.1 术语：先认五个名字

| 名字 | 读作 | 是什么 |
|---|---|---|
| `ComponentSpec` | 组件 | 一个组件的**身份**：名字 + 身份图标。**一个组件一枚** |
| `StateSpec` | 状态 | 一个会变的东西（「隧道」「电量」）。**一台状态机** |
| `StateOption` | 状态取值 | 状态机的一个可能取值（「已连接」「电量低」）。**自带级别与图标** |
| `StateLevel` | 状态级别 | 严重程度，5 个值：`OK` / `IDLE` / `OFF` / `WARN` / `ERR` |
| `StateReport` | 状态报告 | 运行期的一次上报：**我现在处于哪个取值**，外加动态文案 |

串起来读一遍：

> 组件声明若干**状态**（`StateSpec`），每个状态枚举它全部的**取值**（`StateOption`），
> 每个取值带一个**级别**（`StateLevel`）；运行期组件回报当前处于哪个取值（`StateReport`），
> 框架据此配色、挑代表态、刷新副标题。

「状态」在中文里既能指「一台状态机」也能指「它当前的取值」。本文一律按上表区分：
**状态 = 状态机，取值 = 它当前在哪一格。**

## 1.2 组件是什么

一个组件 = `src/barkit/plugins/<id>/` 下的一个子包，其中 `plugin.py` 暴露一个 `Plugin` 子类。

框架用 `pkgutil` 扫描 `barkit.plugins` 的每个子包（`_` 前缀的跳过），自动发现并加载。**你不需要注册任何东西**——新建一个子包就等于新增一个组件。

```python
# src/barkit/plugins/my_component/plugin.py   （同目录还要有一个空的 __init__.py）
from barkit.core.plugin import RUN_ON_DEMAND, Plugin


class Plugin(Plugin):
    id = "my_component"       # 唯一标识
    name = "我的组件"           # 人读名
    version = "1.0.0"         # 组件自身版本
    run_mode = RUN_ON_DEMAND  # 按需触发，不做周期轮询
    api_version = 3           # 契约版本
```

## 1.3 你声明 / 框架负责

组件只提供两份东西，其余全部由框架负责：

| 你提供的 | 写在哪 | 作用 |
|---|---|---|
| **声明**：我有哪些状态、图标、控件、按钮 | 覆写**声明方法**（`state_specs()` / `component()` / `row_specs()` …），各自返回对应的 Spec | 框架据此在三个位置渲染出你的组件 |
| **报告**：我现在处于哪个取值、什么文案 | `tick()` 返回一个 `StateReport` | 框架据此刷新角标颜色与副标题 |

框架负责的事：

| 框架负责 |
|---|
| 什么时候画、画在标题栏还是组件列表、圆角多少、用什么颜色 |
| 三处显示位的顺序；标题栏图标超过 7 枚时自动收进末尾的「+K」 |
| `tick()` 跑在哪个线程、多久跑一次、连续失败后是否熔断 |
| 报告广播、界面刷新、浅色 / 深色主题切换重绘 |

数据流只有两条：

```
你的声明方法        ──声明──▶ 贡献注册中心 ──▶ 标题栏图标条 / 组件列表行 / 底部快捷按钮
你的 tick()        ──报告──▶ 框架自动广播  ──▶ 各显示位的颜色 / 行的副标题 / 托盘图标
```

贯穿全文的核心切分线：**声明只放静态内容，报告只放动态数值**。
声明在加载、改配置、启停时重建；报告每一轮 tick 都是新的。

**声明点 ⇄ 方法**：一个声明点一个方法，各自带明确的返回类型与基数。

| 声明点 | 覆写的方法 | 返回类型 | 基数 | 详见 |
|---|---|---|---|---|
| 身份图标 | `component()` | `ComponentSpec \| None` | 0/1 | 3.3 |
| 状态机 | `state_specs()` | `tuple[StateSpec, ...]` | n | 2.2 |
| 列表行 | `row_specs()` | `tuple[StatusRowSpec, ...]` | n（不声明也有 1 行） | 2.6 |
| 详情页入口 | `detail_entry()` | `DetailEntrySpec \| None` | 0/1 | 2.8 |
| 设置页 | `settings_page()` | `SettingsPageSpec \| None` | 0/1 | 2.8 |
| 操作按钮 | `actions()` | `tuple[ActionSpec, ...]` | n | 2.9 |
| 全局热键 | `hotkeys()` | `tuple[HotkeySpec, ...]` | n | 2.9 |
| 配置表单 | `config_schema()` | `FormSchema` | 1 | — |
| 外部资源 | `resources()` | `PluginResources` | 1 | — |
| 长驻服务 | `resident_services()` | `tuple[ResidentService, ...]` | n | — |
| 领域订阅 | `subjects()` | `tuple[str, ...]`（**领域名**，不是文件路径） | n | — |
| 期望态领域 | `intent_subject()` | `str`（空串 ＝ 不声明） | 1 | — |
| 系统事件 | `event_topics()` | `tuple[str, ...]` | n | — |
| 诊断文本 | `diagnostics_text()` | `str \| None` | 0/1 | — |

前七行是**贡献点**（产出 Spec，框架据此渲染界面）；其余是**非 UI 声明**（框架拿去做托管 / 订阅 / 诊断，不画界面）。方法名与基数的机器可读真源是 `contribution/points.py::declaration_points()`（它只收录前七个贡献点）。

**没有「header chip」这个声明点** —— `ChipSpec` 已随声明式 UI 重构删除；`points.py` 里只剩 `POINT_MENU_ITEM` 常量、未进 `declaration_points()`。想在标题栏占一格，今天只有 `component()` 一条路。**能力（`capabilities/`）也不是声明点**，是可选的能力基类，靠继承获得，见《组件开发指南》§3.6。

**订阅的事实怎么到手**：框架把 `subjects()` 交给会话（订阅即立刻推一份当前的），推送到达时转交
`on_observed(subject, observed)`；组件要读最新那份调 `observed(subject, default)`。
**没有「监视哪个文件」这个声明点了** —— 事实是推来的，不落盘也不读盘。

五条规则：

| 规则 | 说明 |
|---|---|
| **默认实现** | 每个方法在基类都有默认值（空元组 / `None` / 空 schema）——**只覆写你有的声明点**，其余不用管 |
| **`plugin_id` 由框架注入** | Spec 的身份字段由框架在收集时填，组件**一个字都不写** |
| **`key` 只在同一声明点内唯一** | `Plugin.id` 唯一标识**组件**；`key` 区分的是**同一个声明点里的多条贡献**（多台状态机、多行、多个按钮）。全局身份 = `f"{id}.{key or 'default'}"`。**跨声明点同名是正常写法**：状态机和它的行都可以叫 `"main"`，`ActionSpec` 与 `HotkeySpec` 可以都叫 `"recognize"`。同一声明点只有一条时 `key` 可省略；同一 (组件, 声明点, `key`) 撞名在收集期报错 |
| **拼错即失败** | 返回类型不符 / 元素不是该声明点的 Spec / 违反基数（如两枚身份图标）→ 收集期报错并隔离该组件，**不静默丢弃** |
| **静态且幂等** | 方法必须廉价、无副作用，且同一实例上反复调用返回等价内容（框架在加载、改配置、启停时会重新收集） |

**为什么需要 `key`（而不只是组件 ID）**

`Plugin.id` 回答「**这是谁的东西**」，`key` 回答「**是他的哪一件事**」。组件与条目是**一对多**的：
一个组件可以同时管两台状态机（隧道 + DNS）、挂两个按钮、包两个热键。这时所有条目的归属完全相同，
只有名字能把它们分开——就像学号能指认是哪个学生，但指认不了「他的第几门课」。

为什么必须是**名字**，不能是序号或对象身份：声明是会增删的。序号在增删时会整体位移，框架会把新的一批
「第 2 条」错认成上一轮的另一个人，复用出来的控件就串了行（开关的勾选态、输入框里的半截文字跑到别的行上）；
对象身份更不可靠——声明每次重新收集都会重新构造。名字是唯一跨刷新稳定的锚，
**有了它，「重新声明」才不等于「重新创建」**。这是声明式 UI 的第一性问题，React 的 `key`、SwiftUI 的
`Identifiable` 都是同一个东西。

为什么唯一性只要求「同一声明点内」：约束的范围不该超过机制真正需要的范围。行池与状态池互不相干，
同名不构成冲突；强行要求全局唯一，只会逼出 `"main_row"` / `"main_state"` 这种别名，
把同一个业务概念拆成两个名字，反而更难维护。

这两份东西在运行期如何汇成一条线，见下一节。

## 1.4 状态流：三处显示位

组件的状态在运行期是**单点更新**的：只有一处写入、一处聚合、一处分发。

```
你：tick() 返回 StateReport
      │  唯一写入点
      ▼
框架：按 plugin_id 聚合出「代表态」（取全部状态机里最坏的那一个取值）
      │  唯一聚合点
      ▼
框架：一次算出代表态的取值、级别与文案
      │  唯一分发点
      ├──▶ 标题栏：图标 = 取值图标，颜色 = 级别色，无角标
      ├──▶ 列表行：图标 = 组件图标，角标 = 取值图标且染级别色
      ├──▶ 列表副标题：行的 subtitle 计算（未声明时回退代表态 summary）
      └──▶ 托盘：角标位一枚取值图标（最坏那一级里的组件），染其级别色
```

三处显示位都在框架的**同一个函数**里算出来（`shell/panel.py` 的 `_recompute_plugin`），
所以它们永远同源。你不需要分别设置：

| 显示位 | 图标 | 颜色 |
|---|---|---|
| 标题栏 | **取值图标**（什么状态） | 级别色**染在图标上** |
| 列表行 | 主位 **组件图标**（是谁） + 角标 **取值图标**（什么状态） | 级别色**染在角标上** |
| 列表行 · 副标题 | — | 文案 = **该行的 `subtitle` 计算**（见 2.7）；未声明时回退代表态的 `summary` |
| 托盘 | 角标位一枚 **取值图标**（最坏那一级里的组件，该级并列时轮播） | 级别色**染在角标上** |

**悬停提示不是第四个显示位**——它就是列表行那一句，逐字相同（决议 D18）：标题栏图标的悬停提示
=「组件名：副标题」，**不逐台枚举状态机**（枚举是第二条文案路径，与列表行必然对不上）。

**图标有两个来源，各司其职**：

| 图标 | 声明在哪 | 是什么 | 出现在 |
|---|---|---|---|
| **组件图标** | `ComponentSpec.icon` | 组件身份，**不随状态变** | 列表行主位 |
| **取值图标** | `StateOption.icon` | 当前状态，**随取值变** | 标题栏、列表行角标、托盘 |

取值图标省略时取组件图标（`StateOption.icon` 不填 → 用 `ComponentSpec.icon`）。

**托盘底图默认画应用标识，但可以由用户改指某台状态机**（可选能力，见 2.5）：状态机在 `StateSpec` 上
**给了主图标**（`icon` 非空）即取得被选资格；用户在设置窗「通用」页把 `tray.base_source` 指向该状态机的
**身份**（`{组件 id}.{状态机 key}`）之后，菜单栏那一格就改画它的**取值图标**（随取值变）。没给主图标的
永远不出现在配置项里；该状态还没报过状态、报告没给取值图标或它已失联时**回落它声明的主图标**；
只有该组件被禁用 / 卸载才回落默认底图。

**颜色只有一个来源**：代表态的级别。三处显示位取的是同一份级别，所以永远同色。

**颜色聚合，文案不聚合。** 这两件事回答的问题不同，所以取数方式也不同：

| | 回答 | 取数 | 为什么不能反过来 |
|---|---|---|---|
| 颜色 | 这个组件**整体**有多坏 | **聚合**：代表态级别（最坏那台状态机） | 若按单台状态机上色，三处显示位会各说各话 |
| 副标题 | **现在是什么** | **不聚合**：由**该行**自己算（`subtitle`，见 2.7） | 多台状态机时"最坏那台"的文案未必是最该看的那句 |

只在单状态机的组件上，两者碰巧可以共用一份取值——所以这条差别此前被掩盖了。

**三处显示位为什么画法不同**：

| 问 | 答 |
|---|---|
| 为什么标题栏不画角标？ | 标题栏是 30px 方块、一行最多 7 枚。外框 + 角标在这么小的面积里互相挤压；把级别色直接染在图标上，一枚图标同时表达了「是什么状态」与「有多坏」 |
| 标题栏「一切正常」时是什么颜色？ | **绿**。「颜色 = 级别色」按字面执行：`OK` 也有自己的级别色（`design/levels.LEVEL_COLOR`），不另设「正常就中性」的例外——多一条配色口径就多一处要对齐的地方。列表行角标仍守「ok 隐」（健康不抢眼），两者不冲突 |
| 为什么列表行又画角标？ | 列表行有图标盒 + 整行宽度，有空间把「是谁」（主位图标）与「什么状态」（角标）分开画，信息量最大 |
| **没有状态机的组件**，标题栏那格怎么办？ | **不声明它**（◷ 2026-09-17）。那格画的正是代表态的取值图标 ＋ 级别色，没有状态机就没有代表态 —— 声明出去只会永远画同一枚身份图标、永远中性灰、悬停只说组件名，白占一格（可见上限 7）。按需型组件（识别、一键输入）因此不声明标题栏，入口是快捷区域按钮与热键。同类前提见《显示位》§2.4 的那张「你得先有什么」表 |
| 为什么托盘只画一个组件的图标？ | 菜单栏宽度是公共资源，一次放得下（也应该只放）一枚。画「最不健康的那一个」正好回答最重要的问题——**现在最该关心谁**；同一级别并列时才轮播，不丢信息 |

**代表态** = 该组件全部状态机里**当前最坏**的那一个取值；严重度相同时取**先声明**的那台
（声明顺序就是组件作者写的**关注度顺序**——想把哪台机优先显示，就把它写在最前）。
同一个状态机的多个取值是互斥的，所以平局只可能出现在「多台状态机」的组件上。

**为什么这样设计**：如果一个组件能在三处显示位各说各话，用户就会看到「标题栏标红、列表还是绿」
这种自相矛盾的界面。单点更新让这种事在结构上不可能发生。
