### D21 轮询周期进声明，作为「建议值」　✅ 已定稿（2026-09-12 用户裁定）

**用户原话**：「实际实现的话 tick 函数应该是由主框架轮询来调用的吧？」→ 是（复核见下表）。
随之暴露的问题：组件**无从表达**「我该多久跑一次」——今天是配置 `plugins.<id>.poll`（默认 30s，
`core/scheduler.py:141`，`DEFAULT_POLL = 30`）。

| | |
|---|---|
| **结论（用户裁定）** | 新增类属性 `suggested_poll`（秒，`RUN_PERIODIC` 时必填）：框架据此生成配置默认值 `plugins.<id>.poll`，**用户仍可在设置页覆盖**——组件给的是建议，不是命令 |
| **为什么不做成不可覆盖** | 节流是用户对电池 / CPU 的正当控制面；组件只声明「我的合理节拍」。与 2.4 显示位的两层控制同构：声明给默认值 + 用户层可调 |
| **`RUN_ON_DEMAND` 时忽略** | 按需触发的组件根本不进调度器，填了也不生效、不报错 |
| **调度权仍在框架** | 变的只是**数值来源**；「谁调用、跑在哪、失败怎么办」一概不变 |
| **影响面** | `core/plugin.py`（新增类属性）/ `core/scheduler.py:141`（默认值改读声明）/ 配置默认值合成 / 设置页（用户可改）/ 6 个组件 / 测试 / 本文 §2.1 |
| **状态** | **已落地**（2026-09-16）＋ 指向台账 `§A17` |

**附：`tick()` 的调用权（复核记录）**

| 问题 | 答案 | 证据 |
|---|---|---|
| 谁调用 | 框架调度器；组件**永不**自己调 `tick()`、不起线程、不排时钟 | `core/scheduler.py` |
| 谁进调度器 | 只 `RUN_PERIODIC`（`RUN_ON_DEMAND` 根本不注册） | `scheduler.py` `add_plugin` 首行判定（2026-09-15 起比较常量 `RUN_PERIODIC`，此前叫 `KIND_DAEMON`） |

| 时钟 | 单一 `Heartbeat`，相位按 `plugin.id` 错开（同 poll 不齐步；**poll ≤ 心跳周期时不成立**，粒度由心跳决定） | `core/heartbeat.py` `phase_for` |

| 线程 | 每组件独立 `QThreadPool(maxThreadCount=1)`，一插件卡死不连坐 | `scheduler.py:139-144` |

| 在跑 / 超时 | 上一轮没跑完则跳过本拍；60s watchdog 按失败处理并作废迟到结果 | `_on_beat` / `_watchdog` |

### D22 D9 收窄：声明点**可以**携带「纯读取回调」　✅ 已定稿（2026-09-13 用户裁定）

D9 关掉了「计算属性挂 Spec」。但「网络切换」设计提出 `StatusRowSpec.subtitle: Callable[[], str]` 时**撞上了 D9**——
两者字面冲突。复核后判定：**D9 的判据定得太宽，需要收窄。**

| | |
|---|---|
| **收窄后的 D9** | 关闭的是「**用声明点回调替代 `tick()`**」——即在 Spec 上算取值、绕开报告。 |
| **仍然允许** | 声明点可携带**纯读取回调**：`SwitchSpec.get_checked` / `get_enabled`、`MenuSpec.get_items` / `get_current`、`ModeBadgeSpec.get_state`、`StatusRowSpec.subtitle`。框架在每次刷新时求值。 |
| **回调的硬约束** | ① **纯读取**——不得有副作用（写文件 / 改配置 / 发请求 / 切模式 / 弹窗）；② 幂等——不依赖调用次数或时机（框架一帧内可能调多次）；③ 返回值不逃逸（不返回 widget、不缓存引用）。 |
| **允许的理由** | 回调**不产生**取值，只把组件已有的状态翻译成框架能画的形状；`tick()` 负责**产生**取值。两者分工不同，不构成第二条状态流。`SwitchSpec.get_checked` 从 D6 起就是这个模式——D9 若真禁掉全部回调，它早就违规了。 |
| **判据** | **回调只回答「现在是什么」，不改变「现在是什么」。** 要改变，走动作回调或 `tick()`。 |
| **落点** | 【契约】§3.1 新增「唯一的例外：纯读取回调」；§2.5 / §2.6 / §2.7 各自的取值回调字段 |
| **状态** | 已定稿，文档已改（代码无需改动——模式本来就存在） |

### D35 大窗体的保存：**声明式回调 ＋ 关窗拦一下**　✅ 已定稿（2026-09-18 用户裁定）

**用户原话**：「Form 需要有保存按钮……另外，改成手动保存。」

| | |
|---|---|
| **原条款** | D26「结论 ②」只定义了形态（`popover` / `window`）；**「什么时候写下去」从未写过**，于是实装成了「改一格写一次盘」（`_SceneEditor` 的类 docstring 里当时还专门写了理由：外层壳已有一枚「完成」，再过一道保存会让用户以为改过了其实全丢）。 |
| **问题** | 那条理由防的是「以为改过了」，但代价是反过来的——**「界面改了、盘上没动」在界面上完全看不出来**。用户提的三问（窗体要居中、要有关闭键、要有保存键）里，第三问戳的正是这个：他不能预判自己刚才那一下生效没有；而要动网卡配置这种「改错了会断网」的字段，一次性的显式写盘比逐格写更合手。 |
| **结论 ①** | `DetailEntrySpec` 新增 `save: FormSaveSpec \| None`，**两枚必作答回调**：`commit()` → `(ok, text)`（`ok=False` 时 text 是失败原因）、`dirty()` → 现在还有没有没写进去的改动。**声明了才有保存键**，没声明的窗体一个字节不变。 |
| **结论 ②** | **只许配 `window`**，配 `popover` 在**声明期**报错。理由：浮层卡是「点开就改、点外面就没了」的形态，攒一堆改动再问一句「要不要存」在那种形态里没有立足点；而「填了不生效」是最坏的一种成功，故不静默忽略。 |
| **结论 ③** | `window` 形态改走**原生标题栏**（居中于触发它的那块屏、关闭键与缩放归系统、**去掉「点外部即关」**）。此前它也是 frameless 浮层卡 —— 既没有关闭键、又带着浮层的关闭语义，两头不像用户见过的编辑器。 |
| **结论 ④（关窗那一下）** | `dirty()` 为真时**拦下关窗**，在窗内问一句，两个出路都**不是空操作**：确认位 = 「保存并关闭」（存失败则留在窗内并给出原因）、取消位 = 「放弃改动」。为此 `FeedbackBar` 的取消位扩成可承载一个真动作（`cancel_label` ＋ `on_cancel`），不传就是原来的「取消」。 |
| **为什么不是模态框** | 用户原话是「二次弹窗询问是否保存」，但**这条做不到、也不该做**：零模态是本项目已定稿的红线（置顶窗上开嵌套事件循环 ⇒ 用户只能强杀 ⇒ 中断信号落进系统回调 ⇒ `abort()`，`shell/` 另有门禁守着）。**实质等价、形式不同**：问句出在同一窗体的页脚，两个出路一个都不少。 |
| **「框架关窗」与「用户关窗」必须分开** | 框架自己关（`DetailHost.close()`：换一个详情页 / 退出）**不拦** —— 那是用户看不见的动作，拦了表现为「点另一行没反应」。用户关（关闭键 / `Cmd+W` / 「完成」）才拦。**已知代价**：框架关窗时攒着的改动会丢，登记在案（见台账 §A36「遗留」）。 |
| **失败不回滚（改了旧口径）** | 写盘失败**不再回滚**到写之前那份：攒在窗体里的就是用户刚打的字，收走它等于毁掉草稿。改为「原样留着报告在哪」＋「把半成品拦在保存之前」（半份场景 / 半份网卡配置都不进配置，理由同 D30 的「形状认得出才画」）。 |
| **配套（组件侧）** | 编辑器的「改一次落一次盘」随之改成「攒在内存、点保存才写」；脏判据是**与上次保存那份快照整体比**，不是在每条编辑路径上记得「标记脏」（那种写法漏一处就永久脏）。页脚那两枚 `[固定使用]` / `[交还系统]` **仍是动作**（点一下立刻写），不参与保存 —— 它们改的是「当前生效的那一个值」，与左边那张表不是同一件事。 |
| **落点** | 【契约】§2.8（字段表 ＋ 「`save` 解决什么」）；代码 `contribution/specs.py::FormSaveSpec`、`shell/detail.py::DetailForm`（关窗守卫 / 居中 / 原生壳）、`shell/ui_kit.py::FeedbackBar`（取消位）、`plugins/route_guard/{plugin,settings}.py` |
| **状态** | 已定稿，文档已改；**代码已落地**（2026-09-18，§A36）：＋12 用例（`test_detail_form` ＋11、`test_route_guard` 净 ＋1） |
