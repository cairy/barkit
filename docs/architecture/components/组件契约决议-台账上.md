### D7 徽标多状态表：挂账　⏸ 未做

需求侧曾提「badge 按钮列表：每个按钮支持多种状态，每状态含名称 / 颜色 / action / 是否禁用」。**不做**：

1. 徽标是**二元模式**（自动 ↔ 手动），不是状态机；多状态用 `get_state` 回调足够，且不必让插件持有 widget。
2. 「颜色」只有 accent / neutral 两态（视觉规格），开放为自由色会撞「状态同源」。
3. 「是否禁用」的真实场景是**行内控件**（守护没装 → 开关灰掉），已由 `SwitchSpec.get_enabled` 覆盖，徽标不需要第二套。

**启动条件**：出现第一个「模式徽标需要三态以上」的实证组件。

### D12 运行层命名：`Status*` → `State*`　✅ 已定稿（2026-09-12 用户确认）

**你问的**：「实际 `StatusSnapshot` 是状态详情吧？是不是叫『状态描述』更合适？」

| | |
|---|---|
| **它装了什么** | `level`（判定）+ `summary`（一句话描述）+ `detail`（细节）+ `updated_at`（时间戳）。所以它是「**判定 + 描述**」，叫「状态描述」会丢掉判定那一半 |
| **为什么不用「描述」当类名** | 「描述」这个词在报告内部有更合适的位置：`summary` 本身就是**一句话描述**，`detail` 是细节。若类名叫「状态描述」，就变成「描述对象里的描述字段」——同一个词占两层，更难读 |
| **真正的问题** | `State` 与 `Status` 是同一个中文词「状态」的两套英文词根，全文并存会持续制造困惑。D13 已把「状态」定义为**可枚举的状态机**，运行层那一份应当同根 |
| **结论** | `StatusSnapshot` → **`StateReport`**；同批把 `StatusLevel` → **`StateLevel`**，词根统一 |
| **目标词汇** | 组件 `ComponentSpec` → 状态机 `StateSpec` → 取值 `StateOption` → 级别 `StateLevel` → 报告 `StateReport`。**一套词根，一个中文词** |
| **备选名** | `StateReport`（推荐，与框架动词「上报」同源） / `StateReading`（读数，偏仪表隐喻） / `StatusDescription`（＝状态描述） |
| **影响面** | `contribution/specs.py:40-61` 定义 + `core/scheduler.py` / `shell/app_shell.py` / `shell/panel.py` / `shell/renderers/*` + 6 个组件 + 测试。**面较大**，与 D13 同批做（都要动同一个对象） |
| **状态** | **✅ 已落地（2026-09-15，与 D13 同批）** —— 门禁与落点表见 §A13 |

### D13 状态枚举：把「取值」抬到声明层　✅ 已定稿（2026-09-12 用户确认）

**模型**：组件把**所有可能的状态取值列举出来**，运行期当前状态对应其中之一。

| | |
|---|---|
| **结论** | `StateSpec.states: tuple[StateOption, ...]` 枚举全部取值；`StateOption(id, level, icon, text)`；运行期报 `StateReport(state=<id>)` |
| **论据** | ① 声明写的是业务语言（「电量低」），不是技术级别；② 图标与默认文案随取值变——**今天 `icon` 固定在 `StateSpec` 上，运行期换不了**，所以「充电中」和「电量低」用不了不同图标；③ 报告了未声明的取值可被发现；④ 设置页与文档能列出组件的全部取值（今天做不到） |
| **硬要求** | **每个取值必须自带 `level`**。否则颜色 / 角标 / 托盘聚合失去唯一来源，直接撞状态同源（D2） |
| **连带简化** | `initial` 从 `Callable[[], StatusSnapshot \| None]` 退化为 `str`（取值 id）——首屏只要「从哪一格开始」，不需要整份报告工厂 |
| **与既有决议的关系** | 采纳则 D1（`priority`）彻底失去意义；也让「类型 = info / warn / error」自然落在每个取值上，不需要单独概念 |
| **代价** | 运行期对象形状变化 → 影响全部 6 个组件 + 渲染 + 测试；需定义「动态文案覆盖」规则（声明给默认 `text`，运行期 `summary` 可覆盖） |

### D15 声明期是否收敛为单点：不合并　✅ 已关闭

**起因**：一个组件今天要写 4 条 Spec（`ComponentSpec` + `StateSpec` + `StatusRowSpec` + `BadgeRuleSpec`），
`key="main"` 在 `StateSpec` 与 `StatusRowSpec` 里各出现一次，读起来像「同一个东西写了两遍」。

**先厘清事实：这不是两个状态。** 运行期是单点更新（契约规范 1.4）：唯一写入点是 `tick()`，
唯一聚合点是「代表态」，唯一分发点是 `shell/panel.py:887` 的 `_recompute_plugin()`——
**同一个函数**里算出 `worst` 级别与代表态文案，同时喂给标题栏角标、列表健康点、列表副标题、
托盘圆点。两处 `key` 分属不同的 point 桶，**互不引用、互不校验**：

| 声明 | key 的真实职责 | 消费者 |
|---|---|---|
| `StateSpec.key` | 决定话题地址 `plugin.<id>.status.<key>`，是**状态流的路由地址** | 事件总线 / 快照表 |
| `StatusRowSpec.key` | 决定这条行贡献的 identity，是**渲染复用键**（同一行跨重绘复用同一 widget） | `shell/panel.py:723-732` 的 `_row_cache`；`PointRegistry.contribute()` 的撞名校验只有测试在用 |

**而且行不通过 key 找状态**：`panel.py:895` 的行按 `plugin_id` 索引
（`self._row_widgets.get(plugin_id)`），副标题取该插件**代表态**的 snapshot（`panel.py:929-931`）。
所以两个 key 写不写成一样，对渲染结果零影响。

**唯一性作用域是 (组件, 声明点)，不是「组件」。** `Plugin.id` 唯一标识的是**组件**本身，它区分不了同一组件里的第几条贡献；
一个组件在同一声明点下可以有多条（多台状态机 / 多行 / 多个按钮 / 多个热键），这些贡献 `plugin_id` 相同，只能靠 `key` 区分。
全仓实证：5 个组件都同时写 `StateSpec(key="main")` 与 `StatusRowSpec(key="main")`；`recognize` 的 `ActionSpec` 与 `HotkeySpec` 同为 `key="recognize"`——
同名不冲突，因为注册表按 point 分桶（`contribution/registry.py:61` 的 `_by_point[point][identity]`）。
单条贡献时 `key` 可省（框架取 `"default"`）；此时 identity 退化为 `plugin_id.default`，才是「一个组件一个 key」那回事。

| | |
|---|---|
| **结论** | **不合并**。声明按显示位分开，运行期由框架收成单点 |
| **论据 1** | 「行」与「状态机」是两条**独立的声明轴**，不是同步关系：`recognize` 既无状态机也无行（只有图标 / 按钮 / 热键），`autotype` 有行没有状态机。合并会强迫其中一方声明假对象 |
| **论据 2** | 合并的唯一收益是「少写一处」，代价是把 `custom` 逃生舱 / `on_click` / `reason` 这些行专属字段挤进 `StateSpec`，让最需要保持静态简洁的状态声明变胖 |
| **论据 3** | 两处 key 职责不同、互不引用，不存在「必须同步」的风险——合并解决的是一个不存在的问题 |
| **重启条件** | 出现第一个「行与状态机必须严格一一对应、分开写会持续写错」的实证场景 |
