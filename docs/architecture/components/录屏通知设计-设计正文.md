**总评：能，而且不用改 OpenDisplay 一行代码。四条能力里三条已实测可用，一条（菜单栏让位）需要一次性设置。唯一真正的盲区是 mirror 模式的状态判定。**

## 2.1 OpenDisplay 自己是怎么做的

先把你说的那个图标坐实。全部在 `../opendisplay/Mac/OpenSidecarMacApp.swift`：

```swift
// :26-36  菜单栏项：一个 SwiftUI MenuBarExtra
MenuBarExtra(isInserted: Binding(
    get: { controller.presentation == .menuBar },
    set: { _ in }                       // ← 注意：setter 是空实现
)) {
    ContentView(controller: controller, updater: appDelegate.updater)
} label: {
    Image(systemName: controller.running
          ? "rectangle.on.rectangle.fill"      // 实心 = 有会话
          : "rectangle.on.rectangle")           // 空心 = 无会话
}
.menuBarExtraStyle(.window)

// :193    你说的"实心/空心"到底是哪个变量
var running: Bool { !sessions.isEmpty }
```

**四个可以直接复用的结论**：

| # | 事实 | 位置 | 对我们的意义 |
|---|---|---|---|
| 1 | 图标 = `running` 的两个 SF Symbol | `:32-33` | 你要的"实心/空心屏"语义**已被上游定义好**，照抄语义即可（字形要自己画，见 §5.1） |
| 2 | `running` = `!sessions.isEmpty`，**不落盘** | `:193` | 外部**读不到**这个真值（无 URL scheme、无 CLI、无状态文件）→ 状态只能靠系统侧观察反推（§2.3） |
| 3 | 菜单栏项由 `presentation == .menuBar` 控制 | `:27` | **让位开关已经存在**：用户把 "Show app in" 改成 Background only 即可（§2.5） |
| 4 | `applicationShouldHandleReopen` → `MainWindow.show()` | `:61-65` | **这是"从外部打开它窗体"的正规入口**，且上游自己在 UI 里写明了用法（`:903`）："Open the OpenDisplay app again (Spotlight/Finder) to show this window." |

第 4 条就是全部可行性的钥匙：**BarKit 不需要 OpenDisplay 开放任何接口，它自己已经把"被重新打开"定义成了标准行为。**

## 2.3 状态从哪来：三级线索

从便宜到贵，三层叠加，**零 fork 优先**（与 `signals.py` 现有的降频设计一脉相承）：

| 级 | 判据 | 手段 | 成本 | 结论 |
|---|---|---|---|---|
| ① | **装没装** | `NSWorkspace.sharedWorkspace().URLForApplicationWithBundleIdentifier_("com.peetzweg.opensidecar.mac")` | 零 fork | 未装 → `absent` |
| ② | **跑没跑** | `NSWorkspace.runningApplications()` 按 bundle id **前缀**匹配（**必须前缀**：Debug 构建是 `...mac.debug`，`project.yml:96`） | 零 fork（实测通过） | 未跑 → `idle` |
| ③ | **有没有第二屏** | 现有 `signals.detect_virtual_display()`（CG 签名快照 + `system_profiler` 指纹） | 微秒级 + 插拔时一次 fork | 有 → `extended` |

**⚠️ 已知盲区：mirror 模式。** `MacSender.swift:22-24` 的枚举注释写得很直白：

```swift
enum CaptureMode: String {
    case mirror   // main display (Milestone 1)      ← 主屏镜像，不建虚拟屏
    case extend   // virtual display (Milestone 2)   ← 建虚拟屏
}
```

`VirtualDisplay.swift` 只在 extend 路径上被创建（`MacSender.swift:411-456`）；mirror 模式下 `virtualDisplay = nil`（`:468`）。**后果**：mirror 模式下第三级线索恒为假，状态判定退化成"进程在跑"——**界面会在"已连接"这件事上撒谎**。

**处置（三选一，见裁决项 3）**：
1. **接受**：mirror 模式下报"运行中（未侦测到第二屏）"，把它当成"信息不完整但不说谎"的诚实状态；
2. **补线索**：mirror 模式下改用"OpenDisplay 进程有对外连接"（WiFi 连 iPad:9000）或"本机在推流"（CPU/编码线程）—— 都需要新的探测手段与调参，收益有限（你是 extend 用户）；
3. **修上游**（见 §2.6）。

## 2.4 打开窗体（已实测）

**探针（2026-09-14，本机）**：

```
before: 3 个 OpenDisplay 窗口
   id=97  layer=25  35x24  @(-420,188)   ← 菜单栏项（第二屏那条）
   id=58  layer=25  35x37  @(1052,0)     ← 菜单栏项（主屏那条）
   id=237 layer=101 440x540 @(647,39)    ← MenuBarExtra 面板（预建，未显示）

   rc=0
after: 4 个（新增 id=475）
   id=475 layer=0   440x568 @(515,108) onscreen=True   ← ★ MainWindow 被拉起
```

**结论**：`open -a OpenDisplay` → rc=0 → 出现一枚 **layer=0、440×568** 的普通窗口。440×568 = `ContentView` 的 440×540 + 28 标题栏 → **就是 `MainWindow.show()`**。走的是 `:61-65` 的 reopen 回调，不需要任何权限，不需要 OpenDisplay 配合。

**顺带三个观察**：
1. **它带出了两个菜单栏项**（id=58 / id=97，各 35px）——因为 iPad 那块屏有自己的菜单栏。**你为了"给 bar 留空间"要省掉的其实是两格，不是一格。**
2. MenuBarExtra 的面板窗（layer=101）**始终预建存在**，即使没显示。所以"窗口存在"不能当"面板开着"用。
3. 落地方式：`core/proc.run_cmd(["open","-a","OpenDisplay"], timeout=10)` —— `run_cmd` 禁 shell、超时清进程组（`core/proc.py:28-49`），也是「打开外部应用」在仓里的唯一出口。**◷ 2026-09-19**：原文另举 `core/config.py` 的「打开配置」编辑器链路为先例，那条是零调用方的死链路、已整条删除。**不要在插件里自建 `subprocess`。**

## 2.5 让它让出菜单栏那一格

**上游已经提供这个开关**，就是它 UI 里的那个 Picker（`:897-906`）：

```
Picker("Show app in", selection: $controller.presentation) {
    Text("Menu bar")        // 图标在菜单栏（默认）
    Text("Dock")            // 图标在 Dock
    Text("Background only") // 都没有 —— 上游原话：再次打开 App 即可显示窗
}
```

`presentation` 持久化在 UserDefaults（`:169-177`），**本机实测当前不存在这个键 → 说明你从没改过 → 一直是 Menu bar**。

**为什么"由用户自己改"比"BarKit 代写"好**（这是一个建议采纳的取舍）：

| | 用户在原 App 里改（建议） | BarKit 代写 `defaults write` |
|---|---|---|
| 生效条件 | 立即生效，无需重启 | **必须重启 OpenDisplay**（`presentation` 只在 init 读，`:169`）→ **当前推流会断，iPad 黑屏一次** |
| bundle id | App 自己知道 | BarKit 要猜，且 Debug 构建是另一个 id |
| 越界程度 | 零 | 跨 app 偏好写入（灰区） |
| 用户知情 | 知道自己在改什么 | 不知道 BarKit 动了别人的配置 |

**建议落点**：本组件设**一条只读提示**——"检测到 OpenDisplay 仍在菜单栏占位"（用 `CFPreferencesCopyAppValue` 读 `presentation`，零 fork），点它**打开 OpenDisplay 窗体**，用户在那个 Picker 里自己改一次即可。**不做 `defaults write`。**

> **待实机确认**：`MenuBarExtra(isInserted:)` 的 `set` 是空实现（`:28`），所以「改 `presentation` → 图标真的消失」这条我**没法在不动你配置的前提下验证**。上游注释与 `:54 / :176 / :903` 三处逻辑都指向"设计如此"，但**必须你亲自试一次**（`Show app in` → Background only，看菜单栏两格是否都消失）。

## 2.6 若要 100% 准：给 OpenDisplay 加一个状态出口

零改动的天花板就是 §2.3：**读不到 `sessions`**。要拿到真值，最小改动是二选一（都在上游源码里，各约 5–15 行）：

| 方案 | 改动 | 收益 |
|---|---|---|
| **A. 状态文件** | `SenderController.sessions` 的 `didSet` 里写 `~/Library/Application Support/OpenDisplay/state.json`（`{running, count, devices[]}`） | BarKit 零 fork 读文件；**mirror 模式盲区同时消失**；还能显示设备名/数量 |
| **B. URL scheme** | `Info.plist` 注册 `opendisplay://`，实现 `application(_:open:)`：`show` = 开窗、`connect`/`disconnect` = 连接控制 | 打开窗口从"reopen 猜"变成"显式意图"；**顺带获得 BarKit 反向控制能力** |

**但这是改第三方仓库**（`origin = github.com/peetzweg/opendisplay`，不是你自己的）。是否值得，取决于你对 mirror 模式的依赖程度与是否愿意维护一个 fork。**建议：先做零改动版，把 A 作为"若 mirror 盲区真的咬到你"的挂账方案。**

## 3.2 信号：从"两个布尔"到"一个四态 + 一个布尔"

现状 `_read_signals()` 返回 `(s1, s2)` 两个布尔。新设计把 S1 换成**有名字的四态**（因为要当状态图标用）：

| 取值 | 条件 | 级别 | 取值图标 |
|---|---|---|---|
| `absent` | 未安装 OpenDisplay | `IDLE` | 空心屏 |
| `idle` | 装了，没跑 | `IDLE` | 空心屏 |
| `running` | 跑了，没侦测到第二屏（**含 mirror 模式 —— 见 §2.3 盲区**） | `IDLE` | 空心屏 |
| `extended` | 第二屏在线 | `OK` | **实心屏** |

S2 保持布尔（"任一规则命中"），只用于决策与文案。**这个四态同时喂三处**：状态机取值、图标选择、决策依据（若采纳 T3，只有 `extended` 之外的三个态不参与决策）。

> **前置依赖**：`absent` / `idle` 需要 ① + ② 两级线索（pyobjc，零 fork）。`signals.py` 现在只有 ③，**要新增**。注意沿用现有降频纪律：pyobjc 调用也放 `detect_*` 里并走同一套"状态变化才重算"的缓存（`signals.py:57-63`）。
