## 3.2 停用时，全部状态机降到 IDLE——但**不能撒谎**

这是产品判断，不是技术细节：**用户主动关掉自动化后，组件应该变灰，而不是继续满屏红。**

`off` 时把四台机的**级别**无条件压到 IDLE，忽略它们各自的真实取值：

| 状态机 | 停用前的取值 | `off` 时取值 | 级别 |
|---|---|---|---|
| `daemon` | `missing`(ERR) / `outdated`(ERR) | `not_needed` | IDLE |
| `net` | `static` / `pinned` / `failed`(ERR) | `frozen` | IDLE |
| `routes` | `applied` / `partial`(WARN) / `failed`(ERR) | `frozen` | IDLE |
| `profile` | `active` / `conflict`(WARN) | `none` | IDLE |

四台全 IDLE → 代表态 IDLE（灰）。**"关掉自动化"和"功能正常"在面板上必须看得出区别**：前者是灰，后者是绿的。

> **为什么 `net` / `routes` 报 `frozen` 而不是 `dhcp` / `none`（修正 2026-09-13）**
> 停用 = **不碰 = 保持现状**。停用后网卡可能仍是固化地址、路由可能仍在生效——那是事实，状态机不能报 `none`（未叠加）来粉饰。这也与现状代码一致：`paused=true` 的语义是「helper 冻结、保持已生效路由不动」（`rules.py:70`；`intent.py:84` 的 `if paused: 沿用上轮实际生效态`）。
> **代价必须补偿**：停用后路由还在、固化 IP 还在。所以 ① 副标题要显式写出来（`已停用 · 保持现状，路由仍生效（3 条）`）；② 必须留一条显式退出路径（`[交还系统]`，见 §4.7 二）。
> **为什么不自动回滚**：撤回本身也是一次"碰"，而且是一次会切断**正在使用中**的连接的"碰"。最轻的动作（关开关）不该有断网风险。

## 3.3 副标题：颜色聚合，文案由组件计算——**这里撞上了契约的一个限制**

契约 §1.4 / §2.7 规定：**列表副标题 = 代表态报告的 `summary`**，而代表态 = **严重度最高的那台状态机**，同级取**先声明**的那台（声明顺序 = 作者写的关注度顺序；◷ 2026-09-15 由「`key` 字典序」改定）。现状代码就是这么写死的（`shell/panel.py` 的 `_recompute_plugin`：`row.set_subtitle(rep[1].summary)`）。

一切正常时，四台都是 OK，平局取先声明的那台 → **写在最前的 `daemon` 胜出 → 副标题变成"守护就绪"**。但用户此刻想看的是 **"自动命中 · office · 已叠加 3 条 · 守护就绪"**——**四台机的信息，一行说完**。

> **这是硬冲突：颜色该聚合，文案不该聚合。** 颜色回答"有多坏"（必须取最坏，三处同色）；文案回答"现在是什么"（该由组件决定写哪几台、按什么次序）。原来靠"同一个取值同时决定颜色和文案"，在单状态机组件上侥幸成立，多状态机一上就散架。

**真正的限制不是"选不对那台机"，而是"只准用一台机的文案"。** 所以修法不是换一台机（`primary` 只是换个人选），而是**解除"必须是某台机的 summary"这个约束**：

> **建议增补**（详见 §5.2-②）：列表副标题改为**行级、由组件计算的整行文案**——
> `StatusRowSpec.subtitle: Callable[[], str] | None`，未声明时回退代表态 `summary`；**颜色仍一律取代表态级别**。

**为什么不是 `primary`**（2026-09-13 自我更正，用户指出）：

| | `primary` 方案 | 行级计算方案 |
|---|---|---|
| 能显示几台机的信息 | **一台**（换个机而已） | 任意——"都显示出来"成为可能 |
| 是否新增契约概念 | 是（`StateSpec.primary`） | 否（复用已有的 spec 回调模式，见下） |
| 与"如何显示由组件决定"是否一致 | 不一致——框架替组件挑了 | 一致 |

我先前在本文里写过"**不需要为它新增契约概念**"，然后又提了 `primary`——那是自相矛盾的。行级计算方案才真正兑现了那句话，也才符合契约 §2.7 已经承认的方向：「**根据当前状态算出副标题**的写法，就是在 `tick()` 里算好放进 `summary`」（`组件契约规范.md:607`）——契约本来就把文案的计算权给了组件，只是 §1.4 的那句"= 代表态报告的 summary"把这个权力又收回去了。

**回调不是新机制**：`SwitchSpec.get_checked` / `get_enabled` 早就是"声明里挂回调、框架每次刷新时求值"（契约 §2.6）。`subtitle` 只是把同一个模式用在文案上。

**副标题与徽标的分工不变**：配置项名只在徽标上出现一次。

| 展示位 | 内容 | 例 |
|---|---|---|
| 徽标 | 配置项名（名词） | `office` |
| 副标题 | 组件算好的整行文案 | `网关命中 · 已叠加 3 条` |

> **◷ 订正（2026-09-18）**：副标题那格的例子**原写作 `自动命中 · office · 已叠加 3 条 · 守护就绪`**，与它自己上面那句「配置项名只在徽标上出现一次」当场矛盾（名字出现了两遍），故删掉副标题里的场景名 —— 名字只归徽标（徽标文案**兼任当前项**，D33）。第 6 步做副标题时徽标还写着「自动 / 手动」，那时副标题那个名字是唯一一处，删不得；**徽标真能显示场景名之后**这句才成立。**`conflict` 是唯一例外**，仍列名字（那是**多个**名字的清单，也是「为什么生效的不是我以为的那个」的唯一线索）。见台账 §A32。

> **◷ 订正二（2026-09-18，用户裁定）**：副标题那格**再去掉两样** —— ① **装置健康那一段整个删了**：
> 「守护就绪」是**默认态**，占一格等于什么都没说（四种故障 —— 过期 / 未装 / 配置非法 / 停用 ——
> 本来就各自**领句并 return**，正常时不必再站一次岗）；② **首段从「自动命中」改成说依据**
>（`网段命中` / `网关命中` / `网段与网关命中` / `网卡在线命中`）：「自动命中」只回答"怎么来的"，
> 没回答用户要追问的"命中了什么"，而场景名在徽标上不能复述；依据只按该场景配置里**真写着的**
> 命中条件说（`match.subnet` / `match.gateway`，都写 = AND），查不到就退回「自动命中」（**不编依据**）。
> 落点见 §A35。

**"都显示出来"要多少给多少——但由组件决定上限。** 320px 的行放不下四段时，取舍规则是组件的判断（本组件的次序：**异常项优先 → 生效场景 → 结果 → 装置健康**），契约只提供位置、不规定内容。这一条也顺带解释了为什么副标题不必等长：它本来就是一句话，不是表格。

**顺带发现的契约缺口**：`tick()` 返回多台机报告的形状**代码里已经实现了**——`core/scheduler.py:124-136` 支持 `dict[key, StatusSnapshot]` → 逐 key 发布到 `plugin.<id>.status.<key>`；但契约 §2.7 只写了单份 `StateReport`。增补 ② 应一并补上这句。

# 四、界面落点（你问的问题）

## 4.1 判定线

**不是"设置页 vs 配置窗体"二选一，而是三层。** 两条判定线：

```
判定线 1：这个字段属于「某个配置项」，还是属于「整个组件」？
          ├─ 某个配置项 ──▶ 配置窗体（在配置项的编辑语境里）
          └─ 整个组件 ──▶ 判定线 2

判定线 2：这是「造/改领域对象」（任务流），还是「运维这个装置」？
          ├─ 造/改对象 ──▶ 配置窗体
          └─ 运维装置 ──▶ 设置页（且永不进配置窗体）
```

再加一条**优先级判定**（契约 §2.6 + UI 规范 §7.2）：

```
判定线 3：高频、二元、即时？ ──▶ 面板行就地（Switch / ModeBadge），不弹窗
         否则 ──▶ 配置窗体 / 设置页
```

## 4.2 落点表

| 项 | 落点 | 依据 |
|---|---|---|
| 配置项列表（增 / 删 / 拖排序） | **配置窗体** | 领域对象集合，任务流 |
| 配置项的每个字段（名称 / 监控网卡 / 生效网段 / 网络配置 / 路由规则） | **配置窗体** | 属于某个配置项 |
| 路由规则列表（增删改） | **配置窗体**（配置项里的二级列表） | 属于某个配置项 |
| 自动化总闸（停用 / 启用） | **设置页顶部** | 低频 + 破坏性；面板行只做状态回显（§4.5 / §4.6） |
| 切场景（自动 / 手动指定某个） | **面板徽标 → 场景列表** | 手动切是**主路径**（§2.6），必须两步内可达（§4.5） |
| **取消当前场景的路由（本次）** | **面板行 Switch** | 当场动作、高频；**覆盖层**，离开场景即恢复（§4.8） |
| 整个场景的路由开关（持久） | **配置窗体**（配置项内 `routes.enabled`） | 改"以后"，属于配置项（§4.7 一） |
| 网卡 DHCP / 手动 | **配置窗体** | 是配置项的属性（§2.2 冲突 A） |
| 场景是否参与自动匹配（`manual_only`） | **配置窗体** | 配置项属性，且必须可见（§2.6） |
| 生效的配置（只读） | 面板副标题 + 配置窗体顶部 | 结果，不是配置（§2.2 冲突 B） |
| 路由是否已叠加（只读） | 面板副标题 + 配置窗体 | 结果 |
| `[交还系统]`（还原网卡配置） | **配置窗体**（场景内）+ **设置页**（常驻） | 动作；停用态下也必须可达（§4.7 二 / 三） |
| 无匹配时（保持现状 / 交还系统） | **设置页** | 跨配置项的全局策略 |
| 守护 安装 / 重装 / 卸载 | **设置页** | 装置运维 + 系统授权 + 破坏性 |
| 轮询间隔 `poll`（框架）/ `helper_poll`（helper） | **设置页** | 装置调参；`poll` 默认值由 `suggested_poll` 生成 |
| 立即检查 / 打开数据目录 / 复制诊断 | **设置页** | 运维 |

**读法**：左边一列凡是"配置项内部"的东西，全部在配置窗体；凡是"这个装置本身"的东西，全部在设置页。**没有一个字段同时出现在两处可改**。

## 4.4 为什么不建议"全放配置窗体"

你问的第三个选项。三条具体代价，都能落地检验：

1. **卸载入口会消失。** helper 的安装状态是**组件级健康**（未装 / 过期），它必须在设置页和面板行可见。塞进配置窗体后，"守护没装"这个最该被看见的信号被埋在二级入口里，用户想卸载还得先打开配置窗体。
2. **配置窗体承担双语义。** 一边"编辑领域对象"，一边"运维装置"，于是会出现"编辑到一半弹系统授权、弹完回到表单"的割裂；破坏性动作（卸载 helper）混在可安全关闭的编辑窗口里，关闭窗口 = 关掉一个本该在设置里的入口。
3. **违反了已经定稿的收敛原则。** 契约 §7.2（UI 规范）已经改判为"**同一类配置只在一处可改**"。如果配置窗体里再放一份设置，自动化开关、检查间隔就有了第二个真源。

**什么时候该"全放配置窗体"？** 当组件根本没有装置运维项时（比如纯读的状态组件）。本组件有 helper、有系统授权、有破坏性动作，所以不适用。

## 4.5 面板行控件给谁（2026-09-13 **反转**）

上一版判定"徽标只读、面板不给切换入口"，**已反转**。依据是 §2.6：手动 IP 场景本质上无法自动命中，**手动切是主路径，不是逃逸舱口**——把主路径藏在二级窗口里是错的。

**最终分配**：

| 位置 | 承载 | 为什么放这 |
|---|---|---|
| `row_specs().mode`（徽标槽） | **场景选择器**，可点 | 契约 §2.5 给了「每行一枚徽标」的独立槽位，不占 `controls` 名额 |
| `controls[0]` | **Switch = 本次叠加** | §4.8：当场撤掉 / 恢复当前场景的路由 |
| `controls[1]` | 空 | 总闸移设置页，理由见 §4.6 |
| 整行点击 | 配置窗体（`DetailEntrySpec`） | 改配置，走契约 §2.4 正规路径 |

**场景列表长什么样**（点徽标后弹出）：

```
选择场景
──────────────────────────────────────────────
● 自动 按网段匹配（当前）
  office 192.168.110.0/24 · 3 条路由
  home 192.168.21.0/24 · 1 条路由
  iPad 直连 仅手动 · 静态 ← manual_only（§2.6）
──────────────────────────────────────────────
```

**两条硬要求**：

1. **每项必须带摘要**（网段 + 路由数 + 仅手动标记）。只给名字就是你上一轮反问我"看不见上下文怎么选"的那个问题——**这条要求不放松**。
2. **选中即生效**，不再弹二次确认、不再走配置窗体。这是把 4 步压到 2 步的全部要害。

**契约代价（前置依赖，必须先落地）**：现状 `MenuSpec` 只有静态 `items` / `current`，且菜单项是**单行纯文本**。要满足上面两条，需要补：

- `get_items` / `get_current`（运行时重读——场景列表会随配置窗体改动而变）
- 菜单项支持**副文案**（`label` + `hint`）

这两条从"登记待决"升级为**本组件的前置依赖**（§5.3-① 已改判）。
**退路**：若不动契约，徽标保持只读、切换走整行进配置窗体——但那就退回 4 步，与 §2.6 的"手动切是主路径"冲突。

**徽标怎么声明候选列表（2026-09-14 定案）**：`ModeBadgeSpec` 补 `items` / `get_items`
（`contribution/specs.py`），**不新增徽标类型** —— 两种点击形态的渲染是同一份代码、差异只在点击行为，
用类型去表达行为差异是错配（决议 **D33**）。三条要点：

- **`label` 兼任当前项**（按 `MenuItem.label` 匹配）⇒ **不设 `current`**：徽标上写着谁，谁就是当前项，不制造第二真源。
- **与 `on_click` 互斥**，同时声明在**构造期**报 `ValueError`。本组件走列表形态 ⇒ **不给 `on_click`**。
- **每项必须带 `hint`**（网段 + 路由数 + 仅手动标记）——上文"硬要求 1"在契约里的落点。

本组件的声明形状：

```python
mode=ModeBadgeSpec(
  label="office", # 当前场景名 —— 徽标文案即当前项
  accent=True,
  get_items=self.profile_items, # → 每项 (label, on_click, hint)，hint 承载摘要
  get_state=self.mode_state, # → (当前场景名, accent)，随刷新自对齐
)
```

> **◷ 承载控件定案（2026-09-18，第 7b 步落地时订正）**：本段原定「`ui_kit.apply_combo_style()` ＋ **原生
> `QComboBox`** ＋ `QStyledItemDelegate`（`paint()` 画两列、**必须同时覆写 `sizeHint()`**，否则摘要被裁）」，
> 实装用的是 `ui_kit.CandidateMenu`（`QMenu` ＋ 自绘 item 的 `hint` 副行、`popup()` 非阻塞）—— 它是**框架级**
> 控件（面板徽标 / 行内菜单控件 / 底部栏「⋯」溢出三处共用），为一个组件换掉会把这三处拆成两种实现。

> 给原生菜单补一个能画两行的 item，而不是换控件）。弹层外观 = macOS 系统样式，**这是接受项、不是待办**。
