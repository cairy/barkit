## 4. 配置

### 4.1 默认值写在你的 `config_schema()`

插件业务配置的默认值**只有一个真源**：`plugin.py` 里的 `config_schema()`（§9.5）。出厂文件
`config.default.yaml` 里**没有**你的业务键——它只留框架级默认（`app.*` / `hotkeys.*` / `tray.*`）
与 `plugins.<你的 id>.enabled` 这一个加载门控（那是框架的键，不写进 schema）。

```python
def config_schema(self) -> FormSchema:
  return FormSchema(
  plugin_id="your_component",
  fields=(
  FieldSpec("your_flag", "你的开关", FieldType.BOOL, default=False),
  FieldSpec("helper_poll", "巡逻间隔（秒）", FieldType.NUMBER, default=300),
  ),
  )
```

**合并顺序**（每个 `→` 覆盖前一个）：出厂文件 → 插件 `config_schema()` 默认值 → 用户配置
（`~/Library/Application Support/BarKit/config.yaml`）。`dict` 递归合并，`list` **整体覆盖**
（不是逐元素合并）。于是**默认值不落盘**，只有用户改过的键写进那份用户文件；卸载插件即随
schema 一起消失、不留残键。

**读这份声明**走 `self.cfg.value("某键")`，**写它**走 `self.cfg.set("某键", 值)`——类型 /
默认值 / 取值域全部回读这里，调用点不再写第二份兜底、也不再手写一份取值域
（见《组件开发指南》§3.3「配置访问」与 §4.3「写用户配置」）。

**三条别踩的**：

- **别把默认值写第二遍字面量**：消费方代码里若已有常量（如 `ipad_tunnel.DEFAULT_LOCAL_PORT`），
  `default=` 就引用它，不要手抄数字——抄一遍就是「两处默认值」在代码内部重演。
- **嵌套段声明 `FieldType.DICT`，不要平铺**：一个键底下是一组子键时（如 `wifi: {on_activate: …,
  on_deactivate: …}`），平铺成 `wifi.on_activate` 会产出一个**带点的字面键**，而消费方读的是
  `cfg["wifi"]["on_activate"]` ⇒ 默认值静默失效。`DICT` 给整段（与 `LIST` 同族：只做默认值
  合成 ＋ 宽松校验，无渲染器）。
- **门禁 `test_config_defaults_single_source` 不是障碍**：出厂配置的 `plugins.<id>` 段里除
  `enabled` 外**多一个业务键就红**。它守的正是「默认值不会漂移」——两处都写时改了一处，界面上
  看不出另一处还钉着旧值（用户读到的默认值与组件实际 fallback 分叉）。

> `poll`（框架轮询 `tick()` 的间隔）**不要写在这里**：默认值由你的 `Plugin.suggested_poll` 给，
> 设置窗会在**你这个组件页的页尾**自动生成一个「运行间隔」下拉让用户改——那是**框架**的控件，组件一个字都不用写
>（《组件契约决议》D21）。自己再声明一个 `poll` 字段等于开了**第二条覆盖通道**：两处都能写
> 同一个键，而界面上只看得到框架那一个（门禁 `test_no_plugin_declares_framework_poll_field` 会拦下）。
> **一个配置键只服务一个消费者**：你的组件若自带后台 helper 且有独立节律，**另起键名**（如 `helper_poll` / `resolve_poll`），**不要复用 `poll`**（D27）。

> 💡 **有一项配置不属于你**：菜单栏主图标来源 `tray.base_source` 是**主框架**的全局设置（落设置窗「通用」页），**不在 `plugins.<id>` 下**。
> 你的组件侧只需给状态机一枚**主图标**（`StateSpec.icon`），它就会进候选供用户挑选；**不给则永远不出现**。
> 用户选中后，菜单栏那一格改画该状态机的**取值图标**（没给取值图标 / 还没报过状态 / 已失联 → **回落你给的主图标**；
> 只有整个组件被禁用 / 卸载才回落 BarKit 默认底图）。
> **取值为状态机身份**（如 `notify_guard.display`），不是事件总线 topic。见契约规范 §2.5 与《决议》**D34**（◷ 2026-09-14 修订，
> 原口径「声明 `as_tray_base=True`」已撤销）。

### 4.2 ⚠️ list 整体覆盖的坑

`core.config.deep_merge` 对 `list` 值是"整段替换"。如果你的配置里有列表（如 route_guard 的 `profiles`），**千万不要把单条规则拷贝进用户 YAML 的列表**——合并时会把默认的其他规则整条抹掉。

route_guard 的解法：覆盖项单独存为 `rule_overrides` **字典**（按场景名索引），`dict` 递归合并只新增/改写对应键，保留兄弟键。你的组件若有"可增删的列表 + 用户覆盖"需求，照搬此模式。

> 💡 **目标形态**：「可增删的列表」这类**集合型配置**只能**自绘**（`FieldType.LIST` 没有渲染器），不能塞进 `config_schema()`；**放在哪**由**使用频次**决定——每天都用 → `detail_entry().build`，配一次就不再动 → `settings_page().build`（《组件契约规范》§2.8「配置放哪」/《组件契约决议》D30）。此外，`rule_overrides` 这层**运行期覆盖**在「网络切换」重设计中被拆成两档语义——「**本次**」（覆盖层，离开场景自动恢复）与「**以后都不要**」（配置层开关），见 `网络切换设计.md` §4.8。上面这个模式今天可用，但新组件**不要**照抄它「一次性和持久混用」的语义。

### 4.3 写用户配置（零授权）：还是 `self.cfg`

需要持久化用户操作结果（开关状态 / 列表）时，走 `self.cfg` 的**三个写口**。

> **一句话**：`set` 写一个键、`update` 写一组键、`mutate` 是逃生舱；三者都**不许**绕开
>（不要自己读用户 YAML 再 `save_user`，也不要从组件里取 `ctx.config`）。门禁
> `test_plugin_config.py::test_plugins_write_config_only_through_the_facade` 按 AST 守这条。

| 写口 | 用在什么形状上 | 语义 |
|---|---|---|
| `cfg.set("k", v)` | 单个**已声明**的键 | 校验（类型 / `choices`）＋ **等于声明默认值即删键** |
| `cfg.update({"k": v, …})` | 一次写多个已声明键（设置页只写它显示的那几个） | 逐键同 `set`；**先整批校验再落盘** |
| `cfg.mutate(fn)` | 嵌套子键（如 `rule_overrides.<场景>.<位>`）、要连带的删除、框架键 | 逃生舱：`fn` 拿到的是**用户差异段**，直接改它；**不带**上面那两条规则 |

```python
def set_your_flag(self, value: bool) -> bool:
  value = bool(value)
  if self.your_flag == value: # 幂等早退：不白写一次盘
  return True
  try:
  self.cfg.set("your_flag", value)
  except Exception as e: # 写盘失败 ⇒ 交回 False，由设置页行内提示
  log.error("写 your_flag 失败：%s", e)
  return False
  self.publish_snapshot() # 即时广播；不等下一拍 tick
  return True
```

四条要点，每条在 `tests/test_plugin_config.py` 里都有判据：

- **等于声明默认值即删键**。用户 YAML 是**差异层**（§4.1「默认值不落盘」），留一个与
  缺省同值的键会把那个值**钉死** —— 你日后把缺省从 2 改成 5，那位用户收不到（他并没有
  要求过「永远 2」）。框架自己的 `Config.set_plugin_poll` / `set_plugin_ui_visible`
  就是这个口径；组件侧照同一条。
- **写侧的歪值要抛，不宽待**（与读侧刻意相反）。读侧遇到用户手改写歪要回落默认值
 （不让面板起不来），写侧的歪值是**你的调用点**给出的 ⇒ `PluginConfigError`
 （悄悄落一个用户没要的值比报错糟得多）。`choices` 也在这一道，别再手写一份取值域。
- **失败的结局归调用方**。`cfg` 只报错（不落盘、不碰反馈条）：设置页那条路返回 `False`
  让它行内说话（插件自己持有反馈槽的，如 `route_guard`，由调用点 `_say_error(文案)` 落槽）；
  **面板**那条路必须把 `ActionResult` 交回结果槽（决议 D32-②）—— 面板看不到日志，
  不透传就是「开关弹回原位、一句解释都没有」。
- **写后会触发 `config.changed`**，组件可 `self.ctx.config.changed.connect(self.on_cfg)`
  订阅热重载（route_guard 即如此重算路由意图，改完即经会话声明出去）。

> 💡 `ctx.config` 上还剩两个**更底层**的口：`Config.update_plugin_section()`（就是
> `cfg.mutate` 的实现）与 `Config.user_plugin_section()`（读**差异层**，答「用户改没改过」
> 这个问题）。它们留给门面管不到的场合 —— 今天全仓只有 `ipad_tunnel` 的一次性迁移在
> 读差异层。**做 UI 的模块一律读经插件方法**（《插件结构规范》§7.2），门禁
> `test_no_config_io_in_ui` 守着（§4 跨面禁令 3）。
> **本节示范的写法只允许出现在 `plugin.py` / 领域模块里，绝不允许写进 UI 模块。**

### 4.4 用户配置被写脏了：框架统一提供「恢复默认配置」

**第一件要知道的事：不要把「配置模型升级」做成自动迁移。** 框架的口径是**绝不改写用户
验收过的 YAML** —— 段里留着一个新版不认识的键时，程序在**求值路径**报错，而不是偷偷把它
搬走或删掉。为什么：自动迁移会把用户验收过的一份 YAML 换成他没写过的样子，而那次写入
**不可逆**；组件侧再写一遍迁移函数，就等于全仓有了第二份「谁认识哪些键」的判据。

**第二件：用户自救的入口由框架给，你不用写。** 设置窗里**这个组件自己的页尾**（2026-09-21
起从「插件」管理页下沉到组件页），只要它在用户 `config.yaml` 里**真有差异项**，就会多出一张
「配置维护」卡（含「恢复默认配置」按钮）—— 改前这里只能在配置文件里手改，而那个键界面上
根本看不见。点它 ＝ 清空 `plugins.<你的 id>` 这一段，
合并后自然回到 `config.default.yaml` ＋ 你 `config_schema()` 声明的默认值。

对你的三条含义：

- **别在组件里再写一份「恢复默认」**：那是第二个落点，两处判据迟早分叉（`§A28` 拒绝
  「同一件事两个落点」用的是同一条判据）。
- **`ui` / `poll` 一并清掉**：它们确实是这个组件的配置，且在设置窗那一行上各有可见控件
 （用户点完当场看得见变化）。于是恢复之后有一条好用的不变量：**你的段里只剩 `enabled`**
  —— `enabled` 是运行门控（装 / 不装），不属配置，恢复默认不动它。
- **报错文案要先把「这不是用户写错了」说出来**：像「含未知字段：['force_apply']」这种措辞
  读起来像用户手滑打错，于是他会去翻自己的 YAML 找错别字 —— 而实测里绝大多数其实是
  **旧版本 BarKit 自己写下的键**（如面板开关从前写的 `force_apply`）。措辞现成可抄：
  `plugins/route_guard/rules.py` 的 `_UNKNOWN_TAIL`（定性 ＋ 指路 ＋ 一键恢复默认）。

## 5. 热键

热键是**若干条 `HotkeySpec` 声明**，由 `hotkeys()` 声明点方法返回：

```python
from barkit.contribution.specs import HotkeySpec

def hotkeys(self) -> tuple[HotkeySpec, ...]:
  return (
  HotkeySpec(name="your_hotkey", label="你的热键",
  default_combo="ctrl+alt+k", callback=self.on_trigger),
  )
```

- 字段：`name` 是内部键（也是 `config.yaml` 的 `hotkeys.<name>` 覆盖键），`label` 用户可读，`default_combo` 默认键位，`callback` 触发回调。Spec 的 `plugin_id` 由框架注入，**组件不写**。启动时框架经贡献注册中心统一收集（`contribution/points.py::declaration_points()` 的 `hotkeys` 点），对每条 spec 用 `config.get(f"hotkeys.{spec.name}", spec.default_combo)` 取键位并注册；插件不自己注册热键。
- 键位字符串格式：`"ctrl+alt+o"`、`"cmd+shift+k"` 等，修饰键 `ctrl/alt/option/shift/cmd` + ANSI 键名（见 `core/hotkeys.py` 的 `_KEYCODES`）。
- **键位冲突与同名冲突都由框架拒绝登记**（`register()` 返回 `False`，日志指名道姓说清谁跟谁撞了、该改 `hotkeys.<name>` 的哪一条）—— 不静默顶掉任何一条。所以**别把默认键位配成跟别的组件一样**：那样用户开箱就有一条热键「有时不灵」。两条防呆：门禁 `test_no_two_shipped_plugins_share_a_default_combo` 扫全部内置组件的 `default_combo`（出厂键位不许撞车）；`HotkeySpec.name` 也必须全局唯一（它同时是配置键，两个组件同名同样会被拒）。口径与理由见。
- **全局热键依赖辅助功能权限**（CGEventTap 监听 keyDown）。未授权时热键不可用，框架不会报错但也不触发；需要权限的组件在 `required_permissions` 声明 `"accessibility"` 并在回调里用 `core.permissions.ensure_accessibility()` 引导。

## 6. 状态流与跨线程（唯一路径）

daemon 组件的 `tick()` 跑在 worker 线程，**严禁直接碰 Qt 控件**。状态流只有一条路：**tick 返回报告 → 框架 publish → 渲染层按 identity 刷新**。

```python
import time
from barkit.contribution.specs import StateLevel, StateOption, StateReport

# 取值闭集（D13）：级别与默认文案只写一次；报告只报取值名
STATES = (StateOption("ok", StateLevel.OK, text="一切正常"), StateOption("stale", StateLevel.WARN, text="数据过期"))

def tick(self): # worker 线程：只计算，只返回报告
  value, summary = self._read_external() # 你的读取/计算；value 必须是 STATES 里的取值名
  return StateReport(value, summary, updated_at=time.monotonic())
  # 返回非 None → 框架自动 publish 到 plugin.<id>.status.<key>；插件禁自 publish。
```

要点：

- **静态归 Spec，动态归报告**：声明点方法（`state_specs()` / `row_specs()` 等，逐项见《组件契约规范》§1.3）里的 Spec 只声明「有哪些状态行」和「每台状态机有哪些取值」；运行期数值（取值名 ＋ `summary`）全部在 `StateReport` 里，**禁止**塞回 Spec，也**禁止** publish 裸 dict 或另起 topic。
- **文案只有一份**（决议 D18）：`summary` 同时是面板行副标题、副标题的悬停提示、标题栏图标的悬停提示——所以它得是一句**人看得懂的话**（「3 条生效 · 最后检查 12:04」），不是两个字的状态词；`StateReport.detail` 不存在了，**操作引导语**（点此重装 / 请在设置中安装）请落详情页或行内按钮，别塞进 `summary`。
- **custom 工厂行的刷新由插件自己接**：在 `start()` 里订阅自己的 status topic（`self.status_topic()`，与 `StateSpec.topic` 同源），报告到达时刷新控件（与框架消费同一份事件）：

  ```python
  def start(self):
  if self.ctx.events is not None:
  self.ctx.events.subscribe(self.status_topic(), self._refresh_ui)

  def stop(self):
  if self.ctx.events is not None:
  self.ctx.events.unsubscribe(self.status_topic(), self._refresh_ui)

  def _refresh_ui(self, report: StateReport | None = None) -> None:
  ... # 主线程：唯一允许改 UI 的地方；report 为 None 时用 self._snapshot() 兜底
  ```
- **手动操作**（面板按钮/热键触发的安装、卸载等）改完状态后要立刻反映到 UI：先 `_refresh_ui(self._snapshot())`，再 `self.publish_snapshot()` 广播到**同一个 topic**（基类是唯一广播落点）——手动路径与 tick 产出的报告同构，渲染层无感知差异。
- 切忌在 `setChecked`/`setText` 里再触发同一控件的信号造成回环——`Switch`/`Badge` 用 `clicked` 信号（仅用户点击触发）而非 `stateChanged`/`toggled`。
