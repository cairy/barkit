# 主框架架构 · 能力层（L2）

> 对应主方案 §7（含 root helper 特权通道）。

## 7. L2 · 能力层

> **收纳标准：框架只管插件自己干不了的事。** 实装形态是**可选能力基类**（mixin）与 **root 通道**两样，
> 没有业务服务。

> ◷ **§7.1 / §7.2 / §7.3 是「形态设计」，三节都没按这里实装**（2026-09-19 核对）。
> L2 的实装形态是「框架提供的**可选能力基类**」：`capabilities/automation.py::AutomationCapability`
>（协作式 mixin，零 UI 依赖，只产出 `ModeBadgeSpec`）＋ `capabilities/helper/`（root 侧，stdlib-only）
> ＋ `capabilities/helper_client.py`（app 侧客户端）。各节状态见小节头的 ◷。
> **要读「已在跑的东西」直接跳到 §7.4** —— 那一节才是实装（批次 4 起）。

### 7.1 权限枚举

> ◷ **未实装，现行形态是字符串名。**`Plugin.required_permissions: list[str]`（`core/plugin.py:86`）
> 直接写取值（如 `autotype` 声明 `["accessibility"]`，`recognize` 声明 `[]`）；没有 `Permission`
> 枚举类型、没有 `PermissionRequired` 异常、也没有「授予后重放调用」。引导只有辅助功能一条
>（`core/permissions.py::ensure_accessibility`），由调用方自己发起。下面这块是**当初的形态设计**。

```python
class Permission(Enum):
  ACCESSIBILITY = "accessibility" # 辅助功能（CGEvent 注入）
  SCREEN_RECORDING = "screen_recording" # 屏幕录制（截屏 OCR）
  ROOT = "root" # 需要 root helper

class PermissionRequired(Exception):
  """权限未授予。框架捕获后弹统一引导 UI，授予后重放调用。"""
```

### 7.2 能力注册表（懒加载）

> ◷ **机制未实装（判定：不做）**：`register(cap_type)` / `require(cap_type)` 全仓零命中。
> 能力就是**按需继承的基类** —— 需要自动化那套就 `class Plugin(AutomationCapability, …)`，
> 不需要注册表，也就没有「首次调用才 import」这一层要防。

**懒加载是硬性要求（这条仍然有效）**：无插件时 `capabilities` 不得 import 任何第三方库、
不得实例化任何服务。用 `test_capabilities_lazy`（subprocess 起解释器，只 import capabilities，
断言 `sys.modules`）守护 —— 门禁守的是**约束**，不是下面这套机制。

### 7.3 app 侧客户端（原称 RootBroker）

> ◷ **形状与落点都变了**（2026-09-19 核对）：没有 `RootBroker` 这个类，等价能力是**模块函数**，

> `installed_version()` / `helper_installed()` / `helper_running()` / `run_admin()` /

> 设置页/面板那侧的编排在 `shell/daemon_ops.py`（只画界面、回调注入）。
> ◷ 2026-09-28：三个装该 helper 的组件（网络切换 / iPad 隧道 / hosts 托管）的实现与接线
> 收进 `capabilities/helper_ops.py::HelperOpsCapability`（安装 / 卸载 / 立即检查 ＋
> `helper_notice` / `on_helper_change` / `helper_ops_texts` 三个钩子）；那张卡由框架按
> **声明**（`resources().helper_tasks` / `needs_root`）注入到组件设置页的**页尾框架区**。

请求模型见 §7.4.4 与《主框架架构 · 运行时通信模型》：期望态（`intent.set`）与一次性命令
（`op.run`）经**一条本机会话**下发，观测（`event.push`）经同一条连接推回 ——
**两侧都不再落盘任何通道文件**，`helper_tasks.json` 这个编排表也没有了（它是 `tasks` 那份意图的一帧）。

### 7.4 root helper：框架级特权通道

#### 7.4.1 起因与问题（迁移前的状态）

> ◷ 本小节写的是**迁移前**的样子，**三个问题都已解决** —— 留着是为了解释 §7.4 为什么这么设计。
> 2026-09-19 核对：`plugins/route_guard/helper.py` 这个 2223 行单体**已不存在**，已拆成
> `capabilities/helper/` 的 16 个模块（label → `com.barkit.helper`），且业务与机制按 §7.4.3 分家：
> 匹配决策等 policy 归插件侧（`plugins/route_guard/intent.py`），helper 只剩机制。

当年它跑三个 cycle：

| cycle | 业务 | 归属插件 |
| -------------------- | --------------------- | ----------- |
| `run_cycle()` | 路由增删 | route_guard |
| `run_tunnel_cycle()` | hev 隧道、DNS 劫持、utun 路由 | ipad_tunnel |
| `run_hosts_cycle()` | /etc/hosts 托管块 | hosts_guard |

**它是事实上的框架级 root 执行器，却挂在 route_guard 名下**（label 当年叫 `com.barkit.routed`），
于是有三个问题：

1. 新增一个需要 root 的插件，要往这个文件里塞第四套业务逻辑
2. 任何一处改动都要 bump `HELPER_VERSION` 并重装 daemon，影响全部插件
3. 删除 route_guard 会连带拆掉另外两个插件的 root 能力

#### 7.4.2 目标定位

> **`BarKit Root Helper` = 框架资产，提供特权原语，不提供业务逻辑。**

| 项 | 迁移前 | 目标 —— 2026-09-19 核对 |
| --- | ------------------------ | --------------------------------------- |
| 归属 | `plugins/route_guard/` | ✓ `capabilities/helper/` |
| Label | `com.barkit.routed` | ✓ `com.barkit.helper`（旧 label 由客户端清理） |
| 内容 | 三套业务逻辑（2223 行） | ✓ `core.py` 82 行 ＋ 原语；余下是 `routeops` / `tunnelops` / `hostsops` 的**机制**，按 §7.4.3 就该留在 root 侧 |
| 改动作 | bump `HELPER_VERSION` 重装 | ✓ 插件增删 task 不重装；原语增删仍需（见 §7.4.6） |

#### 7.4.3 职责边界（v3.0 修正）

**留在 helper（root 侧）** —— 因为必须常驻 / 必须 root：

- 系统状态变更的执行（写 /etc/hosts、改路由、改 DNS）
- 周期保活（隧道存活复检、路由复检）—— app 退出后仍要对**自持型**变更生效
- 特权子进程管理（hev）
- 系统状态复原（退出 / 崩溃 / 重启后的残留回收）
- **hev 配置的最终渲染**（见下方说明）

**回到插件（app 侧）** —— 策略与解释，无需 root：

- 规则语义与匹配决策（什么条件下加哪条路由）
- 配置生成与校验（渲染 hosts 块内容、生成隧道意图正文的字段）
- 状态解释（守护推来的那份事实 → `StateReport`）
> _理由见 「§7.4.3 职责边界」。_
>
> **定案：hev 配置由 helper 侧原语内部合成**。即新增一条「隧道配置」原语，入参是校验过的字段（端口、SOCKS 地址、mapdns 地址），yml 由 helper 在系统域生成。语义上仍是「原语固定 + 参数白名单」，不违反能力封闭，且保住了已做的加固。

#### 7.4.4 特权原语：封闭能力集

```python
# capabilities/helper/actions.py —— 编译期常量，运行期只读
ACTION_SCHEMAS = {
  "file.write_block": {"marker": str, "content": str}, # 目标路径内部常量化，非参数
  "route.ensure": {"dest": CidrSpec(), "gateway": IPv4Spec(), "iface": IfaceSpec()},
  "route.remove": {"dest": CidrSpec(), "gateway": IPv4Spec()},
  "dns.set": {"service": ServiceSpec(), "servers": ListSpec(IPv4Spec())},
  "dns.restore": {},
  "net.iface_query": {"iface": IfaceSpec()},
  "net.resolve": {"host": HostnameSpec(), "method": ChoiceSpec([...])},
  "wifi.select": {"ssid": SsidSpec()},
  "proc.manage": {"name": ChoiceSpec(PROC_NAMES), # 从 ROOT_BINARIES 派生
  "action": ChoiceSpec(["start", "stop", "status"])},
  # 同步原语（task 表驱动的业务入口）：入参就是该 subject 那份意图正文，
  # 形状校验下沉到各机制模块（routeops / tunnelops / hostsops）——校验与语义同处一地。
  "route.sync": {},
  "tunnel.sync": {},
  "hosts.sync": {},
}
```

**能力封闭是硬约束，不接受例外：**

| 约束 | 说明 |
| ------------------ | ------------------------------------------------------------------------------------- |
| **封闭枚举** | 能力集是 helper 源码里的常量。运行期不注册、不加载、不发现新能力 |
| **无命令类能力** | 任何形态的 `run_command` / `exec` / `script` / `eval` 一律不存在 |
| **无路径参数** | 请求参数中**不得出现任何路径**。root 侧路径全部是 helper 内部常量 |
| **无动态加载** | 禁 `eval` / `exec` / `__import__` / `importlib` / 模板引擎；subprocess 一律参数化且 `shell=False` |
| **无插件侧 action 模块** | 插件**不得**向 root 域部署任何代码 |
> _理由见 「§7.4.4 marker 不能当路径选择器」。_
> _理由见 「§7.4.4 不提供自定义能力」。_
**能力封闭 ≠ 编排封闭。** 插件可自由增删的是「何时做、用什么参数」，不是「能做什么」：

```jsonc
// intent.set("tasks", …) 的一帧（没有文件了）
{
  "tasks": [
  {"id": "route_guard.sync", "action": "route.sync", "subject": "route", "interval": 30, "enabled": true},
  {"id": "ipad_tunnel.sync", "action": "tunnel.sync", "subject": "tunnel", "interval": 5, "enabled": true},
  {"id": "hosts_guard.sync", "action": "hosts.sync", "subject": "hosts", "interval": 30, "enabled": true}
  ]
}
```

helper core 只做「按 task 的 `subject` 取那份意图 → 到点执行 → 调原语 → 推事实 → 登记变更」。
**task 不指向文件，指向一个领域名**：参数就是那个 subject 上最近一次声明的意图正文。
「立刻跑一轮」有两条来源 —— 该 subject 的意图刚变（当场记成「已到期」），或 app 发来一条
`resync` 命令（不等节拍）。**没有意图的 subject 一次都不跑**：旧形态下 route/hosts 会一直按
30s 轮询，哪怕 app 根本没在运行（拿的是盘上那份可能过期的期望态）——那是「只能拿文件当通道」
逼出来的；现在是「没有声明就是没有声明」。**没有任何活跃意图时守护线程纯阻塞，一天零唤醒。**

**task 表的信任边界**（五条红线）：

| # | 约束 | 理由 |
| - | ----------------------------------------------------------------------------- | --------------------------------------- |
| 1 | `subject` 必须在**闭集** `route` / `tunnel` / `hosts` 内 | 它决定这条 task 去读哪一份意图；放开等于让表指向任意内部状态 |
| 2 | `task.id` 前缀必须是**已注册插件 id**（`"<plugin_id>.<name>"`） | 攻击者可造 task，但不能伪造插件身份 |
| 3 | 数量上限：单插件 ≤ 8 条，总量 ≤ 32 条 | 防资源耗尽与表膨胀 |
| 4 | `interval` 下限 **5s** | 防忙等把 root 进程打满 |
| 5 | **task 结构不得含 `params` 字段** | 参数只能来自该 `subject` 的意图正文 |
> _理由见 「§7.4.4 编排开放不新增能力」。_
**编排开放到底扩大了什么？** 一句话定性：**编排开放不新增能力，只新增调用频次与组合。** 参数本来就完全由这份意图帧控制——攻击者往 `route` 的意图里写一个 `gateway`，与新建一条 `route.sync` task 指定同样参数，能达成的是**同一件事**。所以约束的重点是**频次下限与身份绑定**，而不是在 task 层再叠一层参数语义校验。

| 维度 | 是否开放 | 谁负责 |
| ------------------- | ---------------------------- | --------------- |
| **能力**（能做什么） | 封闭。`ACTION_SCHEMAS` 是源码常量 | helper 源码，需重装 |
| **编排**（何时做 / 用什么参数） | 开放。`tasks` 意图插件自由增删 | 插件 / app，零重装 |
| **参数值域** | 受限于 schema 白名单 | 请求方，helper 强制校验 |

**「可扩展动作列表」这个口子已不存在。** 它曾是用户可写文件里的一个 `actions` 列表，由 root 按 `type` 分发 —— 那就是自定义能力的胚胎。收敛为**固定字段、无 `type` 分发**：

```jsonc
// 隧道意图里与 Wi-Fi 有关的那一段（固定字段，无未知项）
"wifi": {"on_activate": "iPad-Share", "on_deactivate": "HomeNet"}
```

语义随之从「未知 type 不崩溃」改成**未知字段整份拒绝**。整份拒绝的对象也随通道换成会话而变：
不再是「读到未知字段就把整个文件作废」，而是**拒那一帧、会话照旧**（见《运行时通信模型》§2.2）。

#### 7.4.5 安全机制

威胁模型先摆正：helper 是 **root 常驻进程**，要防的不是「用户误操作」，而是**本地同权限恶意进程借 root 之手做事**。据此按「先消灭 RCE，再缓解劫持」排优先级——**能执行任意代码是灾难级，劫持流量是严重但可恢复**。

##### P0 · 消灭任意代码执行面（本轮必做）

| # | 项 | 现状 | 处置 |
| - | -------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1 | **`hev_binary()` 用户域 fallback** | `candidates = [SYS_HEV_DIR/hev, data_dir()/hev]`，`data_dir()` 是用户可写目录。系统域文件一旦缺失，root 就会执行**用户提供的二进制** | **删除 fallback**。只认系统域唯一路径；缺失即报错停机，绝不降级 |
| 2 | **`actions` 可扩展列表** | 用户可写的 `tunnel.json` 带 `on_activate/on_deactivate` 列表，root 按 `type` 分发 | 降级为固定字段（见 7.4.4），且随文件通道一起不再有文件 |
| 3 | 无 `eval`/`exec`/动态 import/`shell=True` | 已遵守 | 固化为红线 + 静态检查测试 |
| 4 | 请求参数中无路径 | 已遵守（意图帧里的 `subject` 是闭集领域名，路径不出框架） | 固化为红线 |
> _理由见 「§7.4.5 安全机制 P0」。_
##### P1 · 启动完整性守卫

**定位（易被误解，写死）**：它防的是**故障与误操作**（安装不完整、升级间隙、sudo 误操作、磁盘错误），**不是主动攻击**。要篡改 `/Library/Application Support/BarKit/` 的前提是能写该目录，而实测它是 `root:wheel 0755`，非 root 本就写不进去。

它确实有一项**回归防护价值**：把「文件缺失 / 权限不对 / 与基线不符」统一变成**停机上报**，从机制上杜绝「缺了就找个地方凑合用」的写法再次出现——P0-1 的漏洞正是这么来的。

| 资产 | 位置 | 异常后果 | 校验 |
| ------------------------- | --------------------- | -------- | ----- |
| helper 代码 | 系统域 `root:wheel 0755` | root RCE | 启动自检 |
| `hev-socks5-tunnel` | 系统域 `root:wheel 0755` | root RCE | 执行前自检 |
| `hev-tunnel.yml`（root 消费） | 系统域 `root:wheel 0644` | 流量劫持 | 读前复检 |
| 意图帧（app 侧产物） | 内存 / 会话上，路径不出框架 | 见 P2 | 值域校验 |

**启动 / 执行前自检三项，任一不过则拒绝执行并上报，绝不静默降级：**

1. `st_uid == 0` 且 `st_gid == 0`（wheel）
2. 无 group / other 写位（`st_mode & 0o022 == 0`）
3. 哈希比对安装时基线（`SYS_RUN_DIR/manifest.json`）

**失败语义**：**停机 + 上报 + 提示重装**，**不做自动复原**（复原需自带副本，副本本身成为新的被攻击资产，且 root 自愈逻辑风险高）。
> _理由见 「§7.4.5 安全机制 P1」。_
##### P2 · 损害控制（意图帧被伪造时）

意图帧来自本地会话，**能连上那个节点的进程**就能发——这是本架构的固有面（旧形态同款：
能写用户私有目录的进程就能改那份期望态文件）。能做的是**压低最坏后果**：

- 值域白名单：域名字符集、IPv4/CIDR 合法性、端口范围、接口名、网络服务名、SSID 字符集
- 跨字段不变量：hosts 写入 IP 不得落 `100.64.0.0/10`（防 fake-IP 死循环）
- 校验不过 → **整份拒绝，保持上轮状态不动**
- 最坏后果被限定为：路由劫持 / DNS 劫持 / Wi-Fi 切换到攻击者热点 —— **严重，但可恢复，且不等于 root RCE**

##### 变更登记簿 + 回滚点（不是审计日志）
> _理由见 「§7.4.5 变更登记簿」。_
##### 已知且接受的风险
> _理由见 「§7.4.5 已知且接受的风险」。_
>
> 缓解后的实际边界：攻击者**不能**让 helper 执行任意代码（能力封闭）、**不能**写任意文件（无路径参数）、**不能**替换 helper 或 hev（完整性守卫）；他**能**做的上限是发一份伪意图造成流量劫持，且变更可回滚。
>
> 会话侧另加了一层对**调用方**的校验：节点在用户私有目录、属主＝该用户、模式 `0600`，连接建立时用 `LOCAL_PEERCRED` 读对端 uid，不等于允许的用户即拒绝。要再往上收，需 **XPC + audit token + code signature**——本轮非目标。

#### 7.4.6 版本策略

```
HELPER_VERSION —— core、进程协议、或原语集合变更才 bump（需重装 daemon）
PROTOCOL_VERSION —— 会话线格式变更才 bump（两侧不符即拒绝握手，能说清谁旧）
```

- 新增一个原语：随 helper core 部署，属 `HELPER_VERSION` 变更（daemon 需重装，但**不再牵动插件业务逻辑**）
- 插件增删 task：只声明一份 `tasks` 意图，**零重装**

> **v3.0 简化**：v2.9 另设了 `ACTION_SCHEMA_VER` 用于「helper 与 app 核对原语集合」。但既然增删原语必然 bump `HELPER_VERSION` 并重装，两者不可能对不上——这个版本号永不触发。故**删除**，原语集合变更统一归 `HELPER_VERSION`。

#### 7.4.7 生命周期（v3.0 修正）

| 钩子 | 触发 | 自持型变更 | 依附型变更 | 配置与数据 |
| ----------------------- | ---------- | ----------------- | ---------------------------------------- | ------ |
| `stop()` | app 退出 | **保持**（helper 保活） | **拆除**（上游随 app 消失，见 §2.5） | 保持 |
| `on_disabled()` | 用户禁用 | **复原** | **复原** | 保持 |
| `teardown()` | 卸载 | **复原** | **复原** | **删除** |
> _理由见 「§7.4.7 生命周期」。_
>
> 另一处已修错误：v2.5 之前写「插件禁用 → task 标 `enabled=false`（不拆隧道/路由）」，同样是行为与界面不一致。禁用的语义是「我不想要这个功能了」，不是「想让它继续在后台生效」。

配套：

| 事件 | 动作 |
| -------------- | -------------------------------------------------- |
| 最后一个 root 插件被删 | **提示**可卸载 helper（bootout + 删 plist + 删系统域文件）；不自动卸载 |
| 卸载后重新安装 | 系统变更由 `start()` 重建；配置回到默认值 |

### 7.5 依赖方向红线

`capabilities` 可依赖 `core` 与 `platform`，**禁止依赖 `plugins` 与 `shell` 的具体组件**。 
`capabilities/helper/` 只依赖 Python 标准库（由系统 `/usr/bin/python3` 运行，兼容 3.9+）。
