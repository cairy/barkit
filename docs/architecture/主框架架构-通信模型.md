# 主框架架构 · 运行时通信模型

> 对应主方案 §2。

## 2. 运行时通信模型（先读这一节）

这一节回答「app 和 helper 到底怎么说话」。后面的 helper 归位、生命周期、task 编排全部建立在此之上。

### 2.1 两个进程，一条本机会话

| 进程 | 身份 | 启动方式 | 生命周期 |
| ---------- | -------------------- | ---------------------------------------------------- | -------------------------------------- |
| **app** | 用户态，普通权限，PySide6 GUI | 用户登录启动 | 随用户退出/崩溃而终止 |
| **helper** | root，LaunchDaemon 常驻 | `RunAtLoad=true` + `KeepAlive{SuccessfulExit:false}` | 开机即运行，退出即被 launchd 拉起，**与 app 是否运行无关** |

两者之间是**一条 AF_UNIX 本机会话**，节点是数据目录下的 `helper.sock`（属主＝该用户、模式
`0600`，父目录 `0700`）。helper 是**服务端**（常驻监听），app 是**客户端**（起来就连接，
断了按 1 秒节拍重连；连上期间**一个定时器都不跑** —— 数据到达由内核事件通知）。

安全口径与旧形态逐字相同：够得着那个节点的进程集合 ＝ 能写该用户私有数据目录的进程集合。
另加一层旧形态给不了的 —— 连接建立时用 `LOCAL_PEERCRED` 读出对端 uid，**不等于允许的用户即拒绝**。
（反面警示：把节点放进 root 拥有的公共目录并放开读写才是降级，任何本地用户都能连。路径与属主
的处置是**硬约束**，不是实现细节。）

「允许的那个用户」由**安装期**写进 plist 的 `BARKIT_UID` 给定：守护开机先起时推不出这个
数 —— 它若拿「数据目录的属主」当答案，读到的会是自己刚以 root 建出来的那个目录，于是把
整棵数据目录连同节点锁成 root:root，app 连不上也写不进，且非 root 改不回来（只能重装
自愈）。安装脚本顺手把数据目录归位（幂等 ⇒ **重装即自愈**）。

**另有第二条约会：蓝牙助手**（2026-10-04 落地的方案 §8 第 4 步）。app 与 root helper
之外还有第三个进程 —— 随包分发的 `BTHelper.app`，切蓝牙控制器电源只能由它做（那需要
「带 `NSBluetoothAlwaysUsageDescription` 的签名身份」，主进程怎么补都不行）。它走**同一份
线格式**（`protocol.py`），但**方向相反**：

| | root helper 那条 | 蓝牙助手这条 |
| --- | --- | --- |
| 谁是服务端 | 守护（常驻，开机即 listen） | **app**（按需 listen） |
| 何时有节点 | 安装期建好、常驻 | 动手那一拍才建，**用完即删** |
| 节点 | `helper.sock` | `bt_helper.sock` |
| 用到的消息 | 意图 / 命令 / 订阅 / 推送 | 只有 `op.run` → `reply` |

方向相反的原因是生命周期：助手由 `open` 按需拉起，**拉起之前没有进程在 listen**。
「谁 listen」不影响协议本身 —— 消息类型一个新加的都没有。节点同样只放用户私有目录、
`0600`、accept 时校验对端 uid，与 root helper 那条逐字同口径。

一次动手（`power-off` → 停 2 秒 → `power-on`）走**一条**会话、一个助手进程；会话死在
两条命令之间时会重建 —— 「蓝牙停在关着的状态」是这条路上唯一真正危险的失败形态
（实现在 `plugins/bt_guard/bt_session.py`，助手侧是 `resources/helper/bt-helper.m`）。

### 2.2 一条通道，四类消息

```
  app（用户域，零授权） helper（root 常驻）
    ─────────────────────                        ──────────────────
    intent.set(subject, payload)   ──►  幂等声明「我要什么」（rev = 正文内容哈希）
    op.run(op, params)             ──►  当场执行一次，帧级回执（req_id 配对）
    subscribe / unsubscribe        ──►  「要哪几个领域的最新事实」

                                   ◄──  event.push（有变化才推；订阅时先推一份当前的）
                                   ◄──  reply / error（应答；拒的只是那一帧，不打死会话）

  连接本身 ＝ 「对面还在不在」（断开即 EOF）
```

| 消息 | 方向 | 作用 | 关键性质 |
| ------------------------- | ------------ | ------------ | -------------------------------------------------------------------- |
| `hello` / `welcome` | app ⇄ helper | 对契约版本 | **唯一一次对版本的地方**：版本不符即 `ok=false` 并拒握手。**除 `hello` 外所有入帧都要求已握手**，否则回 `no_handshake` —— 否则「少发一帧 hello」就绕过了版本闸门 |
| `intent.set` | app → helper | 声明「我要什么」 | **幂等**：`rev` 是正文内容哈希，同内容重发＝空操作；重连后无条件全量重发即天然收敛，不需要「我上次写了什么」这种参照物。**一个 subject 一个写者**：第二个写者默认被拒，只有 `takeover=true`（或同一 client 重连）才换人 |
| `op.run` | app → helper | 「现在做一次」 | 一帧一命令、帧级回执；**不跨重启留状态**（没有 `seq` 水位线，也没有回执账本）。等待上限宽于该命令的最坏用时，超时如实回调 |
| `subscribe` / `event.push` | app ⇄ helper | 「现在怎样」 | 订阅即**立刻**推一份当前的，此后真变才推 ⇒ app 侧零轮询、零文件监视 |
| 连接本身 | 双向 | 「对面在不在」 | 断开＝EOF，不靠端口或时间戳去猜。**依附型意图随连接消失而撤回**（见 §2.5） |

- `subject` 是**领域名**（`route` / `tunnel` / `hosts` / `tasks`），不是文件路径 —— 路径不出框架。
- **一个 subject 只允许一个写者**（`helper/core.py::_Dispatcher._claim`）：守护记着「哪个
  subject 归哪条连接写」，第二个写者回 `already_claimed`；要换人就得显式 `takeover=true`，
  且原写者会收到 `taken_over`。同一 client 重连视为同一写者（守护可能先处理新连接、后处理
  旧连接的 EOF，不该把自己挡在门外）。**于是「A 断开」不会拆掉 B 正在用的东西** —— 撤依附型
  意图时只看这条连接**此刻还持有**哪些 subject。
  `doctor` 被门禁钉死不许连这条会话：它是只读工具，连上就是第二个写者。
- **被拒也要有回执**（2026-10-02）：`intent.set` 不带 `req_id`，守护拒收时 app 侧无从
  知道**哪一个 subject 的期望态没生效**，只剩一行日志 ⇒ 组件以为自己声明成功了。
  现在 `already_claimed` / `taken_over` 这两条拒绝帧带上被拒的 `subject`，app 侧按
  `helper_link.intent_rejection(subject)` 留可查状态、以 `on_reject` 上抛。**不带
  subject 的拒绝帧不记账、不猜**（那是旧版守护，按「无法归因」降级）。
  要拿到这个回执**须重装守护**；**不升 `PROTOCOL_VERSION`** —— 这一栏是可选字段，升版本
  会让「新 app ＋ 旧守护」直接握不上手，比降级糟 → 
- 「拒一帧」与「断会话」**分家**：未知消息类型只拒那一帧；旧契约那条「读到未知字段整份拒绝」
  是文件形态的产物，随文件通道一起消失。
- 线格式（长度前缀分帧、消息名、错误码）的真源是 `capabilities/helper/protocol.py`，
  两侧共用一份；单帧上限 1 MiB，**禁用 pickle 与任何可执行载荷**。
- 分帧**两半都要有**：读的一半是 `FrameReader`（拼帧），写的一半是 `FrameWriter`（允许
  部分写 ＋ 可写通知）。`SOCK_STREAM` 上两半都不成立 —— 把写假定成「一次 `sendall` 发完」，
  缓冲一满就会把「对端此刻没在读」误判成「对端坏了」。两侧对称：守护用 `selectors` 的
  `EVENT_WRITE`，app 侧用写方向的 `QSocketNotifier`（**常建、默认禁用**，只在真有积压时开）。
  于是「发不出去」只剩「对端真坏了」一种含义，与缓冲多大无关。
- **「对面在不在」有两个方向，都得有期限**：`EOF` 只覆盖「对端真没了」。另一端是「连上了
  却不再说话」—— 客户端等 `welcome` 有上限（`HANDSHAKE_TIMEOUT_S`，到点断开重连，否则
  守护假死时 app 会**永久**停在握手，既无 EOF 也不重连）；守护侧对「还没握手的连接」与
  「卡着半条帧的连接」各设一个回收期限。**正常空闲不设期限** —— 订阅型客户端几小时不
  讲话是对的，超时守的是「说了话但没说完」，不是「闲」。

### 2.3 「立刻跑一轮」不再是敲门

从前是 app `touch` 一个 `.trigger` 文件、守护每 1 秒 `exists()` 一次（空闲一天唤醒 86,400 次）。
现在这件事有两个来源，都不是文件：

| 场景 | 现在的信号 |
| ------------- | ------------------------------------------------------------------ |
| 链路就绪 / 断开（隧道） | **端口本身**：中继占上 `127.0.0.1:local_port` 这件事就是信号，守护现探端口即知上游在不在 |
| 用户点「立即检查」 | `op.run("resync", {"subject": …})`：不重发配置，只让对面把已有那份期望态再收敛一次 |
| app 退出 / 进程被杀 | **连接断开（EOF）**：依附型意图当场被撤回并跑一轮收尾 |

### 2.4 完整时序：以 iPad 隧道为例

```
  iPad ──USB──► bridge（app 进程内，127.0.0.1:1080）──► hev（root）──► utun90
```

| 阶段 | app 做什么 | helper 做什么 |
| ----------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **冷启动**（helper 已由 launchd 拉起） | `start()`：把隧道的期望态作为一帧 `intent.set` 声明出去（**纯意图**：`enabled` ＋ 端口 ＋ 劫持开关；链路事实**不在**这一帧里）；中继按探测结论决定要不要占端口 | 收到意图；`enabled` 为真**且探到上游端口有人在听**才拉起 hev、等 utun 建出、按开关补路由/DNS |
| **链路就绪** | bridge 准入探测通过（有 USB 设备 ＋ iPad:9001 能打通且 SOCKS5 握手有应答）→ 中继**占上** `127.0.0.1:local_port` | 现探端口 → 激活隧道（保活轮秒级复检，不必等谁通知） |
| **链路断开**（拔线） | bridge 发现 **USB 设备消失** → 中继**放掉** `local_port`（探测超时/引擎无应答不算，见 §2.7） | 复检到端口没人听 → 拆隧道（停 hev、撤路由、还原 DNS） |
| **app 退出** | `stop()`：框架先停中继（`local_port` 随之没人监听）；连接随后关闭；**不写任何「事实」** | 收到 EOF → 撤回依附型意图并跑一轮收尾 → 复检上游端口已消失 → 拆隧道 |
| **app 重启** | 重连后**无条件重发全部意图**（同内容＝空操作）；中继重新探测（3s 一轮 × 2 票 ≈ 6s），就绪后占回端口 | 上一轮已拆完；等端口重新有人在听再重建。**一次重启 = 一次完整拆建**，见 §2.6 |

### 2.5 系统变更的存续性分类

| 类型 | 定义 | 依赖 app 进程？ | `stop()`（app 退出） | `on_disabled()`（用户禁用） | `teardown()`（卸载） | 例 |
| ------- | --------------- | ---------- | ---------------- | --------------------- | ---------------- | ----------------------- |
| **自持型** | helper 可独立维持 | 否 | **保持** | 复原 | 复原 | 路由表项、`/etc/hosts` 标记块 |
| **依附型** | 上游资源在 app 进程内 | **是** | **拆除** | 复原 | 复原 | 隧道（依赖 bridge 的上游 SOCKS） |

**判定方法**（写进 `PluginResources`）：`system_mutations` 里声明的每一项都要标注
`survives_app_exit: bool`。框架据此决定 `stop()` 时是「什么都不做」还是「先复原再退出」。

依附型的意图在会话上是 `EPHEMERAL_SUBJECTS`：**连接消失即视为撤回**（不靠谁显式发一帧撤回——
进程被杀时那一帧根本发不出来），守护随即跑一轮收尾。这正是旧形态补不上的一格。

**为什么不用显式心跳让 helper 感知 app 生死？** app 的「退出 / 重启」歧义**定案不额外处理**
（§2.6.3）：连接断开就是最直接、最不可能误判的信号，不需要引入心跳、超时参数与时钟对齐。

### 2.6 app 的退出与重启

> **用人话说：你退出 app 再打开，hev 会被杀掉，等 6~10 秒再重新起一个。**
>
> 一次 app 重启 = 隧道完整拆建一次，中断 5~10 秒。这个行为**安全且代价可接受**，定案不做额外处理。

#### 2.6.1 实测路径（逐步对照源码）

| 步 | 发生了什么 | 位置 |
| - | ------------------------------------------------------------------------------- | ----------------------- |
| 1 | `stop()`：框架先停中继 ⇒ `local_port` 不再有人监听；连接随后关闭（**不发任何字段**，也没有字段可发） | `ipad_tunnel/plugin.py` |
| 2 | 守护收到 EOF → 撤回依附型意图 → 跑一轮收尾：复检上游端口已消失 → `want_active` 落假 → 杀 hev、撤 `/1` 路由、还原 DNS | `tunnelops._ensure_tunnel` |
| 3 | app 重启 → 重连并重发全部意图；中继重新探测：`probe_interval=3s` 且需连续 2 票同向才翻转，**最早 3s、典型 6s**才占回端口 | `ipad_tunnel/bridge.py` |
| 4 | 保活轮现探到端口有人在听 → 起 hev → 等 utun 建出 → 加路由 → 设 DNS | `tunnelops._activate_tunnel` |

合计中断 5~10 秒。（若配置了 `on_activate` / `on_deactivate` 的 Wi-Fi 切换，还会额外多两次切换；当前配置为空，不触发。）

#### 2.6.2 根因与代价

隧道是这样串起来的：

```
hev ← 127.0.0.1:1080（bridge，跑在 app 进程里） ← iPad
```

bridge 在 app 进程内，app 一退它就没了，hev 的上游随之消失。这时若不拆隧道，流量会打向一个
没人监听的端口——变成黑洞（开了路由劫持就是整机假连接）。所以**「app 退出就拆」这个决定本身是对的**。

「iPad 链路是否就绪」与「上游是否可用」这两件事**都不是意图**，所以它们不住在意图里：前者由
app 侧中继的去抖结论决定它占不占端口，后者就是「那个端口有没有人在听」这件事本身。
于是意图帧退化成**纯意图**（幂等、谁都能纠正、不会拿着一句过期的事实误导人），
而「app 退出就拆」这个决定本身不变。

**代价只有一件事**：那 6~10 秒不走隧道，期间走本机直连，不掉线。拆除的动作是撤掉 `/1` 路由、
还原系统 DNS，结果是回落到本机网络正常上网，**不是断网**。真正会断网的是 Wi-Fi 切换，
而当前配置 `on_activate` / `on_deactivate` 均为空，不触发。

#### 2.6.3 决策汇总

三处相关决策，根子上的障碍都是绕不开 helper 的保活轮：

> app 退出 → 中继停掉 → `127.0.0.1:1080` 消失 → 保活轮每 5 秒复检一次上游端口（`tunnelops._ensure_tunnel`），发现没人听就主动拆。

这条复检是**防黑洞的必要机制，不能去掉**。所以即使 app 侧什么都不做，helper 也会自己拆。

**① 为什么不做「重启不拆」**——想过三种做法，全部否决：

| 否决的方案 | 为什么不值 |
| --- | --- |
| app 侧 `stop(restarting=True)`：重启时不断中继 | 如上，那个端口随进程走，helper 保活轮照样拆，只在重启 < 5 秒时侥幸生效 |
| 租约 `lease_expires` + 分级降级 | 能可靠解决，但要动 helper（bump 版本 + 重装）+ 新字段 + 新状态机，为低频场景增加长期维护面 |
| 把中继独立成常驻进程 | 能根治（隧道还会变成「自持型」），但多一个进程要管：装 / 卸 / 版本 / 启停，与「框架保持精简」冲突 |

**定案：不做。** 接受重启即拆建——安全、可预期，代价是几秒钟。

**② 拉起延迟与「首轮立即探」**——app 冷启动 / 重启后，隧道指示要等好几秒才亮。根因不在 helper、
也不在面板，在 **app 侧 bridge 的链路探测去抖**：

- `BridgeController.start()` 把首轮探测排到 `probe_interval=3s` 之后，且 `flip_votes=2` 要求连投
  两票才翻结论（`bridge.py`）。干净冷启动：t=3s 投第 1 票、t=6s 投第 2 票才翻 ⇒ 中继这时才占上端口。
- 此后守护的保活轮（≤5s）现探到端口 → `_activate_tunnel` 起 hev + 等 utun（1~3s）→ 才 `active`。
- 面板刷新是推送驱动的（`event.push`），不是瓶颈。

| 项 | 决定 | 理由 |
| --- | --- | --- |
| 首轮立即探（冷启动 6s → 3s） | **采纳** | `start()` 首轮直接跑一次 `_probe_once()` 再排后续，一行改动、零新增开销、两票去抖完整保留 |
| `TUNNEL_POLL` 5 → 1 压崩溃黑洞 | **否决** | 崩溃是低频事件；为低频把常驻守护的轮询频率长期翻倍 = 持续增开销，不划算。崩溃黑洞维持 ≤5s（已定「不做」） |

判据：**只为确实可观测的问题改，不为低频场景长期加开销。**

### 2.7 链路抖动的防护（隧道）

抖动源有两个：USB 接触不良（链路几秒内反复翻转），以及**探针与被测链路抢同一条 USB 通道**
（2026-09-20 实测定案）。

**定案：去抖是 app 侧 bridge 的职责，不进 helper。**
- 上升沿（不占 → 占）：立即占，用户等着用
- 下降沿（占 → 不占）：延迟 5s 确认后才放

理由：去抖需要理解「USB 偶发断开」这种业务语义，helper 是通用执行器，不该懂。且放在 bridge 侧易测易调。

**判据分层 + 冷却**（原判据在运行期会把「量不通」读成「链路断」）。现场：隧道接管流量时 57 条会话
全部卡在 SOCKS 握手、探针走同一条 usbmuxd 通道必然 5s 超时 ⇒ 旧判据下探针报「链路断」⇒ helper 拆机
⇒ 负载消失、探针立刻恢复 ⇒ 2 分钟一轮、每轮约 40s 全机断网。

- **运行期**（隧道正在接管流量）：探针只轻查「USB 设备还在吗」，`LINK_NO_DEVICE` 才拆；
  完整的 usbmuxd Connect + 握手会让位给数据面，**不再参与运行期判据**。
- **准入**（隧道未接管流量）：做完整探测（设备 ＋ Connect ＋ SOCKS5 握手应答）——
  端口能连 ≠ 引擎会干活。
- **数据面自报**：运行期健康由中继自己数（会话窗口的成功/零字节），连续 `DATA_BAD_WINDOWS`
  个「零成功」窗口才允许触发拆除；这是运行期唯一能证明「隧道在空转」的证据。
- **冷却**：发布 false 后设备类 ≈12s、数据面类 ≈120s 内不自动重开。
- 中继接入同步改成非阻塞两段式（发请求 → 轮询应答 + 截止时间），在途上限满了就停 accept。

### 2.8 落盘还剩什么

通道类文件（期望态 / 状态 / 敲门 / 任务表 / 蓝牙助手那对请求与结果）**一份都不剩**。
会话之外只留两类，都不是通道：

| 文件 | 类别 | 谁写 / 何时写 |
| --- | --- | --- |
| `helper_snapshot.json` | 崩溃恢复 ＋ 给人看 | 守护；**只在意图或观测真变时**，单文件一次原子写（稳态可以整天不写） |
| `helper.log` / `barkit.log` | 诊断 | 各自进程；单文件写满**就地截尾**，不另开备份 |

**快照不是通道，所以它不需要新鲜度**：读它只有两种场合 —— 守护刚启动（此刻任何读数都是当前值），
或人 `cat`。于是「最长静默 120 秒兜底写」与 `checked_at` 水位线一起取消。
