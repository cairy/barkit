# 主框架架构 · 契约层（C，横切）

> 对应主方案 §5。

## 5. C · 契约层

> **字段定义权已移交《组件契约规范》**（`components/组件契约规范.md`）。本节只保留**分层与机制**：
> 扩展点注册、身份拼装、收集与排序、逃生舱的类型守卫、版本化口径。
> Spec 的字段清单、枚举取值、命名规则一律以该文档为准——两处各写一份字段表会立刻产生第二真相源，
> 而这正是本方案要消灭的东西。

### 5.1 扩展点注册表

框架声明「有哪些位置」，插件声明「挂到哪些位置」，两边通过 `point` 字符串解耦。

```python
class PointRegistry:
    def register_point(self, point: str, renderer: "Renderer") -> None: ...   # Shell 启动时注册
    def contribute(self, spec: "Contribution") -> None: ...                   # 插件挂载贡献
    def collect(self, point: str) -> "list[Contribution]": ...                # Shell 取贡献，已排序
```

**新增一个 UI 位置只需两步**：在 `points.py` 加常量 + 在 Shell 注册渲染器。基类、注册表、插件契约全部不动。

```python
POINT_STATUS_ROW    = "status.row"      # 状态面板的一行
POINT_HEADER_CHIP   = "header.chip"     # 标题栏状态芯片
POINT_SETTINGS_PAGE = "settings.page"   # 设置窗分页
POINT_PANEL_ACTION  = "panel.action"    # 面板底部动作按钮
POINT_MENU_ITEM     = "menu.item"       # 菜单栏下拉菜单项
POINT_HOTKEY        = "hotkey"          # 全局热键
POINT_BADGE         = "badge"           # 托盘徽标贡献规则
```


### 5.2 Spec 协议

**字段定义不在本节**（见本节开头的移交声明）。这里只留三件**机制**：

**① 身份拼装**（所有 Spec 共用，与 `Contribution` 基类同源）：

- `identity() == f"{plugin_id}.{key or 'default'}"`；`plugin_id` 由框架在收集时注入，插件一个字都不写；
- `key` 只在**同一声明点内**唯一，跨声明点同名是正常写法（状态机与它的行都可以叫 `"main"`）；
- 同一声明点只有一条贡献时 `key` 可省略（框架取 `"default"`）；
- 渲染层靠它**就地复用** widget（禁清空重建）——这是声明式 UI 的第一性问题（React / SwiftUI 同理）。

**② 收集与排序**：`PointRegistry.contribute(spec)` 按 `point` 分桶并拒绝 identity 撞名；
`collect(point)` 返回按 `(order, identity)` 排序的列表；插件间顺序由 `plugin_order` 统一裁决（§6.4）。

**③ 逃生舱的类型守卫**（契约层不真正 import PySide6，只在类型检查期可见）：

```python
if TYPE_CHECKING:
    from PySide6.QtWidgets import QWidget
    WidgetFactory = Callable[[], "QWidget"]
else:
    WidgetFactory = Callable[[], object]
```

### 5.3 状态流闭环

Spec 与 StateReport 的分工是本节的核心：

```
插件 声明方法 ──► Spec（静态声明：key / icon / order / states）
        │                        │
        │                        └─► 只在插件加载、配置变更、启停时重建
        ▼
插件 tick() ──► StateReport（动态数据：state / summary）
        │
        ▼  框架在 tick 返回非 None 后自动 publish plugin.<id>.status.<key>
EventBus ──► 渲染队列（50ms 合并去重，见《内核层》§8.3.6）
        │
        ▼
Renderer 按 spec.key 命中已缓存 widget → 就地更新字段
```

三条规则：

1. **框架在 `tick()` 返回非 None 后自动 publish** `plugin.<plugin_id>.status.<key>`。插件**不得**自己 publish 该前缀的 topic——否则两条路径互相覆盖，状态不可预测。由 `test_plugin_does_not_publish_status` 守门。
2. **渲染层按 `key` 维护 `dict[key, widget]`**，命中则就地更新，未命中才构造。
3. **`StateSpec.topic` 由 identity 派生**，不另设一套标识。

> 现状佐证：`core/plugin.py:85` 的 `tick()` 返回 `None`，芯片状态靠插件自行 publish、app 用 `_chip_level[topic]` 缓存（`app.py:129`）。v3 归一为「唯一入口、框架转发」。

> **给 UI 规范的约束**：任何新增的状态类 Spec（如 `StateSpec`）都必须遵守这个分工——**静态归 Spec，动态归报告，二者用 `plugin.<id>.status.<key>` 关联**。不得把 `level` / `summary` 这类运行期字段塞进 Spec 声明里，否则状态流会出现第二条路径。字段定义见《组件契约规范》§2.

### 5.4 版本化

```python
SPEC_VERSION = 1            # contribution/specs.py
SUPPORTED_API_VERSION = 2   # contribution/registry.py
SCHEMA_VERSION = 2          # core/config.py
```

与 `api_version` 分开：**渲染器演进（Spec 字段增删）bump `SPEC_VERSION`，不需要动插件契约；`api_version` 变更才需要插件作者改**（v1 适配层 `legacy/adapter.py` 已随批次 6 删除，见《主框架架构-插件可插拔》§9.6）。Shell 遇到更高 `SPEC_VERSION` 的 Spec 时降级渲染并告警，不崩溃。
