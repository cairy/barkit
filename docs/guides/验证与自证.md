# 验证与自证

每次改动后照抄本口径验证，确保不引入回归、不污染用户配置。

## 测试

```bash
QT_QPA_PLATFORM=offscreen uv run pytest tests/ -q --basetemp=/tmp/barkit-bt-<标签>
```

> **`QT_QPA_PLATFORM=offscreen` 不是可选项**（2026-09-21 实测）：本机就是 macOS，不设它时
> 平台是 **cocoa** ⇒ `test_entrance_is_noop_off_cocoa` 这类「本机应为离屏」的门禁**第一个
> 断言直接红**（`assert _is_native_cocoa() is False`），看着像回归、其实是跑法不对
>（原同族那条 `test_glass_only_on_native` 已随玻璃模式于 2026-09-21 删除）。夹具与产品
> 代码都不设它（`tests/test_tray_base.py` / `test_shell_design.py` / `test_ipad_tunnel.py`
> 只有三处模块级 `setdefault` 兜底），**命令里显式带上**最稳。

> 历史基线：966 passed / **约 29 秒**（偶有 1 例环境相关失败，见已知技术债）。
> **当前基线：1213 passed**（2026-09-17；**逐文件分片跑**，见下方「全量一次跑会崩」一节）；
> 下表里的 966 是更早的对照实测值。
> 原开工手册记录用 `.venv/bin/python -m pytest`；barkit 现以 uv 管理依赖，等价命令为 `uv run pytest`。
> **本机兜底**：CI/交互终端之外的 shell（含 AI 会话）PATH 里可能没有 `uv`，
> 用绝对路径 `~/.local/bin/uv run pytest …` 或直接 `.venv/bin/python -m pytest …`。

### ⚠️ 在 AI 会话里跑测试必须先清空 `PYTHONPATH`（2026-09-15 实测）

WorkBuddy/CodeBuddy 会把 `PYTHONPATH` 指向自己的 shim 目录
（`/Applications/WorkBuddy.app/…/cli/vendor/shim`），其 `sitecustomize.py` 会被
**每个 Python 进程自动加载**，并通过 unix socket 与宿主通信。cProfile 实测：
`test_panel.py` 有 **70%** 的时间耗在 `sitecustomize.py:_broker_readline`
的 7.5 万次 `socket.recv` 上——**不是测试在跑，是在等 socket**。

| 同一份代码 | 全量 966 用例 | `test_architecture.py`（41 例） |
|---|---|---|
| AI 会话内（broker 注入） | 137～248s，**波动极大** | 29.0s |
| `PYTHONPATH=` 清空后 | **29.4s** | **0.83s** |

```bash
PYTHONPATH= QT_QPA_PLATFORM=offscreen .venv/bin/python -m pytest tests/ -q --basetemp=/tmp/barkit-bt-<标签>
```

**纪律**：不得拿 AI 会话里未清 `PYTHONPATH` 的耗时当性能依据。它会把同一件事
放大 5～8 倍，足以让人误判「测试太多要精简」并据此删测试——而本套件其实很健康
（966 例 / 29 秒；其中 788 例快到测不出耗时，最慢单例 3 秒）。

### ⚠️ 全量一次跑会崩 —— 本批起改用逐文件分片跑（2026-09-17 实测）

`pytest tests/`（一次收集全部用例）会在 `test_architecture.py` **前段**崩：
`Fatal Python error: Segmentation fault`（退出码 139）或 `Bus error`（138），
**位置随机浮动**（落在第 21~27 个用例之间），栈恒停在 `pytestqt/plugin.py` 的
`_process_events`。`-v` 显示崩在下一条用例**开始处**，而那几条是纯 AST 门禁、自己不碰 Qt。

- **与当轮改动无关，别据此怀疑自己**。复核手法（照抄）：

```bash
git stash push -m wip && PYTHONPATH= .venv/bin/python -m pytest tests/ -q > /tmp/base.log 2>&1
echo "base_exit=$?"; git stash pop # 138/139 ⇒ 改动前同样崩
```

- **可用跑法（分片 ＝ 每个文件一个独立进程）**：

```bash
for f in tests/test_*.py; do
  QT_QPA_PLATFORM=offscreen PYTHONPATH= .venv/bin/python -m pytest "$f" -q > /tmp/shard.log 2>&1
  echo "$f exit=$? :: $(tail -1 /tmp/shard.log)" # 每行一条文件级结论，一眼看出红在哪个文件
done
```

- 实测：49 个文件全绿、**1213 passed**（2026-09-17）。单跑 `test_app_shell.py` +
  `test_architecture.py` 也不崩（75 passed）⇒ 崩的是**跨文件残留**：真装配用例
 （`test_app_shell.py` 真建 Panel / SettingsWindow / StatusItem）留下挂起事件与悬垂对象，
  被 pytest-qt 在**后续用例之间** `processEvents` 时踩到。
- 待单独一轮定位，归 §5 第 16 条；成因与复现见《踩坑记录》第 39 条。

> **⚠️ 别在分片循环前面加 `rm -f /tmp/xxx-*.log`（会让整条链静默中止）**：zsh 对**无匹配的 glob**
> 直接报 `no matches found` 并**中止整条 `&&` 链** —— 循环根本没跑，而退出码看着是 **0**。
> 实测（2026-09-17）：`rm -f /tmp/barkit-shard-*.log && for f in …; done` 在结果文件还不存在时
> **一个用例都没跑**，却照样打印了结尾标记，差点据此认为「全绿」。
> **照抄做法**：清旧结果用 `: > /tmp/<名字>.txt`（重定向截断，无 glob）；循环体内
> `> /tmp/xxx.log` 本身就是覆盖写，**不需要先删**。
> **判据**：跑完必须核 `wc -l /tmp/<名字>.txt` ＝ `ls tests/test_*.py | wc -l`（对不上就是没跑全）。

### ⚠️ 比「哪些用例红」必须在同一跑法下比 —— 平台变量是**导入期副作用**（2026-09-24 实测）

`QT_QPA_PLATFORM=offscreen` 在本仓**没有一处统一设置**（`tests/conftest.py` 里没有），
它只是 `tests/test_shell_design.py` / `tests/test_tray_base.py` 模块级的 `os.environ.setdefault`。
pytest 在**收集阶段**就 import 所有 test 模块 ⇒ **同一个测试文件，跟谁一起跑决定它跑在哪个平台**：

- `pytest tests/test_settings.py` 单跑（或只再带上 `test_hotkeys_page.py`）⇒ **没人设过**这个变量
  ⇒ 真跑 cocoa，窗口与几何都是真的 ⇒ `test_section_band_covers_the_card_edge_to_edge` /
  `test_machine_title_and_icon_outrank_their_options` / `test_combo_field_lets_the_wheel_scroll_the_page`
  **红**；
- 与 `test_shell_design.py` 同跑 ⇒ 收集期把变量设上 ⇒ **同一批用例全绿**。

**判据（三条互证）**：`QT_QPA_PLATFORM=offscreen … pytest tests/test_settings.py` → 全绿；
不带变量单跑 → 3 红；`grep -rn QT_QPA_PLATFORM tests/ src/` 只命中那两个测试文件的模块级
`setdefault`。⇒ 那 3 条**不是既有失败**，是跑法造出来的**假红**（正式的全量跑从来是绿的）。

**照抄做法**：① 单文件复跑**务必**带上 `QT_QPA_PLATFORM=offscreen`（上面那个分片循环里本来就有，
手动单跑最容易漏）；② 拿「失败集合」跟另一棵树对拍时，**文件集合 ＋ 平台变量两样都得一致** ——
否则「单文件 3 红、全量 0 红」会被误读成「本批引入 / 修掉了 3 条」。

**◷ 2026-09-28 已收口**：默认值移到 `tests/conftest.py`（`setdefault` ⇒ 显式环境变量仍优先），三处散点全删，并加门禁三条（`tests/test_architecture.py` 的 `test_qt_platform_default_has_a_single_source` 面不多 / `…_is_set_in_its_single_source` 面不少 / `…_gate_detects_a_stray_default` 合成自证）。**当年那句「会改变所有用例的平台、仓里有靠『offscreen 之下 `platformName` 仍是 darwin』的判据」经复核不成立** —— 全仓没有那样的判据（`ui_kit._is_native_cocoa()` 判的是 `platformName() == "cocoa"`，离屏下两个平台都为假；`macos_window._NATIVE` 读 `sys.platform`，与这个变量无关）。判据与数字 →。上面「照抄做法」那两条仍然成立 —— 显式带上变量永远不会错。

### ⚠️ 量「控件拿到多宽 / 有没有被省略」必须先 `show()` 宿主（2026-09-24 实测）

同一条坑的两个方向面，都会让用例**假绿**（断言跑了、但断言的那件事压根没发生）：

- **隐藏控件上不投递重排事件。** 控件没 `show()` 时，即使布局把它的几何改了，
  ``_elide``（``resizeEvent`` 里）也不会重算 —— 实测宽度已经变成 29、文本却**原样停在全文**。
  量省略 / 量几何前先 `show()`（离屏 show 同样算数），再 `qtbot.wait(1)` 让布局落定
 （一次 `processEvents` 不够，见上一条的同族）。
- **手工 `label.resize()` 造不出「被压窄」的状态。** 这一格若从未被布局结算过，初始宽是
  `QWidget` 默认的 100 而不是它的 `sizeHint`；手工 resize 也不触发重算。要「被压窄」，
  就让**布局**发宽度（宿主给窄宽 ⇒ 标签被压），别直接调 resize。

**照抄做法**：把被测控件放进宿主 → `host.show()` → `host.resize(窄宽, 高)` →
`qtbot.wait(1)` → 再断言；断言前先加一条**前提断言**（如
`assert label.width() < label.sizeHint().width(), "用例前提：这一格真的被压窄了"`），
否则坏掉的是前提、看起来却像被测代码过了。

## 在 Windows 上自证（写代码的那侧）

按项目分工，**Windows 只写代码、验证习惯上仍交 macOS**。但「完全不能验」会让很大一片
逻辑只能靠猜 —— 折中做法是一个**不落仓**的本地 pytest 插件
``.workbuddy/tools/pytest_win_shim.py``（`.workbuddy/` 已被 gitignore）。它只替换本机测试
进程里的几个名字，**不改任何生产代码**，把四类 POSIX/环境差异揉平：

| 差异 | 生产代码是真确的 | 本机揉法 |
|---|---|---|
| `os.getuid()`（Windows 无此属性） | POSIX 专属，正确 | 补一个 lambda |
| `core/autostart.py` 调 macOS 的 `launchctl` | 二进制不在 Windows | 桩掉 `autostart.status` |
| `core/config.py` 的原子写 `os.rename(tmp, path)` | POSIX 语义＝目标存在则**覆盖**；Windows 的 rename 做不到（WinError 183） | `os.rename = os.replace` |
| `O_NOFOLLOW`（helper `safeio` 防符号链接劫持） | POSIX 专属打开标志 | 按 `0` 处理（等于本机不验这层） |

**后两条尤其重要**：修复之前，凡是需要**写回用户 YAML** 的用例在 Windows 上一律恒红
（插件配置迁移 / 面板开关 / 暂停 / 覆盖层全走这条路径），Windows 侧等于对这些逻辑零覆盖。
补齐后这批用例能真正验到断言，Windows 与 macOS 的红灯集合也因此收敛到同一小撮。

用法（`PYTHONPATH` 的两项都要 **Windows 风格**路径，MSYS 的 `/c/...` Windows Python 认不出）：

```bash
PYTHONPATH="src;<仓库根>/.workbuddy/tools" QT_QPA_PLATFORM=offscreen \
  .venv/Scripts/python.exe -m pytest -p pytest_win_shim tests/test_xxx.py -q
```

剩下的红灯是真测不了的：依赖 macOS 命令的探针（`/sbin/ifconfig` 等）、以及
`CoreGraphics` / pyobjc 这一类本机缺库。**判断红灯归属要看基线，别推断**：

```bash
git worktree add C:/tmp/barkit-base HEAD # 取 HEAD 副本跑同一批文件
# 两边都取失败名列表再 comm：只有在「当前」一侧多出来的才是本次改动引入的
```

## 隔离自证（必做）

改测试前后，对真实 `~/Library/Application Support/BarKit` 做 `mtime:size` 快照 diff。

- **阴性对照**：root helper 守护进程在跑，会自己周期写 5 个文件
 （`helper.log` / `state.json` / `hosts_state.json` / `hosts_resolved.json` / `tunnel_state.json`）
  —— 这不是测试污染。先跑 20s 空闲对照再下结论。
- 实测参考：P1 只有 4 个文件 mtime 变化、零新增文件 ⇒ 干净；
  P2-a 零新增零消失、变化 2 个（都在上述 5 个内）⇒ 干净。

- **别用 `stat -f` 手写 diff**（格式串会打出文件系统块统计而非文件变化，曾据此误判）；用脚本记 `mtime:size`。
- ⚠️ **AI 会话的沙箱里会看到一条假污染**（2026-09-18 实测）：`~/Library/Application Support/BarKit`
  下 Python 的 `Path.unlink()` 被拒（`PermissionError: [Errno 1] Operation not permitted`），而
  `write_text` 是放行的 ⇒ `barkit doctor` 的写探针（`.doctor-write-probe`，唯一会写的盘，写完即删）
  **会留下一个 0 字节残留**，`test_doctor_survives_missing_pyside6`（它就真的跑一遍 doctor）一跑必现。
  **判据**：在同一个目录里手动 `p = dir / ".x"; p.write_text(""); p.unlink()` —— 若也报
  `Operation not permitted`，就是**沙箱**而不是代码不自清；清掉即可（`rm` 是放行的），别去改 doctor。

## 新增门禁的自证（**必做**，2026-09-15 实测差点验空）

每条新门禁都要「**植入违规必抓 ＋ 合规写法不误报**」两半都做，且有三条纪律：

1. **植入要落在真实文件上**，不能只写 tmp 样本用例。tmp 样本只证明「判定函数」对；真实文件才证明
  **扫描面覆盖到了**（今天三条门禁逐个在 `example/` / `shell/panel.py` / `plugins/hosts_guard/`
  各塞一行违规，确认全红，复原后全绿）。做法：读原字节 → 追加 → 跑那条门禁 → **`finally` 里按原字节
  写回** → 断言复原后再跑一次全绿。
2. **植入的字符串必须是「真的旧名」**。今天把旧名 `StatusLevel` 写成了新名 `StateLevel`，
  结果「植入违规必抓」这一半根本没验到 —— 只有断言里的行号对不上才暴露。
  自证样本里的每个名字都要**逐字核**（旧名 / 新名只差两个字母的那类尤其危险）。
3. **`import` 一行不算「使用」**（AST 里是 `ast.alias` 不是 `ast.Name`）：半改名的文件是在
  **真正用到它**的那一行被抓的。样本要**同时**有「注释里提旧名」（不误报）与「表达式里用旧名」（必抓）两种。
4. **植入要连同它的依赖一起植入**（2026-09-17 实测）：在真文件里塞回一行旧写法时，若那行引用的东西
  **同一轮刚好被删过导入**，跑出来是 `NameError` 而不是门禁的诊断 —— **红了，但红的不是门禁**，
  自证等于没做。判据：看报的是不是门禁自己写的那句断言；是 `NameError` / `ImportError` 就先补导入
  再重跑。（本轮实例：给 `recognize` 塞回 `ComponentSpec(...)`，第一次只红了 `NameError`；
  把导入一并补回，才红在门禁那句「没有状态机却声明标题栏」上。）

## 门禁**扩面 / 改扫描面**时（2026-09-19 新增，`test_no_hardcoded_colors` 那批）

「改动一条已记下的约定」比新增门禁更需要自证 —— 它既可能**没收干净**（面改了但漏文件），
也可能**悄悄放走**（面收窄了没人发觉）。五条：

1. **先重数，连「怎么数的」一起给**。同一件事两个口径往往差一截，差的那些要能逐条解释。
  实例：AST 判据（只看字符串字面量、排除 docstring）给 `1 文件 / 41 处`，裸 `grep` 给 `46 行`
  —— 多的 5 行全是注释 / docstring 里的**说明性举例**（「原先写死 `#9aa0a6`」那类）。先解释
  差值，再谈「零例外」是否成立；只报一个数等于把扫描面的洞留给自己。
2. **边界写成一个具名常量，不写成一张表**。表会长大；常量要长大就得动到它那一行附近。再用一条
  自证把边界钉住：① 面**不多**（边界文件不许落回面内）；② 面**不少**（`全量 - 边界` 里每个文件
  都得在面内，报错时**把漏掉的文件逐个列出来**）；③ 边界**指向真文件、且真定义那个真源**
 （`is_file()` ＋ 模块级名称断言 —— 文件改名 / 挪位后老常量会**静默跳过不存在的路径**，
  面反而变宽却没人发现）。
  **① 与 ② 必须分开写**：合成一条 `==` 断言时两种坏法会挤进同一句报文 —— 实测「面被收窄、
  漏了一批文件」被报成「排除项不止一个文件」，**报文与实情正相反**，读的人会往反方向查。
  同理**别写「某某文件必须在面内」这类逐条点名的断言**：它被 ② 完全遮住、永远轮不到自己红，
  是假守。判断「扩面真的扩到了没有」只该看 ② 的漏掉清单是否为空。
3. **反向验证的植入点要挑「只在扩面后才进面的文件」**。往那儿塞违规，红了才同时证明
  「扩面真的生效」，而不只是「门禁还活着」。
4. **补一轮「边界指错」的植入**：把常量指向一个不存在的文件名。这一轮价值最高 —— 真源文件会
  落回面内，于是**门禁本体先红一大片**（41 处），正是「扫描面变宽却没人发现」的实证。
  另注意判据要同时收 `ast.Assign` 与 `ast.AnnAssign`：本仓 `TOKENS: dict[...] = {` 是后者，
  只认前者会在有人去掉类型注解时**误报**（第一轮就是这么红的）。
5. **每轮植入之前先跑一次「现状须全绿」**。改坏自己要改的东西时（漏删一行、少个变量），
  植入轮照样会红，但红的是 `NameError` 而不是门禁 —— 看起来像「门禁抓到违规」，其实自证
  已经废了。实测：改那两条断言时漏掉 `targets = _color_scan_targets()`，前置检查当场报
  `NameError`，否则后面几轮的「红」全是假的。
6. **扫描面按「这个文件是不是那种东西」判，不按文件名模式判**（2026-09-20 实测）。
  文件名模式只能覆盖「名字有规律」的那部分 —— 规范里凡有**不带后缀**这类例外，**整类就漏在
  面外**，而漏的这一类恰恰没人会想起来补。实例：`test_no_config_io_in_ui` 原本扫
  `("settings.py", "*_view.py", "*dialog*.py")`，而《插件结构规范》§7.3 明文的「运行期**构件**」
  **不带** `_view`（`recognize/selview.py` 是 `QGraphicsView` 子类）；往里写 `ctx.config.user_path`
  **门禁不红**，同一行放进 `window_view.py` 会红 —— 这个**同行对照**就是洞的举证方式（同一轮里
  也顺手证明探针不哑）。改法是判据换成 AST 事实（import 了 PySide6，除域面 `plugin.py`），
  扫描面 11 → 12。
  **配套的一课**：那条门禁**本来就有扫描面自证**，却照样看不见 —— 因为它的断言是「点名的两个
  名字在不在」（`{"settings.py", "manager_view.py"} <= got`）。**逐条点名只能守「模式拼错」，
  守不住「有一类文件根本不匹配任何模式」。** 自证要写**整类覆盖**：本仓的新写法是要求「扫描面里
  **必须存在不匹配任何旧模式的文件**」—— 一条**照旧模式反向对照**的断言；没有它，扫描面退回按
  文件名时用例照样绿，而那正是要防的事。

## 「搬家 / 换真源」类改动的证明（2026-09-20 新增，配置默认值单一真源那批）

把一份数据从 A 处搬到 B 处、**行为应当完全不变** —— 这类改动的证明分三层，**缺中间那层会误判**：

1. **逐键等价**（弱）：两侧都展开成扁平 `k → v` 再逐键比，**连同类型**
 （`type(a) is type(b)`，否则 `1` / `True`、`300` / `"300"` 会判成相同）。它只证明「值没抄错」。
2. **按生产路径合成后对拍**（硬）：照抄**生产里那句注入 / 装配调用**，把「用户会看到的最终状态」
  dump 成 JSON，两侧逐字节 `diff`。逐键对比**过得了、而合并顺序错了照样坏** —— 例：把
  `plugin_defaults` 合并到 `user_config` **之上**，每个键都还在、值却不再被用户覆盖。
  **必须反查 dump 不是空转**（里面要真出现那批键），否则「两侧都空」也会 diff 成空。
3. **四链**（回归面）：节点集 `comm` 双向 ＋ 全量 ＋ 失败集合 diff ＋ pyflakes。纯搬迁的预期长相：
  失败集合**双向为空**，节点集**只增**（新增用例）或**双向为空**（不加用例）。

**另一条**：供货方（撤掉旧真源的那侧）与消费方（读它的那侧）**必须同一批接上**。只撤不接的表现
是一批用例报「配置里没有 X」，极易被读成设计错 —— 判据是「**测试里构造的对象必须与生产同形**」，
修法是让测试走生产的注入路径，而**不是回头把旧真源加回去**（那等于把刚清掉的「两处真源」复活）。

## pyflakes 增量对比的正确做法

1. **归一化**：`uniq -c` 会把「同一条告警出现在不同文件」合并成不同计数 ⇒ `comm` 全量误报。
  必须保留相对路径＋去行号＋`sort -u`（`sed 's/:[0-9]*:[0-9]*:/: /' | sort -u`）后再 `comm`。
2. **造一份 HEAD 基线再比**（比肉眼 / `uniq -c` 都可靠）：
  `git worktree add -f /tmp/bk-head HEAD && (cd /tmp/bk-head && pyflakes src/ tests/) && git worktree remove /tmp/bk-head`
3. 实测参考：HEAD 54 条 → 改动后 47 条，零新增、净减 7；批次 12 实测 47→47（`comm` 两方向都空）——新代码不带告警。
  **2026-09-17 复核：50 个文件全绿 1236 passed；pyflakes 45 → 45（`comm` 两方向都空）。**
4. **两侧必须用同一个解释器**，否则会得出「新增 40+ 条」的假结论。
  实测（2026-09-17）：`.venv/bin/python` **没有装 pyflakes**（`No module named pyflakes`），
  而命令里写了 `|| 另一个解释器` 兜底 ⇒ **只有改动侧**落到了兜底分支、HEAD 侧直接空输出，
  于是 `comm -13` 把全部 45 条报成「新增」，看起来像「这一轮引入了一堆告警」。
  **判据**：跑完先核**两侧行数都非零**（正常同一量级）；一侧为 0 就是解释器 / 路径错了，
  **别继续解读 diff**。仓里现成可用的解释器见本文件末尾「或 `~/.workbuddy/binaries/...`」那句。
5. **改完代码 / 测试立刻跑一次 pyflakes，别只看 pytest 的 passed 数**（2026-09-20 实测）：
  那一批改写断言时，把「`assert cfg.get(…)`」这**一句整行挪进了另一个用例**，而新用例作用域里
  没有 `cfg` —— pytest 只报一条红，**pyflakes 直接给 `tests/test_config.py:451: undefined name
  'cfg'`**，一行定位。教训两条：① 挪错的句子要**放回原位**、不是删掉了事（它原本守的东西就没人守了）；
  ② `Edit` 的 `old_string` / `new_string` **都不带行尾换行**（带 `old_string` 会吞掉下一行、
  带 `new_string` 会插空行）—— 改完顺手 `git diff <file>` 数一下落盘处数。
